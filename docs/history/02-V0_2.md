# OpenSite Commerce V0.2 — 零授权费存储、Bun 选型与核心架构深化

**架构版本：V0.2**  
**目标：开源、自部署、低成本、高性能、支持 B2B/B2C、AI Agent 管理与可视化建站。**

这一轮我重新审查了 V0.1 的技术栈，重点考虑三个实际问题：

1. 用户可能只有一台服务器，却需要保存数万款商品及大量图片、视频。
2. 系统既要有足够好的运行性能，也要让独立开发者和 AI 编码代理高效开发。
3. 商品、企业资料、博客、模板、页面组件必须使用统一的数据和 API 架构，不能发展成几套相互独立的系统。

## 一、先修正两个关键架构决定

### 决定一：对象存储必须支持完全自部署、零软件授权费

我同意你的成本判断。

对于有数万款服装商品的商家，如果项目从一开始就强制使用按存储容量和流量计费的商业对象存储，确实可能增加长期运营成本。

但要区分：

**免费对象存储软件 ≠ 免费的物理存储资源。**

我们可以做到不强制支付任何对象存储软件订阅费，也不依赖商业对象存储服务。

但是硬盘、服务器、备份空间和公网带宽仍有实际成本。

因此，我建议改成三级存储架构：

| 存储模式 | 技术 | 软件授权费 | 用途 |
|---|---|---|---|
| 默认模式 | Go 原生文件系统存储 | 免费 | 单机部署、小中型网站 |
| 标准扩展 | RustFS 或 SeaweedFS 社区版 | 免费 | 大量商品图片、多磁盘存储 |
| 高级扩展 | 任意 S3 兼容存储 | 取决于供应商 | 多服务器、外部存储 |

**V0.2 正式决定：默认不强制安装独立对象存储服务。**

用户安装 OpenSite Commerce 后，系统直接使用服务器挂载的数据目录保存图片、视频和文档。

当商家的数据规模扩大，再切换到自部署的 S3 兼容存储。

这种设计比第一天就部署完整对象存储集群更轻便。

### 决定二：Bun 值得使用，但需要明确它负责什么

这里存在两个同名技术：

- **Bun JavaScript Runtime**：运行 JavaScript/TypeScript，集成包管理器、测试运行器和构建工具。
- **Bun Go ORM**：Uptrace 开发的 Go 数据库操作库，用于 PostgreSQL 等数据库。

两者完全不同。

我核对了官方资料：

[Bun JavaScript Runtime](https://bun.sh/docs) 是基于 JavaScriptCore 的 JavaScript/TypeScript 工具链；它提供原生 HTTP Server、SQL 客户端和 S3 API。

[Uptrace Bun ORM](https://github.com/uptrace/bun) 则是基于 Go `database/sql` 的 SQL-first ORM，采用 BSD-2-Clause 许可证。

**我的初步推荐是：Go 继续承担交易和数据一致性要求较高的核心业务；Bun JavaScript 工具链可用于前端开发，并作为未来 TypeScript 服务端的候选技术。**

至于 Go Bun ORM，后面会单独比较它与 `pgx + sqlc` 的优劣。

## 二、重新设计免费的媒体存储体系

### 2.1 不应让所有用户为了上传图片而部署对象存储服务器

V0.1 存在一个不够简洁的地方：

即使用户只经营几百款商品，也需要理解 S3、Bucket、Access Key、对象存储服务。

这并不符合轻量化自部署的目标。

V0.2 改为：

```text
                   OpenSite Commerce
                          │
                          ▼
                    Media Service
                          │
                          ▼
                   Storage Interface
                          │
             ┌────────────┴────────────┐
             │                         │
             ▼                         ▼
      LocalStorageAdapter       S3StorageAdapter
             │                         │
             ▼                  ┌──────┼─────────┐
      本地SSD / HDD             │      │         │
      NAS挂载目录               ▼      ▼         ▼
                             RustFS SeaweedFS 其他S3
```

整个上层业务系统不需要知道图片实际存储在哪里。

商品、博客、企业介绍、页面编辑器和 Agent 都通过同一个媒体服务操作文件。

例如：

```http
POST /api/v1/media/uploads
GET  /api/v1/media/{id}
```

API 操作的是媒体资源，而不是磁盘的绝对路径。

### 2.2 文件系统模式

默认部署：

```text
/var/lib/opensite/
├── postgres/
├── media/
│   ├── originals/
│   ├── derived/
│   └── staging/
├── backups/
└── runtime/
```

这只是示意目录。生产环境的备份不应仅放在同一块磁盘中。

建议通过 Docker Volume 或 bind mount 持久化数据，不能将正式商品图片仅保存在容器可写层。

媒体文件使用系统生成的不可预测对象键，不直接使用用户提交的文件名作为路径。

这样能够避免文件名冲突和路径穿越问题。

**好处是：一个 Go 后端、一套 PostgreSQL、一个持久化媒体目录，就能完成基础独立站的部署。**

### 2.3 哪些免费开源对象存储值得考虑？

我重新核对了几个项目。

| 项目 | 许可证 | 适用特点 | 当前建议 |
|---|---|---|---|
| 本地文件系统 | 不需要额外软件 | 部署最简单 | 默认 |
| [RustFS](https://github.com/rustfs/rustfs) | Apache-2.0 | S3 兼容，提供单机及集群部署方式 | 优先验证 |
| [SeaweedFS](https://github.com/seaweedfs/seaweedfs) | Apache-2.0 | 面向大量文件的存储架构，可水平扩展 | 大规模场景候选 |
| [Garage](https://github.com/deuxfleurs-org/garage) | AGPLv3 | 面向小中型自部署、跨节点复制 | 特殊部署场景候选 |

RustFS 官方明确提供单服务器及多服务器部署方式，但单节点单磁盘模式没有额外的数据冗余，必须依赖备份。

SeaweedFS 开源仓库采用 Apache-2.0，同时存在独立的 Enterprise Edition；不能将企业版的恢复和自修复功能当成社区版默认能力。

Garage 完全可以免费部署，但 AGPLv3 需要在分发、修改和网络服务使用场景下认真遵守相应许可证义务。

### 2.4 当前选择

**我建议优先实现文件系统适配器，再测试 RustFS，而不是立即绑定 RustFS。**

原因很简单：

项目需要的是可替换的媒体存储能力，而不是开发另一套对象存储系统。

存储后端应该只是实现细节。

即使未来 RustFS 或其他项目的维护状况发生变化，OpenSite Commerce 也不应该受到重大影响。

这属于可以在 V0.2 确定的长期架构原则。

## 三、Bun 深度评估：是否应该替换 Go？

### 3.1 Bun JavaScript Runtime 的优势

Bun 不只是一个包管理器。

官方目前提供：

| 能力 | Bun 实现 | 对项目的价值 |
|---|---|---|
| JavaScript/TypeScript Runtime | 直接运行 TS/JS | 可以开发服务端 |
| HTTP Server | `Bun.serve()` | 可以构建高性能 API |
| PostgreSQL | 内置 `Bun.SQL` | 减少数据库客户端依赖 |
| S3 | 内置 S3 客户端 | 可以连接自部署 RustFS |
| 包管理 | `bun install` | 加快依赖安装 |
| 测试 | `bun test` | 前端及 TS 模块测试 |
| 构建 | `bun build` | 编译浏览器端和服务端代码 |

其中，Bun 内置的 S3 API 支持 S3 兼容存储以及预签名 URL。([Bun S3 官方文档](https://bun.sh/docs/runtime/s3))

需要特别注意：**Bun 的 S3 功能是客户端，不是对象存储服务器。** 它不能替代 RustFS 或本地文件系统。

### 3.2 Bun 能否实现整个独立站后端？

可以。

一种可能的全 TypeScript 架构是：

```text
React Admin
     │
     ▼
Bun + Hono API
     │
     ├── PostgreSQL
     ├── 商品管理
     ├── 企业CMS
     ├── 模板管理
     ├── Agent API
     ├── 订单处理
     └── 文件存储

Astro Storefront
     │
     ▼
Bun Runtime（候选）
```

好处是开发语言统一。

管理后台、API、SDK、模板 Schema 和 Agent 工具都可以使用 TypeScript。

对独立开发者而言，这可能减少跨语言数据类型维护的成本。

但有三个问题：

**第一，Bun 的快并不等于整个电商系统都会更快。**

Bun 在进程启动、部分 HTTP 处理和部分工具链任务上有优势，但真实电商响应时间还包含数据库、商品查询、库存锁、缓存、支付接口、SSR 渲染等。

这些必须使用相同业务负载测试，不能拿简单 HTTP benchmark 直接推断整个商城性能。

**第二，Bun 的生态兼容性需要验证。**

Astro 官方虽然提供 Bun 使用指南，但明确提醒某些集成可能存在兼容问题。([Astro 官方文档](https://docs.astro.build/en/recipes/bun/))

尤其应测试：

- Astro SSR。
- React Islands。
- 可视化编辑器。
- 动态主题加载。
- 图片处理依赖。
- 数据库连接池。
- 长时间运行的服务端任务。

**第三，订单、库存和支付系统更重视可预测性。**

例如商品库存只剩一件时，100 个请求同时下单，系统必须确保不会超卖。

这不是 Bun 或 Go 单独决定的，而是事务模型、数据库锁、幂等策略和状态机是否设计正确。

### 3.3 Go 与 Bun 的架构对比

| 维度 | Go | Bun + TypeScript |
|---|---|---|
| 原生编译 | 是 | Bun 运行时执行 JS/TS |
| 进程部署 | 单二进制优势明显 | 依赖 Bun 运行时 |
| HTTP 性能 | 高 | 高，具体取决于负载 |
| 内存效率 | 通常较适合轻量服务 | 需要测量 JS 堆及运行时开销 |
| 并发任务 | Goroutine | 异步 I/O；CPU 工作可用 Worker |
| 开发效率 | 简洁、类型安全 | 全栈 TS 类型复用优势 |
| 前端生态 | 需要 TS 配合 | 原生 TS 生态 |
| 数据一致性 | 成熟的 PostgreSQL 工具链 | 同样可以依靠 PostgreSQL 保证 |
| 自部署 | 部署路径简洁 | 同样可以容器化 |
| 长期维护 | 适合稳定业务核心 | 适合快速发展的 TS 应用 |

我不认为存在一种编程语言，在所有电商场景下都同时拥有最高开发效率、最低内存和最快响应时间。

### 3.4 V0.2 的选型决定

我的推荐：

| 模块 | 技术 |
|---|---|
| 核心 API | **Go** |
| 商品、订单、库存 | Go |
| PostgreSQL 访问 | pgx + sqlc |
| 后台管理 UI | React + TypeScript |
| 前端开发工具 | **Bun** |
| 网站展示 | Astro |
| 网站 SSR 运行时 | Node.js 稳定基线；Bun 作为候选 |
| 主题 SDK | TypeScript |
| Agent SDK | TypeScript + OpenAPI |
| 对象存储 | 本地文件系统 / S3 兼容实现 |

这并不意味着必须永久保留 Node.js。

应该先做一个真实原型，使用同一套 Astro 页面在 Node.js 和 Bun 下对比：

- 运行内存。
- 冷启动。
- SSR p95 延迟。
- 并发页面渲染。
- 第三方插件兼容性。
- 长时间运行稳定性。

如果 Bun 通过相同的功能测试，并在资源开销上具有优势，可以将它升级为默认网站 SSR 运行时。

**但不建议仅凭宣传性能数字，立即把成熟交易内核整体改为 Bun。**

### 3.5 如果你说的 Bun 是 Go ORM

这个库也值得考虑，但我的结论有所不同。

[Uptrace Bun](https://github.com/uptrace/bun) 采用 SQL-first 设计，支持关联查询、结构体映射、迁移和软删除。

例如大量后台列表、普通 CMS 数据的 CRUD，用 Bun ORM 确实能减少手写代码。

但你的项目中有：

- 多租户隔离。
- 大批量 SKU 写入。
- 复杂客户定价。
- 库存原子更新。
- 订单事务。
- 数据库 RLS。
- 显式审计。

这些操作更适合精确控制 SQL。

因此我的建议是：

**核心数据库访问继续采用 `pgx + sqlc`，不要在 V0.2 引入第二套 ORM。**

sqlc 官方支持生成基于 `pgx/v5` 的 Go 数据访问代码。([sqlc 官方文档](https://docs.sqlc.dev/en/latest/guides/using-go-and-pgx.html))

后续如果普通 CMS 模块的大量简单 CRUD 显著拖慢开发，可以用独立原型比较 Bun ORM 和 sqlc 的代码量、查询行为及事务一致性。

但不应把二者混用成为默认架构。

## 四、ARCH-002：重新设计数据库与业务实体

这一部分是本轮最重要的架构深化。

我建议不要先建几十张表再考虑网站怎么使用，而是先确定：

**哪些是业务事实，哪些是展示配置，哪些是发布后的内容。**

### 4.1 采用三层数据模型

```text
┌─────────────────────────────────────────────┐
│ 第一层：Business Data（业务事实层）          │
│                                             │
│ 商品、SKU、属性、价格、库存、订单、客户       │
│ 企业资料、媒体资产、博客内容                 │
└───────────────────┬─────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│ 第二层：Presentation Data（展示配置层）      │
│                                             │
│ 主题、页面模板、组件、布局、数据绑定          │
│ 设计令牌、展示规则、多语言配置               │
└───────────────────┬─────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│ 第三层：Published Views（已发布视图层）      │
│                                             │
│ 商品页面、首页、企业介绍、博客、分类页        │
│ SSR HTML、公开API响应、搜索索引             │
└─────────────────────────────────────────────┘
```

三层分别承担不同的职责。

**第一层回答“是什么”。**

例如：一款衣服有六种颜色、五个尺码、对应价格和库存。

**第二层回答“如何展示”。**

例如：商品详情页使用左侧图片、右侧规格选择器的布局。

**第三层负责向访问者提供最终内容。**

例如：用户通过手机打开商品页面，系统结合商品数据和模板生成 HTML。

这一设计允许商品数量增长到数万款，而模板数量依然相对有限。

### 4.2 正式确立五个顶层实体

我建议将整个系统最重要的实体确定为：

| 实体 | 含义 |
|---|---|
| Tenant | 独立的数据与权限边界 |
| Organization | 企业或经营主体 |
| Site | 独立网站、品牌官网或商城 |
| Sales Channel | 销售渠道及交易规则 |
| Market | 国家、语言、币种和区域市场 |

例如：

```text
Tenant：一家服装企业
  │
  ├── Organization：企业法律主体
  │
  ├── Site A：品牌零售官网
  │      └── B2C Channel
  │
  ├── Site B：服装批发官网
  │      └── B2B Channel
  │
  └── Catalog：共享商品目录
```

这样，企业可以维护同一套 10,000 款服装商品，同时经营两个不同的独立站。

两个站点可以使用不同的：

- 域名和网站主题。
- 商品展示模板。
- 商品上架范围。
- 语言和市场。
- 价格表。
- 客户权限。
- 交易流程。

但不需要重复上传所有商品图片。

### 4.3 商品表与站点上架关系分开

建议引入：

`products`

存储商品主数据。

`product_variants`

存储 SKU 与规格组合。

`product_listings`

存储商品在哪个站点或渠道出售。

例如：

| Product | Site | 状态 | 价格规则 |
|---|---|---|---|
| Shirt-001 | Retail Site | 已上架 | 零售价格表 |
| Shirt-001 | Wholesale Site | 已上架 | 批发价格表 |
| Shirt-002 | Retail Site | 已上架 | 零售价格表 |
| Shirt-002 | Wholesale Site | 未上架 | — |

这比为每个网站复制一套商品表更加合理。

**商品是主数据，商品在哪个网站出售是渠道数据。**

这是应当固定下来的架构边界。

### 4.4 核心数据库必须有明确约束

建议建立以下硬性规则：

| 数据对象 | 必须具备的约束 |
|---|---|
| Product | 租户作用域、状态和版本 |
| SKU | 租户内 SKU 唯一性规则 |
| Variant | 同一商品不得有重复规格组合 |
| Media | 租户归属、完整性校验 |
| Page | 站点归属、草稿和发布版本 |
| Theme | 版本号、组件兼容信息 |
| Price | 币种、适用范围、生效规则 |
| Inventory | 原子更新、库存流水 |
| Order | 不可随意修改的成交快照 |
| API Operation | 请求身份、幂等与审计 |

对于商品规模，我不建议一开始按商品数量进行数据库分片。

**30 万 SKU 并不自动意味着 PostgreSQL 单库无法处理。**

更应该先验证索引、查询计划、批量写入方式和搜索模型。

多租户数据表使用 `tenant_id`，配合复合唯一约束、复合外键和 RLS，避免跨租户引用。

运行时数据库账号不拥有 DDL 权限或 `BYPASSRLS`，需要保护的业务表启用 `FORCE ROW LEVEL SECURITY`。

PostgreSQL 官方明确说明了表所有者和特殊角色绕过 RLS 的情形，因此必须结合角色权限一起设计。([PostgreSQL 18 文档](https://www.postgresql.org/docs/18/ddl-rowsecurity.html))

## 五、ARCH-009：媒体存储的数据结构和迁移机制

免费存储只是第一步。

真正重要的是：**用户在使用几年后，能够更换硬盘、服务器和存储系统，而不需要重建几万个商品。**

### 5.1 引入统一的 Blob 与 Media 模型

我建议将媒体进一步分成两个概念。

**Blob：真实二进制文件。**

保存：

```text
blob_id
tenant_id
storage_backend
storage_key
content_hash
byte_size
mime_type
status
created_at
```

**Media Asset：用户能够管理的媒体资源。**

保存：

```text
media_id
tenant_id
blob_id
filename
title
alt_text
width
height
duration
visibility
created_at
```

例如用户上传一张服装主图：

文件本身是 Blob。

商品系统看到的是 Media Asset。

同一张图片被五个地方引用时，只需要维护一个物理原文件。

在同一租户内，可以利用文件哈希进行安全去重。

初期不建议做跨租户自动去重，以免引入文件存在性、访问控制和删除生命周期方面的复杂问题。

### 5.2 加入 Media Usage

单独建立：

`media_usages`

记录文件在什么地方使用。

例如：

| Media | Resource | Role |
|---|---|---|
| image_001 | product_001 | main_image |
| image_002 | product_001 | gallery |
| image_003 | company_001 | factory_photo |
| image_004 | post_001 | cover |
| video_001 | product_001 | demonstration |

这样不仅能够判断哪些文件正在使用，也方便 Agent 批量替换商品图片。

用户删除某个商品时，系统不应直接删除仍被博客或其他页面引用的图片。

### 5.3 文件上传状态机

我建议使用以下状态：

```text
RESERVED
    ↓
UPLOADING
    ↓
UPLOADED
    ↓
VERIFYING
    ↓
PROCESSING
    ↓
READY
```

错误进入 `FAILED`，遗留的未完成上传进入后续清理流程。

**只有 READY 的公开媒体才允许出现在正式网站中。**

图片上传后需要验证实际文件类型、大小、解码尺寸及内容哈希。原文件和生成的缩略图应分开管理。

文件系统与 PostgreSQL 不支持直接共享一个数据库事务，因此需要使用状态机和幂等的后台任务处理文件落盘、数据库提交及失败恢复。

### 5.4 本地存储与 S3 的接口

Go 后端只应通过统一接口访问文件。

例如：

```go
type BlobStore interface {
    Put(ctx context.Context, key string, r io.Reader, size int64) error
    Open(ctx context.Context, key string) (io.ReadCloser, error)
    Stat(ctx context.Context, key string) (BlobInfo, error)
    Delete(ctx context.Context, key string) error
}
```

实际实现分开：

```text
storage/
├── storage.go
├── local/
│   └── local.go
└── s3/
    └── s3.go
```

分片上传、范围读取和预签名 URL 可作为扩展能力，避免要求所有存储后端必须提供完全相同的高级功能。

本地存储可通过 Go 上传接口接收文件。

S3 模式则可提供预签名上传 URL，让浏览器直接上传到 RustFS。

上传完成后都进入同一套媒体验证和处理流程。

### 5.5 不允许存储迁移破坏商品页面

假设用户最初使用：

`/data/media/`

两年后，商品图片已经增长到 500GB。

用户购买新硬盘，决定迁移到 RustFS。

理想的迁移流程应该是：

```text
本地文件系统
     │
     ▼
建立迁移清单
     │
     ▼
复制到 RustFS
     │
     ▼
逐文件校验 SHA256
     │
     ▼
验证媒体引用
     │
     ▼
切换读取后端
     │
     ▼
确认无误后清理旧文件
```

迁移过程中，原始商品的 `media_id` 不应变化。

正式页面也不应该永久保存后端的物理文件路径。

页面使用稳定的媒体资源地址，由媒体服务映射到当前存储后端。

为降低迁移风险，还可以保留一段时间的旧后端读取回退能力。

**这是 V0.2 的一项关键验收标准：媒体存储迁移不得要求重新上传商品。**

### 5.6 图片和视频的成本控制

建议将媒体处理策略分成三类。

| 类型 | 默认策略 |
|---|---|
| 商品原图 | 保存一份原文件 |
| 商品展示图 | 按需生成优化版本并缓存 |
| 商品视频 | 保存原文件，按需求生成封面和播放版本 |

图片转换任务应有并发、内存、像素数量和时间预算。

视频转码不应默认对每个上传文件生成大量码率版本。

当用户只需要企业展示视频时，也可以选择使用外部视频嵌入，避免将所有视频流量放在自己的服务器上。

不过外部视频服务可能引入第三方依赖、隐私和播放限制，需要作为可选方式。

### 5.7 免费存储也必须解决备份问题

例如原始商品图片和视频共占 360GB。

如果还需要一份完整的异地备份，那么仅原始数据的两份副本合计就需要约 720GB，尚未计算缩略图、历史版本和数据库。

因此，不能把 RAID、磁盘镜像或同盘备份当成完整的数据保护方案。

最少需要：

**主数据存储 + 独立备份目标 + 定期恢复验证。**

自部署软件可以免费，但数据保护不能省略。

## 六、ARCH-004：模板引擎进一步深化

V0.1 只定义了组件和页面结构。

现在需要处理更核心的问题：

**如何让用户通过 API 或 Agent 自由修改网站，同时保证模板安全、可升级、不会拖慢大量商品页面？**

### 6.1 不允许为每个商品生成一份独立模板代码

如果商家有 10,000 款商品，就应该：

```text
10,000 Products
      │
      ▼
Product Detail Template
      │
      ▼
Component Renderer
      │
      ▼
10,000 个按需渲染的商品页面
```

而不是：

```text
10,000 Products
      │
      ▼
10,000 套 HTML / React 页面源码
```

页面内容是动态绑定的。

模板本身可以被复用。

这样修改一次商品页的 UI 布局，就能够更新整个商品类别的网站呈现。

### 6.2 模板需要支持继承

建议采用四级优先级：

| 优先级 | 模板范围 |
|---|---|
| 1 | 商品专属模板 |
| 2 | 商品分类模板 |
| 3 | 站点默认商品模板 |
| 4 | 主题默认模板 |

优先级高的模板存在且有效时，使用它；否则逐级回退。

例如：

服装商城默认使用普通商品详情模板。

鞋类商品可以使用鞋码选择器模板。

部分高端商品可以单独配置品牌展示模板。

这样既有规模化，也有局部自定义能力。

### 6.3 建立标准化组件数据绑定协议

模板组件不应该直接知道 PostgreSQL 表结构。

例如一个商品展示组件：

```json
{
  "id": "featured-products",
  "component": "catalog.product-grid",
  "component_version": 1,
  "props": {
    "desktop_columns": 4,
    "mobile_columns": 2,
    "show_price": true
  },
  "binding": {
    "resolver": "catalog.collection",
    "params": {
      "collection_id": "new-arrivals",
      "limit": 8
    }
  }
}
```

这里有几个重要设计。

`component` 指向已注册的组件。

`props` 经过 Schema 校验。

`binding` 指向允许使用的数据解析器。

`params` 只能传递经过验证的查询参数。

Agent 不能通过模板配置提交任意 SQL，也不能随意指定内部 API URL。

### 6.4 建立 Data Resolver Registry

建议正式引入这一层：

```text
Page Template
      │
      ▼
Component Bindings
      │
      ▼
Data Resolver Registry
      │
      ├── catalog.product
      ├── catalog.collection
      ├── catalog.category
      ├── company.profile
      ├── company.gallery
      ├── cms.blog-posts
      ├── cms.related-posts
      └── site.navigation
      │
      ▼
Go Read Services
      │
      ▼
PostgreSQL
```

这是本轮最重要的新增设计之一。

**Data Resolver Registry 是商品系统、CMS 和模板系统之间的正式边界。**

好处有三个。

第一，前端组件不需要理解内部数据库结构。

第二，API 和 Agent 可以通过统一的组件协议修改数据绑定。

第三，后端可以统一处理缓存、权限和查询优化。

例如首页同时包含三个商品组件，服务端可以合并或批量执行查询，避免每个商品卡片都单独调用一次 API。

### 6.5 区分主题包与页面配置

不能把主题理解成一个巨大的 JSON 文件。

建议：

```text
Theme Package
 ├── component manifest
 ├── component versions
 ├── layout definitions
 ├── design token schema
 └── asset definitions

Site Theme Installation
 ├── theme_id
 ├── installed_version
 └── token overrides

Page
 ├── page_id
 ├── template_id
 ├── draft_revision
 └── published_revision
```

主题包由开发者构建并安装。

普通用户通过管理后台或 API 修改页面配置和样式参数。

第一版的第三方主题建议以声明式配置为主。需要运行自定义代码的高级主题则作为受控开发者扩展，不能让普通内容配置变成服务器任意代码执行入口。

### 6.6 页面发布必须是原子操作

这是建站系统经常被忽视的问题。

假设 Agent 正在修改首页，已经更新了 Banner，但商品模块尚未配置完成。

此时访客不能看到半成品。

正确流程：

```text
Published Revision 12
         │
         ├── 正式网站继续使用 Revision 12
         │
         ▼
Draft Revision 13
         │
         ├── 修改 Banner
         ├── 修改商品组件
         ├── 调整导航
         └── 预览
                │
                ▼
          Validate & Publish
                │
                ▼
Published Revision 13
```

数据库中可以通过一次事务更新发布版本指针。

新的访客读取新版本，旧版本可用于回滚。

商品库存、实时价格等业务状态不应被冻结在页面版本中，而应由相应业务服务按当前有效规则提供。

### 6.7 页面缓存策略

建议：

| 页面内容 | 缓存方式 |
|---|---|
| 企业介绍 | 长缓存，发布时失效 |
| 博客 | 长缓存，内容修改后失效 |
| 普通商品详情 | 商品版本关联缓存 |
| 商品列表 | 短缓存或事件驱动失效 |
| 库存 | 动态查询 |
| B2B 专属价格 | 按身份授权，不使用共享公共缓存 |
| 购物车 | 用户私有状态 |

大量商品不等于大量页面必须提前生成。

Astro 可以按需 SSR，再结合缓存处理热门商品页面。

同一个网站更换模板时，也不应该重新构建整个 Astro 应用。

模板数据通过 API 更新，渲染组件则来自已经部署的组件注册表。

## 七、ARCH-006：Agent 批量操作的底层执行机制

这一轮建议把 Agent 架构再收紧一些。

**Agent 不应该直接获得数据库操作能力，而应该使用与后台一致的领域命令。**

### 7.1 三种入口，共用一套领域服务

```text
管理后台用户
       │
第三方 API 客户端
       │
AI Agent / MCP
       │
       ▼
Authentication / Authorization
       │
       ▼
Command Validation
       │
       ▼
Domain Services
       │
       ▼
PostgreSQL + Media Storage
```

例如修改商品价格，无论调用者来自 React 后台、ERP 还是 AI Agent，最终都进入相同的价格服务。

这样可以避免 Agent 绕过 MOQ、价格约束或发布审批。

### 7.2 Agent 批量修改采用统一任务模型

建议正式建立：

`bulk_jobs`

`bulk_job_items`

`operation_audits`

`approval_requests`

任务至少支持以下状态：

```text
CREATED
   ↓
VALIDATING
   ↓
VALIDATED
   ↓
AWAITING_APPROVAL（按策略）
   ↓
EXECUTING
   ↓
COMPLETED / PARTIALLY_COMPLETED / FAILED
```

部分失败要保留逐条结果及可重试信息。

例如批量导入 5,000 个 SPU、150,000 个 SKU 时，不应该把全部操作塞进一个巨大数据库事务。

应根据任务建立确定的批次和幂等标识，使用受限并发执行。

成功的批次保持成功状态，失败的批次能够安全重试。

### 7.3 批量任务应有明确资源预算

这一点尤其适合轻量部署。

建议每个任务具有：

| 预算 | 用途 |
|---|---|
| max_records | 最大处理记录数 |
| max_concurrency | 最大并发数量 |
| max_duration | 最长执行时间 |
| max_media_bytes | 最大媒体处理量 |
| max_retries | 最大重试次数 |
| max_memory | Worker 的资源限制 |
| max_external_calls | 外部 API 调用预算 |

这样 Agent 批量处理商品图片，不会无限占用服务器资源，影响网站正常销售。

实际预算值由部署配置和任务类型决定，不应在架构阶段承诺所有硬件使用同一额度。

### 7.4 Agent 需要理解字段来源

例如批量上架服装。

AI 可以根据图片推测颜色，但图片不能可靠证明面料成分、生产国或某项认证。

因此建议新增字段级溯源信息：

```text
value
source_type
source_reference
verification_status
updated_by
updated_at
```

来源可以是：

- 商家明确提供。
- 原始商品文件。
- 授权供应商资料。
- AI 推断。
- 人工审核。

对于高风险或关键交易字段，AI 推断不能直接等同于已确认的商品事实。

这套溯源能力应优先应用于商品属性补全和批量内容生成，不需要将所有简单字段都设计成复杂审批工作流。

## 八、V0.2 最小部署架构

经过这一轮调整，我建议默认安装只包含真正必要的运行组件。

```text
                      用户浏览器
                          │
                          ▼
                     Caddy / HTTPS
                          │
        ┌─────────────────┼──────────────────┐
        │                 │                  │
        ▼                 ▼                  ▼
   Astro SSR          React Admin         Go API
  网站展示服务          静态文件           业务内核
        │                 │                  │
        └─────────────────┴──────────────────┤
                                             │
                           ┌─────────────────┤
                           │                 │
                           ▼                 ▼
                       PostgreSQL       本地媒体目录
                           │                 │
                           ▼                 ▼
                       后台任务         图片/视频/附件
```

其中：

- React Admin 在生产中是预先构建的静态资源。

## 九、V0.2 需要做的六项工程验证

技术选型不应该仅靠主观判断。

正式开发前，我建议针对最有争议、最可能影响架构的部分建立验证任务。

| 编号 | 验证主题 | 测试内容 | 验收重点 |
|---|---|---|---|
| POC-01 | Bun vs Node | 同一 Astro SSR 应用 | 兼容性、内存、延迟 |
| POC-02 | Go vs Bun API | 同一商品查询与批量写入场景 | 总资源消耗、吞吐、开发复杂度 |
| POC-03 | LocalFS vs RustFS | 上传、读取、删除、大文件分片 | S3 兼容性、数据完整性 |
| POC-04 | PostgreSQL 大 SKU | 10,000 SPU、300,000 SKU | 查询计划、索引、批量写入 |
| POC-05 | 动态模板 | 1,000 页面实例、多组件绑定 | SSR、缓存、页面发布 |
| POC-06 | Agent 批量操作 | 5,000 SPU 导入、故障和重试 | 幂等、审计、部分失败恢复 |

这些都只是**待执行的验证任务**，目前尚未运行压测，因此不能宣称某种运行时或存储引擎已经胜出。

其中 POC-03 应特别使用 RustFS 官方 S3 兼容性矩阵作为参考，因为官方明确区分已测试、尚未实现和有意排除的 S3 行为。([RustFS Compatibility Matrix](https://docs.rustfs.com/en/reference/s3-compatibility))

### 建议增加四项跨模块验收

**场景 A：商品和模板分离**

新增 10,000 款商品，使用同一个商品详情模板。修改模板后，商品记录保持不变，展示布局能够统一更新。

**场景 B：媒体迁移**

先使用 LocalFS 创建商品、企业页面和博客，再迁移至 RustFS。所有已发布内容中的媒体引用保持有效，文件哈希一致。

**场景 C：Agent 批量操作**

重复提交同一个批量任务，不产生重复 SKU。网络中断后可以继续处理，已有成功结果不重复写入。

**场景 D：主题升级**

从主题 V1 升级至 V2，已发布页面在新配置验证通过前不受影响，升级失败能够保持旧版本正常展示。

# 十一、下一轮应该深入解决什么？

现在 V0.2 已经确定了基本的服务划分和数据边界。

但我认为还存在一个比语言选型更重要的问题：

**如何让这个项目成为真正通用的建站平台，而不是一套只能使用开发者预制组件的商城？**

例如，某个商家希望用 Agent 完成以下操作：

> 创建一个服装品牌官网，使用黑白极简主题。首页展示新品和品牌故事。商品详情使用大图布局。增加 About、工厂介绍、博客和 WhatsApp 联系入口。B2B 客户可以询价，普通客户可以直接购买。

理想情况下，Agent 应通过一组受约束的 API，在不编写新的服务器代码的前提下完成：

网站创建 → 主题选择 → 页面编排 → 数据绑定 → 商品导入 → 内容生成 → 预览 → 发布。

但这需要进一步解决四项关键设计。

| 优先级 | 下一轮重点 | 必须解决的问题 |
|---|---|---|
| P0 | **建站 Schema 与组件协议** | 怎样通过 API 安全构造完整网站？ |
| P0 | **商品属性和行业模板协议** | 怎样让服装、香薰、家具共用一个 PIM？ |
| P0 | **发布与版本控制** | 怎样支持 Agent 修改、人工预览、原子发布和回滚？ |
| P1 | **站点数据解析与缓存** | 怎样高效渲染数万商品对应的页面？ |

建议下一轮产出两个更接近工程实现的规格：

**ARCH-002 V1：PostgreSQL 数据库详细设计。** 包含实体关系、字段、复合索引、唯一性约束、RLS、业务不变量和迁移方案。

**ARCH-004 V1：可编程网站构建协议。** 包含组件注册规范、JSON Schema、模板继承、资源绑定、主题安装、草稿发布及 Agent 修改 API。

这两份完成以后，就能从总体架构进入可执行的接口和数据库实施设计。

## 本轮最终结论

**免费对象存储：** 应该从第一版提供。默认 LocalFS，支持自部署 RustFS 或 SeaweedFS，不要求商家购买云存储服务。硬件、带宽和独立备份费用仍然存在。

**Bun：** 值得引入，尤其适合 TypeScript 工具链。若指 Go Bun ORM，它也是合理的 ORM，但暂时没有充分理由替换核心的 `pgx + sqlc`。若指 Bun JavaScript Runtime，可以重点验证 Astro SSR，暂不直接替换 Go 交易内核。

**核心架构：** 保持 Go + PostgreSQL + Astro + React，以统一 API、媒体服务、PIM 和模板协议构建业务能力。

**真正应该形成长期优势的部分：**

> 让用户仅依靠可视化组件、行业模板和经过授权的 API，就能建立、运营、批量维护一个完整的 B2B/B2C 独立站；AI Agent 则作为使用同一套 API 的自动化操作者，而不是拥有特殊数据库权限的另一套系统。

**V0.3 的首要工作应当是把模板建站能力从抽象架构落实为严格的数据结构、组件协议和发布流程。** 这将决定整个项目能否在支持高度自定义网站的同时，保持轻量、稳定和可升级。
