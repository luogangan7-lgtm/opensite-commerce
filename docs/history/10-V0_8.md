# OpenSite Commerce — 整体架构审查与模块化开发方案 V0.8

**审查范围：V0.1–V0.7 架构设计、PR-01 验收状态，以及前后端模块化开发、独立审核、PR、CI 和测试体系。**

## 一、总体结论

**当前技术架构可以保留，但项目的模块边界、依赖管理和工程交付体系还需要进一步完善。**

我不建议推翻已经确定的 Go、PostgreSQL、Astro、React、Bun 和 LocalFS 方案，也不建议转向微服务。

真正需要解决的，是以下六个问题：

| 优先级 | 发现的问题 | 建议 |
|---|---|---|
| P0 | 后端有业务模块规划，但缺少严格的依赖边界 | 建立 Go 模块化单体与模块接口规则 |
| P0 | React 管理后台和 Astro 店铺前端尚未形成对称的模块体系 | **前后端分别按业务领域模块化** |
| P0 | 数据库、API、前端组件和测试缺少统一的模块归属 | 建立模块清单与契约所有权 |
| P0 | PR-01 真实 PostgreSQL 18、sqlc 验收仍未完成 | 完成实库验证，再扩展基础业务 |
| P0 | 多编码代理并行容易造成跨模块修改、反复评审和 CI 资源浪费 | 建立 Contract First、独立审核、分层 CI |
| P1 | 商品规模化、媒体生命周期、主题升级与 Agent 发布缺少足够完整的跨模块验证 | 建立固定数据集、端到端测试和升级测试 |

### 我建议采用的最终组织方式

**一个 Monorepo，三个主要应用，多个业务模块，一套统一契约，一个模块化 Go 后端。**

```text
OpenSite Commerce
│
├── Backend
│   └── Go Modular Monolith
│
├── Admin Frontend
│   └── React Feature Modules
│
├── Storefront Frontend
│   └── Astro Commerce Modules
│
├── Shared Contracts
│   ├── OpenAPI
│   ├── JSON Schema
│   ├── TypeScript SDK
│   └── Event Contracts
│
├── PostgreSQL 18
├── River Background Jobs
└── LocalFS / S3 Storage
```

每个业务模块都有明确的后端、管理后台、店铺前端、API、数据库及测试归属。

例如商品模块不只是 `backend/catalog`，而是由以下部分共同构成：

```text
Catalog Module
│
├── Go 商品领域服务
├── PostgreSQL 商品数据
├── OpenAPI 商品契约
├── React 商品管理界面
├── Astro 商品展示组件
├── Agent 商品操作能力
└── 商品模块测试
```

**模块是业务能力的所有权边界，不一定是单独的进程、数据库或部署单元。**

这样可以实现模块化开发，同时保留单机部署的轻量优势。

# 三、后端：按业务领域划分 Go 模块

## 3.1 不采用微服务，采用有明确边界的模块化单体

建议每个后端模块拥有自己的：

- 领域模型与业务规则。
- Application Service。
- Repository 与 SQL 查询。
- HTTP API Handler。
- 后台任务。
- 权限定义。
- 事件定义。
- 单元及集成测试。

但所有模块可以编译为同一个 Go API 程序。

不要将“模块化”误解成必须部署 20 个独立服务。

但模块边界必须明确。

### 3.4 后端模块之间如何通信？

建议建立严格规则：

**规则 A：模块不能直接修改其他模块拥有的数据表。**

例如 Catalog 不能直接更新 `media_blobs`。

它通过 Media 模块提供的接口绑定媒体资源。

**规则 B：跨模块调用使用明确的 Application Port。**

例如商品发布需要确认媒体是否可用。

Catalog 可以调用：

```text
MediaAvailabilityChecker
```

而不是直接读取 Media Repository 的内部实现。

**规则 C：核心事务可以同步协调。**

例如库存预留和订单创建具有严格的一致性要求。

不能为了追求事件驱动，强行将所有关键业务操作变为异步。

**规则 D：非关键后续处理使用 River。**

例如：

- 生成缩略图。
- 更新搜索索引。
- 发送询盘通知。
- 批量导入处理。
- 清理过期文件。

**规则 E：禁止循环依赖。**

例如：

```text
Catalog → Media → Catalog
```

属于需要重新设计的依赖。

Media 应该管理文件与引用规则，而不是依赖整个商品模块。

### 3.5 SQL 也要按模块归属

继续采用 `pgx + sqlc`。

建议：

```text
db/
├── migrations/
│
└── queries/
    ├── identity/
    ├── site/
    ├── catalog/
    ├── media/
    ├── cms/
    ├── release/
    └── inquiry/
```

迁移文件仍然全局排序，保证所有模块使用同一个可靠的数据库版本。

查询文件按模块归属。

`sqlc` 支持在同一份配置里定义多个 SQL 查询集合，分别输出到不同的 Go 包，因此这种组织方式可以直接落地。([sqlc 官方配置文档](https://docs.sqlc.dev/en/latest/reference/config.html))

不建议第一阶段强制每个模块单独创建 PostgreSQL Schema。

目前已经采用 `app` Schema，可以继续保留，通过表所有权清单、复合外键、数据库角色、Repository 边界和 CI 检查控制访问。

避免为了目录整洁而重新设计全部数据库命名空间。

# 四、前端必须分为两个独立的模块化应用

这一点尤其重要。

**React Admin 和 Astro Storefront 不应该是一套混在一起的前端。**

它们的用户、性能目标和交互方式完全不同。

管理后台重视操作能力。

店铺前端重视加载速度、SEO、内容展示和转化。

因此，采用两个独立应用，但共享必要的契约和基础设计系统。

**第一，不直接修改其他 Feature 的内部状态。**

**第二，不在前端重新实现商品业务规则。**

例如 SKU 唯一性、正式价格、MOQ 和商品发布条件，最终都必须由 Go 后端判断。

React 可以提前校验表单以改善体验，但不是业务数据的最终权威。

建议保留少量稳定基础组件：

```text

├── Select
├── Dialog
├── DataTable
├── FormField
├── Pagination
├── FileUploader

```

这些属于通用 UI。

但以下组件不应该无条件放入公共 UI 包：

- 商品 SKU 编辑器。
- B2B 阶梯定价表单。
- 订单退款操作面板。
- 页面组件树编辑器。

它们属于具体业务模块。

**公共组件库只抽取稳定且真正复用的基础能力，不要提前做成另一个大型框架。**

推荐：

```text
apps/storefront/src/
│

│   ├── index.astro
│   └── [...path].astro
│
├── runtime/
│   ├── route-resolver/
│   ├── release-resolver/
│   ├── component-registry/

├── modules/
│   ├── site-shell/
│   ├── company/
│   ├── catalog/
│   ├── cms/
│   ├── inquiry/
│   ├── search/
│   ├── customer/
│   ├── commerce/
│   ├── localization/
│   └── seo/
│
├── themes/
│

```

Storefront 的每个模块负责某一类公开展示能力。

例如 Catalog：


### 4.4 页面编辑器是独立的 Admin Feature

可视化建站器不应侵入所有前端模块。

建议：

```text
features/page-builder/
├── editor/
├── component-tree/
├── property-panel/
├── preview/
├── operations/
├── history/
└── tests/
```

Builder 读取 Component Registry 和 Editor Schema。

它只负责：

- 组件选择。
- 拖拽与排序。
- 参数修改。
- 数据绑定。
- 草稿管理。
- 预览。
- 发布申请。

真正页面渲染仍由 Astro 完成。

这样可以避免同时维护一套 React 页面渲染器和一套 Astro 页面渲染器。

### 4.5 前端模块的强制规则

| 规则 | 目的 |
|---|---|
| Feature 只公开稳定入口 | 防止跨模块引用内部文件 |
| API 统一使用生成的 SDK | 避免自行拼 URL 和请求格式 |
| 服务端状态不在多个 Feature 中重复维护 | 避免缓存和更新不一致 |
| 组件配置使用共同 JSON Schema | 保证编辑器和 Renderer 一致 |
| 所有发布操作经过 Go API | 防止前端绕过授权 |
| 大型模块支持路由级代码拆分 | 控制 Admin 资源加载 |
| Storefront 默认 SSR，按需 Hydration | 控制浏览器端 JavaScript |
| 跨模块改动需要契约测试 | 防止局部更新破坏其他模块 |

**不需要一开始使用 Module Federation 或微前端。**

Monorepo 中的模块化目录、清晰的导出接口和构建边界已经足够。

微前端会增加部署、版本兼容和样式隔离成本，对当前独立开发者项目没有明显收益。

# 五、前后端统一的模块目录与契约

这是我建议新增的核心工程机制。

## 5.1 建立 Module Registry

在仓库中建立：

```text
modules/
├── identity.yaml
├── site.yaml
├── catalog.yaml
├── media.yaml
├── company.yaml
├── cms.yaml
├── presentation.yaml
├── release.yaml
└── inquiry.yaml
```

每个文件描述一个业务模块的代码和契约归属。

例如：

```yaml
id: catalog
version: 1

backend:
  path: apps/api/internal/modules/catalog

admin:
  path: apps/admin/src/features/catalog

storefront:
  path: apps/storefront/src/modules/catalog

contracts:
  openapi: contracts/openapi/catalog
  schemas: contracts/schemas/catalog

database:
  queries: db/queries/catalog
  tables:
    - products
    - product_variants
    - product_attributes
    - product_listings

dependencies:
  - media
  - site

tests:
  - unit
  - contract
  - integration
```

这份文件是**建议引入的模块元数据格式**，不是当前仓库中已经实现的能力。

### 它有什么价值？

例如修改：

```text
contracts/openapi/catalog/
```

CI 就知道需要验证：

```text
Go Catalog
React Catalog
Astro Catalog
TypeScript SDK
Catalog Contract Tests
```

如果修改 Media API：

```text
Media
  ├── Catalog
  ├── CMS
  └── Site Builder
```

这些依赖方应进入影响范围。

**不能仅凭文件路径属于哪个目录，就认为其他模块完全不会受到影响。**

### 5.2 防止模块注册表变成另一份手工维护的真相

Module Registry 只负责声明所有权和依赖。

它不应重新定义 OpenAPI、数据库 Schema 或组件 JSON Schema 的具体内容。

正式权威关系：

| 对象 | 权威来源 |
|---|---|
| API 结构 | OpenAPI |
| 数据库结构 | PostgreSQL Migrations |
| 组件参数 | JSON Schema |
| 页面数据 | PageDocument |
| 业务规则 | Go Domain Service |
| 模块归属 | Module Registry |
| 依赖版本 | 锁文件和组件 Manifest |

CI 应检查 Module Registry 指向的路径是否存在、依赖是否形成循环，以及新增业务目录是否缺失模块归属。

这样能支持模块化开发，而不是引入更多重复配置。

# 六、反向审查：整个架构还有哪些实质性问题？

下面不再重复已有功能，而是优先指出可能造成安全问题、大规模返工或项目长期难以维护的缺口。

## 6.1 P0：数据库与 API 还没有经过完整的运行验证

这是当前最高优先级。

根据此前 PR-01 的验收记录：

- PostgreSQL 18 实际迁移尚未通过。
- `sqlc generate` 尚未完成真实验证。
- `pgx` 适配器尚未完成依赖编译。
- RLS 和数据库角色权限还没有真实执行结果。
- 生产级 API 和 Astro SSR 闭环还没有建立。

所以当前应将项目状态定义为：

**Architecture Defined / Foundation Partially Implemented / Integration Not Accepted**

而不是“数据库基础已经完成”。

建议立即建立一个固定的 PostgreSQL 18 集成测试环境，真正执行所有迁移，再验证租户隔离和生成代码。

这一步必须通过，才能认为基础设施具备后续模块开发的可靠条件。

## 6.2 P0：商品、价格、库存与交易必须分别拥有数据

之前已确定 Product 与 Variant 分离，这是正确的。

但还需要明确：

```text
Catalog
   │
   ├── Product
   ├── Variant
   └── Product Listing

Pricing
   │
   ├── Price List
   ├── Customer Price
   └── Quantity Tiers

Inventory
   │
   ├── Stock
   ├── Reservation
   └── Movement

Order
   │
   ├── Order
   ├── Order Item
   └── Order Snapshot
```

**不能将价格、库存和成交订单重新塞进 Catalog。**

否则 Catalog 以后会变成整个项目最大的耦合模块。

特别是 B2B：

- MOQ 属于采购规则。
- 阶梯价属于定价。
- 客户专属价格属于 Pricing + Customer。
- 询盘属于 Inquiry。
- 报价属于未来的 B2B Sales 流程。
- 订单属于 Order。
- SKU 属性属于 Catalog。

各模块可以协作，但业务事实必须有唯一所有者。

## 6.3 P0：页面编辑器与真实 Storefront 的一致性风险

之前已经确定使用 Astro 作为最终渲染器，但还需要进一步确保：

1. React Builder 修改的是规范化 PageDocument。
2. Go 后端执行最终 Schema 与业务验证。
3. Astro 根据已注册组件渲染。
4. 预览与正式网站使用同一套组件。
5. 组件契约升级不能破坏历史 Release。
6. 页面发布不能直接执行 AI 生成的 JavaScript。

这里不建议让 Puck、GrapesJS 或其他编辑器库决定项目的数据格式。

编辑器库只能作为交互实现。

**PageDocument 和 Component Registry 才是平台的长期核心契约。**

## 6.4 P0：Theme、Industry Package 和 Component Package 不能混淆

现在有三个模板概念：

| 概念 | 应该负责什么 | 不应该负责什么 |
|---|---|---|
| Theme Package | 网站颜色、字体、页面视觉和布局预设 | 修改商品事实、价格和订单 |
| Industry Package | 商品类型、行业属性、导入映射、行业页面预设 | 执行任意数据库 DDL |
| Component Package | 提供实际可用的页面组件实现 | 绕过权限执行任意业务操作 |

这个边界需要固定。

例如服装行业包可以定义颜色、尺码和尺码表。

服装主题可以决定商品图片在左还是在右。

商品规格选择器则是一个组件。

这样用户能够自由组合行业和主题，而不必把每个行业都做成完全不同的商城。

## 6.5 P0：LocalFS 的扩容边界尚未充分定义

本地文件系统免费、轻量，继续作为默认选择。

但必须明确：

**默认 LocalFS 主要适合单实例或共享同一可靠存储卷的部署。**

如果未来横向扩容三个 Go API 实例，而每台机器使用自己的本地目录，就可能出现：

- A 实例上传图片。
- B 实例读取不到图片。
- C 实例误判图片不存在。

因此需要明确的 Storage Profile：

| Profile | 存储方式 | 部署能力 |
|---|---|---|
| Local Single Node | 本地磁盘 | 默认单机 |
| Shared Storage | 共享持久化存储 | 依赖共享存储的正确性 |
| S3 Compatible | RustFS/SeaweedFS 等 | 适合进一步扩容 |

媒体数据库中的稳定 Media ID 能够支持迁移，但不能自动解决分布式文件一致性问题。

同时必须实现：

- 文件引用保护。
- 上传状态机。
- 媒体完整性校验。
- 备份和恢复。
- 存储容量统计。
- 后台处理资源预算。

软件授权可以免费，但磁盘、备份和带宽仍有成本。

## 6.6 P0：Agent 操作不能形成第二套业务后门

未来 AI Agent 会修改：

- 商品。
- 图片。
- 属性。
- 博客。
- 企业资料。
- 网站页面。
- 价格。
- 库存。

建议架构明确：

```text
React Admin ──────┐
                  │
External API ─────┼──> Go Domain Commands
                  │
AI Agent ─────────┘
```

三者调用相同的领域操作。

Agent 可以使用 MCP，但 MCP 只是工具适配层。

不能让 Agent 直接执行 SQL、修改磁盘上的业务文件，或绕过页面发布审核。

对于批量修改，至少具备：

**Validate → Diff → Authorize → Execute → Audit**

对价格、库存、企业敏感资料及正式发布，还需要根据风险级别执行更严格的审批。

## 6.7 P1：跨模块查询和缓存尚未形成完整策略

商品详情页可能同时需要：

- Catalog：标题、SKU、属性。
- Media：商品图片。
- Pricing：价格。
- Inventory：可售状态。
- CMS：详情内容。
- Site：语言和市场。

不能让 Astro 的每个组件分别发送多次网络请求。

建议由 Go 提供**批量 Read Model / Render Context**，一次组织页面需要的数据。

但 Render Context 只负责读模型，不拥有商品、价格或库存的写入权。

缓存也必须区分公共数据与私有数据：

| 数据 | 策略 |
|---|---|
| 公共企业资料 | 可缓存 |
| 公共博客 | 可缓存 |
| 公开商品介绍 | 可缓存 |
| 实时库存 | 受控更新 |
| 客户专属价格 | 身份相关，不能进入共享公共缓存 |
| 购物车 | 用户私有 |
| 订单与支付 | 不作为公共页面缓存 |

第一阶段可以先采用保守缓存，待真实压测后再增加 Valkey 或其他缓存组件。

## 6.8 P1：多语言、币种和市场需要明确归属

这部分在前几轮中出现过，但尚未充分落到模块关系中。

建议明确：

- Localization 管理语言、翻译和回退规则。
- Site 管理启用的语言及市场。
- Pricing 管理币种和市场价格。
- Catalog 管理商品事实和可翻译商品内容。
- CMS 管理文章和企业介绍翻译。
- SEO 管理多语言 URL、Canonical 和 hreflang。

不能因为用户切换了网站语言，就让商品主数据和 SKU 身份发生变化。

同样，展示币种转换不等于存在对应币种的正式成交报价。

## 6.9 P1：运营后台缺少完整的经营闭环

从长期产品能力来看，还需要补充：

- 商品批量导入、导出和差异比较。
- 商品资料完整性检查。
- 媒体重复和无引用文件管理。
- SEO 批量检查。
- 询盘跟进与客户管理。
- 站点备份恢复。
- 批量任务失败重试。
- API Key、Webhook、任务日志管理。
- 经营分析和商品表现。
- 主题、组件及行业包升级状态。

但不建议现在全部实施。

这些属于模块内的后续能力，应进入 Roadmap，而不是不断增加新的顶层服务。

## 6.10 P1：缺少统一的可观测性与发布运维规范

所有模块至少需要统一：

```text
request_id
tenant_id
site_id
module
operation
duration
result
error_code
```

敏感字段必须脱敏。

需要能够追踪：

```text
Agent 批量创建商品
       ↓
Catalog API
       ↓
PostgreSQL Transaction
       ↓
River Job
       ↓
Media Processing
       ↓
Product Publication
```

如果某个商品上架失败，应该能从 Job ID 找到实际失败阶段，而不必从多个容器日志中人工推测。

同时还应具备：

- 健康检查。
- 数据库连接池指标。
- 后台任务积压指标。
- 媒体存储容量。
- SSR 错误率。
- 发布成功率。
- 备份恢复演练。
- 安全事件审计。

这些是支持真实经营站点必须具备的运维能力。

| 项目 | 决定 | 理由 |
|---|---|---|

**整体架构目前最大的风险不是缺少功能，而是过早实施过多功能，却没有先验证数据、组件和接口之间的基本契约。**

# 九、模块化开发流程

## 9.1 一个模块不等于一个巨大 PR

例如 Catalog 最终会有数万行代码。

不应该创建一个 PR，同时包含：

- 所有数据库表。
- 所有 Go API。
- 所有 React 表单。
- 所有 Astro 组件。
- 全部 Agent 接口。

这样的 PR 无法有效审查，也会使 CI 失败难以定位。

建议采用：

**一个需求 → 明确契约 → 一个可独立验收的变更 → 一个分支 → 一个 PR。**

但这里需要区分两种情况。

### 情况 A：单模块内部改动

例如：

> 商品编辑器增加 SKU 批量删除功能。

可以在一个 PR 中修改：

```text
apps/api/internal/modules/catalog/
apps/admin/src/features/catalog/
contracts/openapi/catalog/
tests/
```

这是一个跨前后端的纵向功能 PR。

只要改动围绕同一个业务行为，就不需要机械地拆成“后端 PR”和“前端 PR”。

### 情况 B：多个模块共同修改公共契约

例如：

> Media API 变更文件引用方式，Catalog 和 CMS 都要使用新结构。

建议：

1. 首先提出契约变更。
2. 确定向后兼容方案。
3. 在单独的 Contract PR 中引入新版本。
4. 各业务模块分别迁移。
5. 最后在单独 PR 中移除旧契约。

**不要让三个编码代理同时自行修改同一份公共 Schema。**

这是减少集成冲突最重要的规则之一。

## 9.2 开发任务的标准生命周期

```text
Issue / Feature Proposal
           │
           ▼
确定所属模块及依赖
           │
           ▼
定义 Acceptance Criteria
           │
           ▼
确认 API / Schema / ADR
           │
           ▼
创建功能分支
           │
           ▼
编码代理实施
           │
           ▼
本地测试与静态检查
           │
           ▼
创建 PR
           │
           ▼
GitHub CI
           │
           ▼
独立代码审核
           │
           ▼
修复 P1 / 重要 P2
           │
           ▼
最终测试和批准
           │
           ▼
合并 main
           │
           ▼
合并后验证
```

不是所有需求都需要写 ADR。

只有涉及数据库所有权、模块边界、公共 API、事务语义、存储策略或其他长期架构决定的变更，才需要新增或更新 ADR。

普通 UI 文案修复、局部表单验证不需要复杂的架构流程。

# 十、Issue、PR 和审核怎样规范化？

## 10.1 Issue 必须描述行为，而不是简单描述文件

不推荐：

> 修改 catalog.go。

推荐：

> 支持同一商品下创建多个 SKU，并拒绝重复的规格组合。

每个 Issue 至少具备：

| 字段 | 说明 |
|---|---|
| Module | 所属业务模块 |
| Objective | 需要交付的用户能力 |
| Scope | 本次允许修改的范围 |
| Contract Impact | 是否修改 API/Schema |
| Dependency | 依赖哪些 Issue 或 PR |
| Acceptance | 可执行的验收条件 |
| Risk | 安全、交易、迁移或兼容风险 |
| Evidence | 需要提交哪些测试结果 |

例如：

```text
Issue: CAT-012
Module: catalog
Title: Create Product Variant

Acceptance:
- 创建合法 SKU 成功
- 重复 SKU 被拒绝
- 重复规格组合被拒绝
- 跨租户 Product 引用被拒绝
- OpenAPI 契约测试通过
- PostgreSQL 18 集成测试通过
```

这样编码代理知道需要交付什么，而不是只知道应该写哪个文件。

## 10.2 一个功能分支对应一个 PR

建议分支格式：

```text
feat/catalog-variant-create
feat/media-local-upload
feat/admin-product-editor
feat/storefront-product-gallery

fix/release-version-conflict
fix/catalog-duplicate-sku

test/tenant-rls
refactor/media-storage-interface
```

所有功能从受保护的 `main` 创建分支。

不允许开发代理直接向 `main` 提交业务代码。

存在明确依赖的功能可以临时采用 Stacked PR，但优先保持较短的依赖链，避免四个代理形成连续十多个互相等待的 PR。

### PR 的合理大小

建议将以下数值作为审查目标，而不是硬限制：

- 普通逻辑改动尽量控制在数百行量级。
- 大规模生成代码单独标记。
- 数据库迁移单独重点审查。
- 大量 UI 样式变更需要实际预览和截图。
- 超过一个业务领域的 PR 应说明为什么不能拆分。

代码行数不是唯一标准。

一个 200 行的支付状态机变更，风险可能高于 1,000 行普通 UI 代码。

## 十一、建立独立审核机制

你之前的并行开发方式已经包含多个编码代理和独立审查代理。

我建议明确区分三种角色。

| 角色 | 主要责任 |
|---|---|
| Implementer | 编码、单元测试、修复缺陷 |
| Independent Reviewer | 独立检查业务约束、错误和回归 |
| Integrator | 检查跨模块契约、CI、依赖和合并风险 |

同一个代理可以在不同任务中承担不同角色，但**不能把作者自己的一次检查当作独立审核**。

### 11.1 审核优先级

建议：

| 等级 | 定义 | 合并规则 |
|---|---|---|
| P0 | 重大安全、数据完整性或系统性故障 | 必须修复 |
| P1 | 当前功能错误、明显回归或关键业务不变量违反 | 必须修复 |
| P2 | 局部可靠性、维护性或有现实影响的边界问题 | 修复或明确接受并跟踪 |
| P3 | 风格、非关键优化和建议 | 可延期 |

尤其需要防止一个问题：

**不能因为编码代理认为评审意见属于 P2，就直接忽略。**

如果 P2 影响 RLS、订单、媒体完整性、并发发布或支付，应重新按实际后果评估风险。

### 11.2 审核必须检查测试证据

例如审核数据库 PR 时，不能只看到一份 SQL 就批准。

应该要求：

```text
Migration Applied: PASS
Reapply Test: PASS
RLS Isolation: PASS
Foreign Key Test: PASS
sqlc Generate: PASS
Go Compile: PASS
```

这些状态必须来自真实执行记录。

对于你之前遇到的环境限制：

```text
PostgreSQL Not Installed
```

应标记：

`BLOCKED`

不能因为静态检查通过，就自动替换为 `PASS`。

### 11.3 PR 必须提供结构化审核回执

建议 PR 描述采用：

```text
Module:
Change:
Contract:
Database Migration:
Security Impact:
Tests Executed:
Tests Not Run:
Known Risks:
Rollback Strategy:
Reviewer Findings:
```

前端 PR 还需要提供：

- 桌面和移动端截图。
- 关键交互说明。
- API 错误状态。
- 可访问性检查。
- 预览链接或可复现步骤。

后端 PR 则需要提供：

- 业务不变量。
- 并发与事务语义。
- 错误码。
- 数据迁移影响。
- RLS、幂等或资源权限测试。

# 十二、CI 必须重新设计：避免每个 PR 触发几十个 Job

这部分需要结合你之前实际遇到的 GitHub Runner 失败、主干测试故障和浏览器 Flaky Test。

你之前的其他项目曾出现单 PR 约 70 个 CI Job、免费层并发资源受限、反复推送反复评审的问题。

**OpenSite Commerce 不应该复制这种高成本 CI 结构。**

我建议：

> **模块影响分析 + 分层测试 + 一个稳定的 CI 汇总检查 + 一个独立审核状态。**

## 12.1 推荐的 CI 结构

```text
Pull Request
     │
     ▼
Detect Affected Modules
     │
     ├── Contract Validation
     │
     ├── Go Build + Unit Tests
     │
     ├── React Admin Tests
     │
     ├── Astro Storefront Tests
     │
     ├── PostgreSQL 18 Integration
     │
     ├── E2E Smoke Tests
     │
     └── Security Checks
             │
             ▼
        ci-required
             │
             ▼
      Independent Review
             │
             ▼
        Merge Eligible
```

这里的模块检测主要决定哪些测试需要执行，而不是跳过整个必需工作流。

### 为什么？

GitHub 官方说明：如果一个必需工作流因为路径过滤而没有运行，关联的必需检查可能持续 Pending，导致 PR 无法合并。([GitHub Docs](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax))

因此建议：

**必需工作流始终触发，在工作流内部决定受影响的模块和测试。**

不能依赖直接跳过整个 Workflow 来实现 CI 优化。

---

## 12.2 CI Job 数量控制

建议普通 PR 使用约 7–9 个逻辑 Job，而不是几十个。

| Job | 检查内容 | 执行策略 |
|---|---|---|
| impact | 分析受影响模块 | 始终执行 |
| contracts | OpenAPI、JSON Schema、SDK 一致性 | 契约受影响时执行 |
| backend | Go 编译、Vet、单元测试 | 后端受影响时执行 |
| admin | TypeScript、React 测试、构建 | Admin 受影响时执行 |
| storefront | Astro 类型检查、组件测试、构建 | Storefront 受影响时执行 |
| postgres | PG18 迁移、RLS、SQL 与领域集成测试 | DB 或相关后端受影响时执行 |
| e2e | 最小业务闭环、预览与发布 | 关键路径受影响时执行 |
| security | 依赖、密钥、危险权限和配置检查 | 根据变更风险执行 |
| ci-required | 汇总所有必需结果 | 始终执行 |

这里的 Job 数量是建议目标。部分检查可以在一个 Job 内串行运行，以降低 Runner 启动开销。

不建议把每个 Go Package、每个 React Feature、每个浏览器以及每个数据库测试文件都拆成独立 Job。

### 12.3 汇总检查不能假通过

`ci-required` 必须检查：

- 影响分析是否成功。
- 需要执行的检查是否真正运行。
- 是否存在 Failure。
- 是否存在 Cancelled。
- Required Test 是否意外 Skipped。
- 是否存在没有生成的必要测试报告。

例如：

```text
Catalog API Changed
    │
    ▼
Required:
- Backend
- Catalog Contract
- PostgreSQL Integration

Not Required:
- Unrelated Admin Features
```

如果 PostgreSQL Integration 没有运行：

**即使 Backend Unit Test 通过，`ci-required` 仍应失败。**

反之，如果一个纯文档 PR 确实不影响代码，也不需要启动 PostgreSQL 服务。

关键是影响判断必须可审计。

对于无法确认影响范围的变更，应保守执行完整检查，而不是默认跳过。

---

## 12.4 实施模块级 Affected Detection

Module Registry 在这里发挥作用。

例如修改：

```text
apps/admin/src/features/catalog/
```

需要：

```text
Admin Catalog Test
TypeScript Check
Admin Build
```

但通常不需要重新执行完整 PostgreSQL 迁移。

修改：

```text
contracts/openapi/catalog/
```

需要：

```text
Contract Validation
Go Catalog Compile
TypeScript SDK Generation
Admin Catalog Typecheck
Storefront Catalog Typecheck
```

修改：

```text
db/migrations/
```

必须执行：

```text
Migration Validation
PostgreSQL 18 Integration
RLS / Foreign Key Tests
sqlc Generation Check
Related Domain Tests
```

修改：

```text
packages/component-sdk/
```

则必须覆盖：

```text
Component Registry
React Page Builder
Astro Renderer
PageDocument Contract
Draft / Preview / Publish
```

这意味着影响检测必须能够沿模块依赖图寻找下游消费者。

### 不建议只使用简单路径匹配

例如：

```text
changed: catalog/**
run: catalog-test
```

这种判断可能遗漏依赖 Catalog API 的 Storefront 模块。

应当根据：

**变更文件 → 所属模块 → 公共契约 → 下游依赖 → 必要测试集合**

生成测试计划。

CI 汇总 Job 验证测试计划确实得到执行。

# 十三、分层测试体系

建议使用四个测试层级，而不是所有测试都在每次 PR 中完整执行。

## Level 1：本地开发检查

目标是尽早发现简单错误。

包括：

- Go 相关单元测试。
- `go vet`。
- TypeScript 类型检查。
- ESLint。
- 受影响组件测试。
- JSON Schema 校验。
- OpenAPI 检查。
- SQL 静态检查。

这部分应尽量保持快速，作为编码代理提交 PR 前的自检要求。

## Level 2：PR 必需检查

包括：

- 受影响模块的测试。
- 契约兼容测试。
- 必需数据库集成测试。
- 必要的安全检查。
- 最小端到端 Smoke。
- 独立审核状态。

这部分决定 PR 能否合并。

## Level 3：合并后与定期全量测试

包括：

- 所有 Go 模块单元测试。
- 所有 Admin Feature 测试。
- 全部 Storefront 组件测试。
- 所有 PostgreSQL 18 数据库集成测试。
- 完整 E2E。
- 全量 Race Detector。
- 主要浏览器兼容测试。
- 依赖及漏洞扫描。

建议在 `main` 合并后和夜间定期执行。

如果定期检查发现主干回归，需要停止相关依赖 PR 的正常合并，并优先修复主干。

## Level 4：专项质量测试

包括：

- 300,000 SKU 性能测试。
- 10,000 SPU 批量导入。
- 媒体迁移。
- 备份与恢复。
- 发布和回滚故障注入。
- 大量页面组件渲染。
- 安全测试。
- 数据库升级测试。
- 兼容性与负载测试。

这些测试不需要每次普通 PR 都完整运行。

建议在定期任务、重大架构修改以及正式版本发布前执行。

---

## 13.1 前端和后端分别需要哪些测试？

| 测试类型 | Go Backend | React Admin | Astro Storefront |
|---|---|---|---|
| 单元测试 | 领域规则 | Hooks、表单、状态 | View Model、组件逻辑 |
| 契约测试 | OpenAPI、权限 | SDK/响应兼容 | Resolver/数据兼容 |
| 集成测试 | PostgreSQL、LocalFS、River | API 集成 | Astro SSR + Go Read API |
| E2E | 真实业务命令 | 表单操作、草稿编辑 | 商品展示、询盘、购买流程 |
| 安全测试 | RLS、授权、幂等 | XSS、CSRF、Token 处理 | XSS、内容公开权限 |
| 性能测试 | QPS、查询、批量写入 | 大表格、大表单 | SSR、Core Web Vitals |
| 回归测试 | 数据与状态机 | UI 交互 | 视觉、响应式、SEO |

### 13.2 Page Builder 必须额外做预览一致性测试

这是前端最重要的一类专用测试。

同一份 PageDocument：

1. 在后台创建草稿。
2. 使用 Astro 生成预览。
3. 发布 Site Release。
4. 使用 Astro 生成正式页面。
5. 比较关键 DOM、组件数量、文案与资源引用。

允许预览模式存在编辑标记等差异。

但实际内容和布局不能出现没有解释的差异。

还应增加移动端视觉回归和可访问性检查。

### 13.3 商品、库存和价格必须进行业务不变量测试

例如：

**Catalog**

- 不能重复 SKU。
- 不能重复规格组合。
- 不能引用其他租户商品。
- 不能发布无效商品数据。

**Pricing**

- 数量阶梯不应出现无定义的优先级冲突。
- 客户专属价格不得跨客户泄漏。
- 货币金额不得使用不受控的浮点计算。

**Inventory**

- 并发预留不超卖。
- 取消订单正确释放库存。
- 重试不重复扣减。

**Order**

- 成交价格快照不可被商品更新覆盖。
- 支付 Webhook 重复通知不重复成交。
- 不合法状态转换必须被拒绝。

这些测试必须由后端承担，不能由前端测试代替。

# 十四、专门处理 CI Flaky、Runner 失败和主干测试故障

你之前遇到的问题不只是 CI 执行慢，还包括不同失败类型混杂。

建议在测试治理中至少区分：

| 失败类别 | 示例 | 处理方式 |
|---|---|---|
| Infrastructure | Runner 无法启动、依赖拉取失败 | 记录环境错误并安全重试 |
| Mainline Regression | 主干已有测试故障 | 先验证基线，优先修复主干 |
| PR Regression | 本次改动引起的错误 | 当前 PR 修复 |
| Flaky | WebKit 偶发导航超时 | 收集证据、定位和隔离 |
| Contract Failure | API、SDK、Schema 不兼容 | 修改契约或实现 |
| Security Failure | RLS、权限或秘密泄漏 | 阻止合并 |

**不能把 Infrastructure Failure 当作测试 PASS。**

如果 CI 所需的 PostgreSQL 18 Runner 无法启动，CI 应保持失败或未完成状态，直到成功重新执行。

### 14.1 Flaky Test 策略

不建议无限自动重试，直到测试偶然成功。

应记录：

- 测试名称。
- 失败次数。
- Runner 环境。
- 浏览器版本。
- 失败日志。
- 可重复性。
- 对应 Issue。

对于已确认的非关键 Flaky 测试，可以在有责任人和到期处理时间的情况下暂时隔离到专项工作流。

但不能将 RLS、支付、库存、发布原子性等关键测试简单降级为不影响合并。

### 14.2 时间相关测试

所有业务代码中依赖当前时间的逻辑，建议通过明确的 Clock 接口注入。

例如：

```text
Clock.Now()
```

测试中使用固定时间。

不要把真实系统时间直接散落在价格有效期、订单超时、发布任务等代码中。

这能够减少主干上因日期变化导致所有 PR 同时失败的问题。

# 十五、GitHub 分支保护与合并策略

建议 `main` 使用受保护分支或 Ruleset。

### 必需条件

| 检查 | 是否必须 |
|---|---|
| `ci-required` | 必须 |
| `independent-review` | 必须配置独立审查来源后启用 |
| 未解决 P0/P1 | 不允许合并 |
| 必需的数据库迁移测试 | 根据改动范围必须通过 |
| API 兼容测试 | 契约变更时必须通过 |
| 分支与 main 的兼容性 | 必须 |
| 必需审核意见 | 按团队和风险策略设置 |

GitHub 支持通过 CODEOWNERS 将文件关联到责任人或团队，并可结合分支保护要求相应审核。([GitHub CODEOWNERS 文档](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners))

但你目前以独立开发者和编码代理为主，需要特别注意：

**不能配置一个实际没有独立审核人能够满足的 GitHub 人工审批规则。**

建议让 AI 独立审查服务提供明确的机器检查状态，再由你控制高风险变更是否合并。

这和伪造一个 GitHub 人类审核批准完全不同。

## 15.1 是否需要 Merge Queue？

可以考虑，但不应该作为项目启动的前置条件。

GitHub Merge Queue 能够对合并组重新执行必需检查，避免多个 PR 分别通过测试，合并到一起后却破坏主干。

如果启用，GitHub Actions 必须处理 `merge_group` 事件，否则队列的必需检查可能无法完成。([GitHub Docs](https://docs.github.com/zh/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue))

还应检查仓库类型和 GitHub 套餐是否满足 Merge Queue 的使用条件。

如果当前仓库不具备该功能，就采用受控的顺序合并、最新主干验证和合并后检查，不需要为了 Merge Queue 升级整个项目架构。

## 15.2 控制 CI 并发与重复执行

建议：

- 按 PR 编号设置工作流并发组。
- 同一个 PR 新提交可以取消已经过时的旧 CI。
- 不同 PR 不应互相取消。
- 发布和数据库迁移任务使用独立并发组。
- 限制测试矩阵最大并发。
- 避免多个工作流重复执行相同的大型测试。

GitHub Actions 官方支持 Workflow/Job 级并发组和取消旧执行的策略。([GitHub Workflow Syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax))

考虑到你还有其他项目占用 GitHub Runner，我建议初期将普通 PR 的并行 Job 控制在约 **4–6 个**，再根据真实队列等待时间和执行成本调整。

这不是平台硬性限制，而是适合当前开发规模的初始资源预算。

# 十六、开发顺序：按照模块依赖安排，而不是同时启动所有模块

我建议分为五个工程阶段。

- 认证与 API Key。
- 站点创建。
- OpenAPI 契约生成。
- 最小 CI 门禁。

```text
   ↓
Quotation
   ↓
Purchase Order
```

**B2C：**

```text
Catalog + Pricing
        ↓
Inventory
        ↓
Cart
        ↓
Checkout
        ↓
Payment / Order
        ↓
Fulfillment
```

这里应当将支付抽象、库存预留、订单状态机和实际收款渠道作为独立审查重点。

第三方支付尽量采用支付服务提供商的合规收款方式，不让平台直接处理原始银行卡敏感数据。

## Phase 4：Agent 和行业规模化

在业务 API 稳定后扩展：

- Agent 批量商品导入。
- Agent 商品资料补全。
- Agent 企业官网配置。
- SiteSpec。
- Site Plan。
- Industry Package。
- 主题与组件生态。
- ERP 集成。
- 多站点运营。
- 商品及网站分析。

Agent 的基础只读和草稿操作可以从更早阶段接入，但完整自动建站应建立在已经验证的领域 API 上。

# 十七、适合多个编码代理的并行开发方式

结合你的工作方式，我建议最多同时保留四条主要实施线，避免所有代理同时修改核心文件。

| 开发线程 | 主要范围 | 不允许自行修改 |
|---|---|---|
| Thread A | PostgreSQL、Identity、Tenant、基础事务 | 其他模块业务逻辑 |
| Thread B | Catalog、Media、Company 的 Go 模块 | 公共发布协议 |
| Thread C | React Admin 与各 Feature | 数据库 Schema 和后端业务规则 |
| Thread D | Astro Storefront、组件、Render Context | 认证/RLS 实现 |

同时设置：

**独立审核线程：** 审查实际 Diff、失败用例、P0/P1/P2、模块边界和测试证据。

**集成负责人：** 维护公共契约、合并顺序和跨模块依赖。

实际分工可以随着阶段变化，不必固定由某个模型永久开发前端或后端。

### 并行开发需要遵循三个规则

**1. 公共契约先确定。**

例如 Catalog API 和商品 View Model 先确定，再让 Go、React、Astro 并行开发。

**2. 尽量避免多人同时修改同一文件。**

尤其是：

```text
sqlc.yaml
go.mod
openapi.yaml
Component Registry
Root Router
CI Workflow
```

这些公共文件应该有明确的变更责任人。

**3. 新模块通过公开入口集成。**

例如 Admin 的 Catalog Feature 不能直接引用 Media Feature 的内部 Hook。

需要共用媒体选择器时，由 Media 模块显式导出稳定接口。

# 十八、建议建立模块级 Definition of Done

不要仅仅因为 PR CI 显示绿色，就认为模块已经完成。

每个模块都需要一个完成标准。

例如 **Catalog V1**：

| 验收 | 要求 |
|---|---|
| Database | 产品、SKU、属性约束经过实库测试 |
| Go Domain | 商品创建、修改、归档规则正确 |
| OpenAPI | 完整契约、错误码、权限定义 |
| React Admin | 商品列表、编辑、SKU 管理可用 |
| Astro Storefront | 商品列表和详情能真实展示 |
| Media | 商品能够绑定已验证的图片 |
| Agent/API | 可以通过 API 创建商品草稿 |
| Tenant Isolation | 跨租户访问被拒绝 |
| Tests | 单元、契约、数据库集成和 E2E 通过 |
| Documentation | 模块接口与行为有开发说明 |

**一个模块可以分多次 PR 完成，但必须达到上述验收条件才能宣布该模块 V1 完成。**

对于没有 Storefront UI 的模块，例如 Audit，也不需要强行创建空的 Astro 组件。模块清单中可以明确写 `not applicable`。

# 十九、正式版本发布与开源维护

建议使用三个版本维度。

| 版本 | 管理对象 |
|---|---|
| Platform Version | 整套 OpenSite Commerce 软件版本 |
| Contract Version | OpenAPI、Component Schema 等接口版本 |
| Site Release | 某个用户网站的内容与布局发布版本 |

三个概念不能混为一谈。

例如：

```text
Platform: 0.8.0
Component: catalog.product-grid@1
Site Release: 27
```

表示平台运行 0.8.0，使用商品网格组件契约 V1，某个网站当前处于第 27 次发布。

### 发布流程

建议：

```text
main
 │
 ▼
Full Integration Tests
 │
 ▼
Security / Dependency Check
 │
 ▼
Database Upgrade Test
 │
 ▼
Backup / Restore Check
 │
 ▼
Build Containers
 │
 ▼
Release Candidate
 │
 ▼
Version Tag
 │
 ▼
Published Release
```

数据库迁移采用 forward-only。

软件版本回滚必须考虑数据库结构是否仍兼容旧程序，不能单纯恢复旧 Docker Image 就认为完成回滚。

对于数据库破坏性变更，采用先扩展、迁移数据、切换读写、最后清理旧结构的方式。

同时持续测试：

- 旧页面组件能否渲染。
- 旧主题能否迁移。
- 媒体引用是否有效。
- 用户网站数据是否保持完整。
- 数据库升级是否可恢复。

# 二十一、我建议立即调整的五项工程决策

最终收敛成以下五项。

### 决策 1：前后端完全按照业务模块组织

后端使用：

`apps/api/internal/modules/{module}`

管理后台使用：

`apps/admin/src/features/{module}`

店铺前端使用：

`apps/storefront/src/modules/{module}`

三者通过共享契约协作，不直接依赖彼此内部实现。

### 决策 2：引入 Module Registry，但不增加新的运行服务

Module Registry 只用于：

- 模块所有权。
- 依赖分析。
- CODEOWNERS 映射。
- CI 影响范围。
- 模块测试入口。

保持声明式和轻量化。

### 决策 3：采用 Contract First + 纵向功能 PR

每次改变公共接口，先确定契约。

单模块功能可以在一个 PR 内同时修改 Go、React、Astro 和对应测试。

不要为了形式上的前后端分工制造大量无法独立验收的 PR。

### 决策 4：CI 保留一个汇总门禁与独立审核

目标结构：

```text
Affected Tests
      │
      ▼
ci-required
      │
      ▼
independent-review
      │
      ▼
Merge
```

不要让 70 个独立 Job 全部成为必需状态检查。

但要确保汇总门禁确实覆盖所有受影响的必需测试，而不是简单忽略 Skipped 或基础设施失败。

### 决策 5：先完成 PR-01，再启动正式的纵向业务集成

目前最关键的阻塞仍然是：

**PostgreSQL 18 实库迁移、RLS、`sqlc generate` 和 `pgx` 实际编译尚未验收完成。**

建议下一个工程周期按照以下顺序安排：

| 顺序 | 工作 | 交付 |
|---|---|---|
| 1 | PR-01 实库验收 | PostgreSQL 18 + sqlc + pgx 真正通过 |
| 2 | 模块目录和边界规则 | Go、React、Astro 模块骨架 |
| 3 | Module Registry + Affected CI | 按模块选择测试，稳定汇总门禁 |
| 4 | Catalog/Media/Company 契约 | 可供前后端并行实施 |
| 5 | 第一个纵向功能 PR | 从商品创建到 Astro 实际展示 |

这五项完成后，就可以比较稳定地推进各个业务模块，而不需要每次新开发一个功能都重新调整全局架构。

## 最终审查结论

我对 OpenSite Commerce 当前架构的判断是：

**技术方向合理，业务模型基本成立，但工程治理和跨模块边界还没有完全固定。**

需要保留的部分是：

Go 模块化单体、PostgreSQL 18、pgx/sqlc、React Admin、Astro SSR、Bun 工具链、免费 LocalFS、统一 OpenAPI、组件化建站和 Agent 领域操作。

最需要完善的是：

**前后端业务模块化、模块所有权、公共契约管理、真实数据库验收、PR 独立审核和按影响范围执行的 CI。**

此外，还应该坚持一条项目原则：

> **每个模块必须具备独立开发、独立测试、独立审核的能力；但整个产品必须通过跨模块契约和端到端测试，证明这些模块能够共同完成真实的经营流程。**

本次审查基于 V0.1–V0.7 的架构设计及此前 PR-01 验收记录，并非对现有仓库所有源码的逐行审计。上述目录、模块注册表和 CI 方案是建议的目标结构，尚未在仓库中实施或验证。

**我建议将这份方案作为 V0.8 架构基线。接下来的实施重点不是新增功能，而是先建立前后端模块骨架、Module Registry、契约所有权和模块感知的 CI，再依赖真实通过的数据库基础逐步开发业务功能。**
