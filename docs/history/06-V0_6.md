# OpenSite Commerce V0.6
## 从架构设计进入可执行工程规格

**版本：V0.6 — Minimum Executable Architecture**  
**日期：2026 年 10 月 11 日**  
**设计基线：Go + PostgreSQL 18 + Astro + React + Bun + LocalFS**  
**本轮目标：ARCH-018、ARCH-019、ARCH-020**

经过 V0.1～V0.5，项目已经形成了完整的总体方向。但 V0.5 还有一个关键问题：虽然给出了数据库 SQL、API 示例和组件协议，它们尚未构成能够独立部署、实际运行并通过端到端测试的系统。

**V0.6 的核心任务是把第一条业务链真正闭合，而不是继续增加新的架构模块。**

本轮围绕三个交付规格展开：

| 规格 | 目标 | 验收方式 |
|---|---|---|
| ARCH-018 | 完成最小业务数据库迁移设计 | 空库迁移、约束、RLS 和恢复测试 |
| ARCH-019 | 冻结首批 API 契约 | OpenAPI 校验、SDK、契约测试 |
| ARCH-020 | 定义第一个完整网站的验收样例 | 企业、商品、媒体、页面、发布全链路测试 |

这里将区分**已经明确的工程设计**和**尚未通过执行验证的实现**。目前没有创建仓库、执行 SQL、部署服务或运行端到端测试，因此不会把设计规格标为已实现。

# 一、V0.6 首先修复 V0.5 的六个问题

## 1. 页面内容版本与 URL 路由错误耦合

V0.5 的 `page_revisions` 同时包含：

```text
page_id
revision
locale
path
document
```

这会使页面内容版本与 URL 路由紧密绑定。

例如，企业修改 `/about` 为 `/company`，可能被迫同时改变页面内容版本，即使页面本身没有修改。

**V0.6 修正：**

```text
Page
 └── Page Revision
       └── PageDocument

Site Release
 └── Route Binding
       ├── locale
       ├── path
       └── page_revision
```

页面版本只描述页面内容。

路由属于发布配置。

这使 URL 变更、重定向和页面回滚更容易独立管理。

## 2. V0.5 缺少真正的 Draft 数据模型

之前已经定义了页面草稿 API，但没有完整定义：

- 草稿保存在哪里。
- 多页面草稿如何组织。
- 两个管理员如何处理版本冲突。
- 草稿如何转换成不可变的 Page Revision。
- 发布失败后草稿如何保留。

V0.6 必须补齐 `site_drafts`、`draft_pages` 和操作记录。

否则 React 编辑器和 Agent 无法可靠协作。

## 3. 商品状态存在重复语义

此前同时存在：

```text
products.status = active
product_listings.status = active
```

如果缺少明确的状态含义，未来可能出现商品主状态为 Active，但所有站点 Listing 均未上架的情况，开发者很难判断这是否属于异常。

V0.6 统一为：

**Product Lifecycle：** 商品存在、编辑或归档状态。

**Listing Publication：** 商品在特定网站或渠道的公开状态。

商品不需要依赖某个网站才能存在。

一个商品可以在 A 网站上架，在 B 网站保持草稿。

## 4. 不能只有 RLS，没有真正的身份和权限模型

V0.5 提供了 RLS 示例，却没有完整的用户、会话和 API Key 结构。

这存在实施风险。

V0.6 第一批迁移必须包含：

- User。
- Tenant Membership。
- Session。
- API Key。
- Scope。
- Audit。
- Idempotency。

管理后台使用短期或可撤销会话，Agent 使用有限权限的 API 凭证。

**不能允许用户自己在请求中指定 `tenant_id`，再由系统直接信任这个值。**

PostgreSQL 官方明确说明，RLS 有默认拒绝机制，但超级用户、`BYPASSRLS` 角色和某些表所有者能够绕过通常的行级策略。因此必须结合数据库角色和 API 授权设计。

## 5. Site Release 不能只记录 Renderer Build ID

旧版本能否恢复，不仅取决于数据库是否存在历史记录。

还取决于当前应用是否仍然包含旧组件的渲染实现。

V0.6 决定在 Release 中记录：

```text
renderer_build_id
component_contracts
theme_version
schema_version
manifest_hash
```

发布和回滚时执行兼容性检查。

第一版不必在服务器上永久保留所有历史运行时，但必须明确：**无法被当前 Renderer 正确渲染的历史版本不能直接恢复。**

## 6. 第一个验收样例不能缺少企业官网与博客

此前为了缩小数据库范围，容易将企业展示、博客和联系功能推迟。

但你的项目并不是单纯的商品管理系统。

它还需要支持：

- 企业官网。
- 企业地址、邮箱及社交媒体。
- 企业图片。
- 博客文章。
- B2B 询盘。
- 商品介绍和规格。
- 模板化页面展示。

因此，V0.6 的最小闭环必须包含这些基础能力。

可以暂缓在线支付、物流和完整订单系统，但不能只交付一个商品列表页。

# 三、ARCH-018：数据库迁移 V1

## 3.1 采用 11 个前向迁移

数据库不再以“需要哪些功能就随时增加一张表”的方式设计。

V0.6 首先冻结以下迁移顺序。

| 迁移 | 主要数据表 | 负责范围 |
|---|---|---|
| 001_identity | `users`、`auth_sessions`、`api_keys` | 身份及凭证 |
| 002_organization | `tenants`、`tenant_memberships`、`organizations` | 租户、企业及权限 |
| 003_site | `sites`、`site_domains`、`site_locales` | 网站及域名 |
| 004_catalog | `products`、`product_variants`、`product_options`、`product_option_values`、`variant_option_values`、`attribute_definitions`、`product_attribute_values`、`product_content_revisions`、`product_listings` | 商品与属性 |
| 005_media | `media_uploads`、`media_blobs`、`media_assets`、`media_usages`、`product_media` | 文件与媒体 |
| 006_content | `company_profile_revisions`、`company_contacts`、`pages`、`page_revisions`、`blog_posts`、`blog_post_revisions` | 企业内容、页面、博客 |
| 007_release | `site_releases`、`site_release_routes`、`site_release_templates` | 网站正式发布 |
| 008_draft | `site_drafts`、`draft_pages`、`draft_operations` | 草稿与编辑 |
| 009_inquiry | `inquiries`、`inquiry_events` | B2B 询盘 |
| 010_reliability | `idempotency_records`、`audit_events`、`outbox_events` | 幂等、审计、事件 |
| 011_security_indexes | RLS、角色权限、复合索引 | 数据保护及性能 |

这是逻辑迁移顺序。创建外键时仍须按依赖排序，部分循环引用需要先创建表，再执行 `ALTER TABLE ... ADD CONSTRAINT`。

**全部迁移采用 forward-only。**

已经在正式环境执行的迁移不能偷偷修改其 SQL 内容。后续变更必须通过新迁移完成，并配备数据升级和恢复方案。

PostgreSQL 18 原生支持 `uuidv7()`，第一版统一使用 UUIDv7 作为主要资源标识。

## 3.2 首批关键表的字段契约

### 身份与权限

| 表 | 主要字段 | 不变量 |
|---|---|---|
| `users` | id、email、password_hash、status | 邮箱经过规范化，唯一 |
| `auth_sessions` | id、user_id、token_hash、expires_at、revoked_at | 只保存会话令牌摘要 |
| `api_keys` | id、tenant_id、key_prefix、key_hash、scopes、expires_at、revoked_at | 不存储明文 API Key |
| `tenants` | id、name、status | 租户身份稳定 |
| `tenant_memberships` | tenant_id、user_id、role、status | 用户只有经授权才能访问租户 |
| `organizations` | tenant_id、id、legal_name、display_name | 企业资料属于指定租户 |

V0.6 采用简单角色模型：

`owner`、`admin`、`catalog_editor`、`content_editor`、`viewer`。

但实际授权以操作权限为准，例如：

```text
catalog.read
catalog.write
media.write
site.read
site.draft.write
site.publish
company.write
inquiry.read
```

角色映射到权限集合。

Agent 和第三方 API Key 还要受自身 Scope 限制。

**最终授权取用户角色、API Key Scope 和资源归属等约束的交集，不能因为获得一个 API Key 就扩大原有权限。**

管理后台建议使用安全 Cookie 会话并实施 CSRF 防护；API Key 使用 Bearer 方式，不暴露到浏览器前端代码。OWASP 明确指出，SameSite Cookie 是纵深防御措施，不能在一般情况下代替完整的 CSRF 防护。

### 商品及属性

这一部分必须比 V0.5 更完整，否则服装的颜色、尺码和大规模 SKU 导入仍然无法实施。

```text
Product
  │
  ├── ProductOption
  │     └── ProductOptionValue
  │
  ├── ProductVariant
  │     └── VariantOptionValue
  │
  ├── ProductAttributeValue
  │
  ├── ProductContentRevision
  │
  └── ProductListing
```

其中：

| 实体 | 必须满足的约束 |
|---|---|
| Product | 同租户 Product Code 唯一 |
| Variant | 同租户 SKU 唯一 |
| VariantOptionValue | 必须属于当前商品有效的 Option |
| Option Combination | 同一商品内不可重复 |
| Attribute Definition | 属性类型、作用范围及校验规则明确 |
| Product Attribute | 值必须符合对应 Attribute Schema |
| Content Revision | 不可原地修改已创建版本 |
| Product Listing | 指向当前站点允许公开的商品版本 |

**第一版明确限制：普通商品属性模板不允许通过 API 执行 DDL。**

商家新增“面料”“香型”“容量”等属性时，创建属性定义和数据，不修改数据库表结构。

高频筛选字段可以建立受控的类型化索引。

### 企业公开资料

企业资料要区分内部法律主体和公开展示内容。

建议：

```text
Organization
    │
    ├── Internal Legal Data
    │
    ├── Company Contacts
    │
    ├── Private Documents
    │
    └── Company Profile Revisions
```

公司名称、介绍、地址、邮箱、电话、WhatsApp、社交媒体链接等均应使用正式字段或经过验证的结构化配置。

对于社交媒体，建议采用：

```json
{
  "platform": "instagram",
  "url": "https://www.instagram.com/example",
  "visibility": "public"
}
```

平台类型使用注册的枚举或扩展规则。

不能接受任意 `javascript:` 等危险 URL Scheme。

营业执照和私有企业资料默认不公开。若需要前台展示，应经过明确授权，并引用经过处理的公开版本。

## 3.3 修正 Page Revision 的 SQL 结构

以下是本轮最重要的数据库结构修正。

```sql
CREATE TABLE app.pages (
    tenant_id UUID NOT NULL,
    site_id UUID NOT NULL,
    id UUID NOT NULL DEFAULT uuidv7(),
    page_key TEXT NOT NULL,

    PRIMARY KEY (
        tenant_id,
        site_id,
        id
    ),

    UNIQUE (
        tenant_id,
        site_id,
        page_key
    ),

    FOREIGN KEY (tenant_id, site_id)
        REFERENCES app.sites(tenant_id, id)
);

CREATE TABLE app.page_revisions (
    tenant_id UUID NOT NULL,
    site_id UUID NOT NULL,
    page_id UUID NOT NULL,

    locale TEXT NOT NULL,
    revision BIGINT NOT NULL,

    document JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    PRIMARY KEY (
        tenant_id,
        site_id,
        page_id,
        locale,
        revision
    ),

    FOREIGN KEY (
        tenant_id,
        site_id,
        page_id
    )
        REFERENCES app.pages(
            tenant_id,
            site_id,
            id
        ),

    CHECK (revision > 0),
    CHECK (jsonb_typeof(document) = 'object')
);
```

注意这里已经取消 `path`。

路由将在发布表中管理。

这样同一个页面拥有稳定的 `page_id`，不同语言可以独立维护内容版本。

例如：

```text
Page: company-about

  zh-CN:
    Revision 1
    Revision 2

  en:
    Revision 1
    Revision 2
    Revision 3
```

不同语言版本可以拥有不同的 URL。

例如：

```text
/about
/zh-CN/company
```

但它们属于同一个逻辑页面。

**这比将语言、路由和页面版本全部绑定到一行记录更适合国际化独立站。**

完整迁移还应通过数据库权限及服务端操作限制，保证已提交的 Page Revision 不被普通运行角色更新或删除。

## 3.4 Site Release 的完整关系

```text
Site
 │
 └── published_release_id
             │
             ▼
        SiteRelease
             │
             ├── Renderer Build
             ├── Theme Version
             ├── Manifest Hash
             │
             ├── SiteReleaseRoutes
             │      └── PageRevision
             │
             └── SiteReleaseTemplates
                    ├── Product Detail
                    ├── Blog Article
                    └── Other Template Types
```

静态页面路径由 `site_release_routes` 管理。

商品详情和博客文章采用保留的动态路径：

```text
/products/{slug}
/blog/{slug}
```

对应的展示模板由 `site_release_templates` 选择。

这样发布一次商品详情模板，不需要向 Site Release 中插入 10,000 条商品路由。

### 关键 SQL

```sql
CREATE TABLE app.site_releases (
    tenant_id UUID NOT NULL,
    site_id UUID NOT NULL,
    id UUID NOT NULL DEFAULT uuidv7(),

    release_no BIGINT NOT NULL,
    renderer_build_id TEXT NOT NULL,

    manifest JSONB NOT NULL,
    manifest_hash BYTEA NOT NULL,

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    PRIMARY KEY (
        tenant_id,
        site_id,
        id
    ),

    UNIQUE (
        tenant_id,
        site_id,
        release_no
    ),

    FOREIGN KEY (tenant_id, site_id)
        REFERENCES app.sites(tenant_id, id),

    CHECK (release_no > 0),
    CHECK (octet_length(manifest_hash) = 32)
);

CREATE TABLE app.site_release_routes (
    tenant_id UUID NOT NULL,
    site_id UUID NOT NULL,
    release_id UUID NOT NULL,

    locale TEXT NOT NULL,
    path TEXT NOT NULL,

    page_id UUID NOT NULL,
    page_revision BIGINT NOT NULL,

    PRIMARY KEY (
        tenant_id,
        site_id,
        release_id,
        locale,
        path
    ),

    FOREIGN KEY (
        tenant_id,
        site_id,
        release_id
    )
        REFERENCES app.site_releases(
            tenant_id,
            site_id,
            id
        ),

    FOREIGN KEY (
        tenant_id,
        site_id,
        page_id,
        locale,
        page_revision
    )
        REFERENCES app.page_revisions(
            tenant_id,
            site_id,
            page_id,
            locale,
            revision
        ),

    CHECK (left(path, 1) = '/')
);
```

这里同时保证：

1. Release 必须属于当前站点。
2. 页面版本必须属于当前站点。
3. 一个 Release 内的同语言路径不能重复。
4. 路由可以在不同 Release 中改变。
5. 页面版本和 URL 可以独立演进。

`site_release_templates` 使用同样的复合外键方式绑定商品或博客模板，增加唯一约束以避免同一站点、语言和模板类型存在多个冲突的默认模板。

这些 SQL 片段是待执行的迁移设计，尚未经过 PostgreSQL 实例测试。

## 3.5 草稿数据模型

V0.6 新增：

```text
SiteDraft
    │
    ├── Base Release
    ├── Current Revision
    ├── Draft Pages
    ├── Draft Theme Settings
    └── Operation History
```

主要结构：

| 表 | 重要字段 | 作用 |
|---|---|---|
| `site_drafts` | tenant_id、site_id、id、base_release_id、revision、status | 整个站点的修改草稿 |
| `draft_pages` | draft_id、page_id、locale、path、document | 页面工作副本 |
| `draft_operations` | draft_id、operation_id、actor_id、before_revision、after_revision、payload | 修改审计与重试 |

这里采用一个明确的策略：

**Draft 可以修改，Revision 不可修改。**

用户在编辑器中修改的是 `draft_pages`。

正式发布时，系统创建不可变的 `page_revisions`，并将它们纳入 Site Release。

例如：

```text
Current Release 12
         │
         ▼
Site Draft A
 revision = 1
         │
         ▼
修改首页
 revision = 2
         │
         ▼
修改 Footer
 revision = 3
         │
         ▼
发布
         │
         ▼
New Release 13
```

后续可以允许多个 Draft 同时存在，但第一版使用乐观并发控制，不引入实时协同编辑。

## 3.6 博客与企业页面的发布边界

博客不是普通页面 JSON 中的一段文本。

建议单独保存：

```text
blog_posts
blog_post_revisions
```

博客身份包含：

```text
site_id
post_id
slug
status
published_revision
```

博客内容版本包含：

```text
locale
title
excerpt
body
cover_media_id
seo_metadata
created_at
```

正式发布的博客内容使用对应版本指针。

商品内容同理。

但要保持三个不同的发布概念：

| 对象 | 版本控制 |
|---|---|
| 网站布局、导航、主题 | Site Release |
| 商品标题、描述、博客文章 | Content Revision |
| 库存、支付、订单 | 实时业务事务 |

V0.6 的默认策略是：独立发布的博客或商品内容，通过各自的发布指针生效。

如果一次站点发布计划还包含博客发布，就在同一个受控发布事务中提交相关版本指针，并记录发布关联。

恢复旧站点布局时，不会自动修改当前库存，也不会无提示地撤销所有后续独立发布的博客内容。

## 3.7 免费媒体存储：补齐上传会话

V0.5 已经定义：

```text
media_blobs
media_assets
```

但还必须增加：

```text
media_uploads
```

建议上传会话包含：

```text
upload_id
tenant_id
actor_id
original_filename
declared_mime
expected_size
expected_sha256
received_bytes
temporary_storage_key
status
expires_at
created_at
```

上传流程：

```text
RESERVED
    ↓
UPLOADING
    ↓
VERIFYING
    ↓
STORED
    ↓
PROCESSING
    ↓
READY
```

失败进入 `FAILED`，过期上传进入清理流程。

### 文件与数据库不能共用一个事务

因此采用：

**安全临时写入 + 文件完整性校验 + 数据库状态转换 + 幂等恢复任务。**

例如发生以下情况：

| 故障位置 | 恢复方法 |
|---|---|
| 上传一半断线 | 上传会话超时并清理暂存文件 |
| 文件已经写入但数据库提交失败 | 清理没有有效引用的暂存对象 |
| 数据库中有 Blob，但实际文件缺失 | 标记故障，不允许 READY |
| 缩略图生成失败 | 保留原图，重试派生资源处理 |
| 文件删除任务执行一半 | 根据状态和对象存在性安全重试 |

图片和视频都使用该媒体模型。

首版视频支持上传、元数据与网页引用，但不强制在单机服务器上进行大量视频转码。

这符合你要求的低成本和大商品数量场景。

## 3.8 数据库中的幂等和审计

V0.6 必须将幂等持久化，而不能依赖进程内 Map。

建议：

```text
idempotency_records
├── tenant_id
├── actor_id
├── operation
├── idempotency_key
├── request_hash
├── status
├── response_status
├── response_body
└── expires_at
```

唯一性约束：

```sql
UNIQUE (
    tenant_id,
    actor_id,
    operation,
    idempotency_key
)
```

相同的幂等键和相同请求内容，返回已有操作结果。

相同幂等键但请求内容发生变化，返回冲突。

对于异步任务，幂等记录保存 Job ID，重复请求返回同一个任务引用。

这对 Agent 批量上架尤其重要。

另外，审计事件应记录：

```text
actor
tenant
resource
operation
before_revision
after_revision
request_id
timestamp
result
```

敏感密钥、原始密码和完整私有证照不应被写入审计日志。

## 3.9 RLS 及公开站点读取

这里需要解决一个此前一直没有完全说清楚的问题：

**普通访客没有登录，系统如何确定他能看到哪个租户的数据？**

答案不能是让访问者提交 `tenant_id`。

正确流程：

```text
访客请求
    │
    ▼
Caddy
    │
    ▼
可信 Host 解析
    │
    ▼
Verified Domain Registry
    │
    ▼
确定 Tenant + Site
    │
    ▼
读取 Published Release
    │
    ▼
Public Read Service
    │
    ▼
只返回公开且已发布的数据
```

域名解析使用一条受限的、只读的内部查询路径。

解析成功后，由服务端建立租户上下文。

管理 API 和公开读取 API 使用不同的权限规则。

公开读取服务不能借助自己的服务身份查询客户私有价格、企业私有文件或其他租户数据。

所有租户业务表执行：

```sql
ALTER TABLE ... ENABLE ROW LEVEL SECURITY;
ALTER TABLE ... FORCE ROW LEVEL SECURITY;
```

并根据不同数据库角色和操作类型设置策略。

运行时数据库角色不能拥有 `BYPASSRLS`、DDL 或 `TRUNCATE` 权限。

PostgreSQL 的 `set_config(..., true)` 只在当前事务内生效，适合避免连接池请求之间遗留租户上下文。

**V0.6 安全验收必须包括：匿名访问、管理用户访问、Agent API Key 访问和跨租户复合外键测试。**

# 五、API 请求、响应和错误协议

## 5.1 统一资源创建响应

例如创建网站：

```http
POST /api/v1/sites
Content-Type: application/json
Authorization: Bearer <token>
Idempotency-Key: <unique-key>
```

请求：

```json
{
  "organization_id": "f11d7e64-7d1b-4000-8000-000000000001",
  "name": "Demo Aroma",
  "default_locale": "en"
}
```

响应：

```http
201 Created
```

```json
{
  "id": "0199f072-6372-7000-8000-000000000002",
  "name": "Demo Aroma",
  "status": "draft",
  "published_release_id": null
}
```

示例 UUID 仅用于说明字段格式。

### API 标准化要求

**资源 ID：** UUID。

**时间：** ISO 8601 / RFC 3339。

**金额：** 十进制字符串，不使用浮点数表示精确货币金额。

**分页：** Cursor Pagination。

**更新：** PATCH 或明确的领域命令。

**异步任务：** 返回 Job ID 和状态查询地址。

**时间与排序：** 不依赖客户端系统时钟决定业务操作顺序。

---

## 5.2 组件修改请求

用户或 Agent 希望在首页增加一个商品网格。

```http
POST /api/v1/sites/{site_id}/drafts/{draft_id}/operations
If-Match: "draft-7"
Idempotency-Key: <unique-key>
```

请求：

```json
{
  "operations": [
    {
      "operation_id": "0199f072-6372-7000-8000-000000000010",
      "type": "component.add",
      "target": {
        "page_key": "home"
      },
      "arguments": {
        "component": "catalog.product-grid@1",
        "node_id": "featured-products",
        "parent_node_id": "root",
        "slot": "main",
        "position": {
          "after_node_id": "hero"
        },
        "props": {
          "columns_desktop": 4,
          "columns_mobile": 2,
          "show_price": false
        },
        "binding": {
          "resolver": "catalog.featured-products@1",
          "params": {
            "limit": 8
          }
        }
      }
    }
  ]
}
```

`catalog.featured-products@1` 是建议注册的 Resolver。它必须由后端明确实现，不是任意 API 地址。

服务端需要检查：

1. 当前用户能否编辑这个 Site。
2. Draft 是否仍然有效。
3. `If-Match` 是否符合当前版本。
4. 组件是否已注册。
5. 组件是否允许放在当前 Slot。
6. Props 是否通过 JSON Schema。
7. Resolver 是否存在并且具有授权范围。
8. 组件数据是否满足节点数量和查询预算。

成功响应：

```http
200 OK
ETag: "draft-8"
```

```json
{
  "draft_id": "0199f072-6372-7000-8000-000000000011",
  "revision": 8,
  "applied_operations": [
    "0199f072-6372-7000-8000-000000000010"
  ],
  "status": "saved"
}
```

React 编辑器和 Agent 使用完全相同的操作契约。

---

## 5.3 每一种组件命令必须有独立 Schema

此前使用：

```yaml
arguments:
  type: object
```

过于宽泛。

V0.6 不应长期保留这种不受约束的定义。

建议在 OpenAPI 中：

```yaml
PageOperation:
  oneOf:
    - $ref: "#/components/schemas/ComponentAdd"
    - $ref: "#/components/schemas/ComponentMove"
    - $ref: "#/components/schemas/ComponentSetProps"
    - $ref: "#/components/schemas/ComponentSetBinding"
    - $ref: "#/components/schemas/ComponentRemove"
  discriminator:
    propertyName: type
```

每一种操作都定义：

- 固定的 `type`。
- Target Schema。
- Arguments Schema。
- 必需字段。
- 禁止字段。
- 权限范围。
- 版本前置条件。

这才能真正支持自动生成 SDK 和可靠的 Agent 工具调用。

### 额外要求：Schema 必须可双端验证

同一份测试样例分别由：

- TypeScript 客户端校验器。
- Go 服务端校验器。

执行验证。

对于边界输入，两端应得出相同结论。

如果结果不同，以 Go 服务端判断为最终依据，并把差异作为契约测试失败处理。

---

## 5.4 错误状态

正式采用 RFC 9457 Problem Details 结构。

| HTTP 状态 | 业务错误码 | 处理方式 |
|---|---|---|
| 400 | INVALID_REQUEST | 修正请求格式 |
| 401 | AUTHENTICATION_REQUIRED | 重新认证 |
| 403 | SCOPE_DENIED | 权限不足 |
| 404 | RESOURCE_NOT_FOUND | 不存在或不可访问 |
| 409 | RESOURCE_CONFLICT | 资源冲突 |
| 412 | VERSION_CONFLICT | 重新读取当前版本 |
| 422 | VALIDATION_FAILED | 修正业务数据 |
| 428 | PRECONDITION_REQUIRED | 补充必要版本前置条件 |
| 429 | RATE_LIMITED | 按限制重试 |
| 503 | STORAGE_UNAVAILABLE | 存储不可用，安全重试 |

对页面草稿等要求乐观锁的修改接口，使用 `If-Match`。

RFC 9110 规定，当 `If-Match` 前置条件不成立时，通常返回 `412 Precondition Failed`。

这让浏览器、后台和 Agent 能使用统一的并发控制语义。

# 六、网站发布事务：正式冻结

这是整个 V0.6 最关键的事务契约。

## 6.1 发布分为两阶段

**阶段 A：Preflight Validation**

进行成本较高的检查：

- 页面组件树。
- Theme 依赖。
- Renderer 兼容性。
- 公开媒体状态。
- URL 冲突。
- 数据绑定。
- SEO 配置。
- 公开内容权限。

检查通过后，记录草稿版本和验证结果。

**阶段 B：Commit Publication**

在数据库事务中重新检查可能发生变化的关键条件，并创建正式发布版本。

### 核心流程

```text
请求 Publish
      │
      ▼
身份与发布权限检查
      │
      ▼
预检 PageDocument、组件、媒体、路由
      │
      ▼
BEGIN TRANSACTION
      │
      ▼
锁定 Site
      │
      ▼
检查 Base Release
      │
      ▼
锁定 Draft 并核对 Revision
      │
      ▼
复核必要媒体和资源引用状态
      │
      ▼
创建不可变 Page Revisions
      │
      ▼
创建 Site Release
      │
      ▼
创建 Route / Template Bindings
      │
      ▼
记录审计及可靠后台任务
      │
      ▼
切换 published_release_id
      │
      ▼
COMMIT
      │
      ▼
新的页面请求读取新 Release
```

### 6.2 必须防止媒体删除竞态

例如，发布校验刚刚确认图片可用，另一个后台操作就删除了图片。

因此不能只在发布前检查一次媒体状态。

需要通过受控引用记录和文件删除协议保证：

- 发布版本能够锁定其使用的媒体资源。
- 正在被正式版本引用的媒体不能被垃圾回收。
- 删除任务需要再次验证引用关系。
- 文件清理必须晚于安全的逻辑删除和保留期。

建议增加：

```text
site_release_media
```

为已发布版本建立媒体引用保护关系。

这不是复制图片，只是保存引用。

### 6.3 第一版不使用复杂 HTML 缓存

为了优先保证发布正确性，V0.6 第一阶段可以让动态 HTML 使用：

```http
Cache-Control: no-store
```

正式 SSR 请求读取当前 Site Release。

商品图片和其他内容哈希固定的媒体资源可以使用长缓存。

这样在尚未实现完整的 CDN 失效策略前，能够避免大量页面缓存和版本管理问题。

以后通过真实压测再决定是否增加：

- 页面级缓存。
- 标签缓存。
- Valkey。
- CDN 缓存失效。

Astro 官方支持通过服务端适配器进行按需渲染，动态路由无需在构建时枚举所有商品路径，因此这种架构不要求在发布时重新生成数万个商品页面。

### 6.4 River 与 Outbox 不应重复承担同一职责

这一轮建议进一步简化：

**River：** PostgreSQL 内部可靠后台任务，例如图片处理、索引刷新、异步通知。

**Outbox：** 未来对外部 ERP、Webhook 等系统发送需要可靠交付的业务事件。

第一阶段的内部任务优先使用 River 的事务性入队。

不要为了每个内部任务同时写入 River 和 Outbox，再开发两套重复的重试系统。

River 官方提供事务内入队机制，能够将业务修改和任务提交放入同一个 PostgreSQL 事务。

### 6.5 回滚不是修改旧 Release

假设已经发布：

```text
Release 12
Release 13
Release 14
```

用户需要恢复 Release 12 的页面布局。

建议：

```text
Restore Release 12
         │
         ▼
验证当前 Renderer 兼容
         │
         ▼
生成新的 Release 15
         │
         └── restored_from = Release 12
```

而不是删除 Release 13、14，或者直接覆盖历史数据。

这样：

- 发布历史完整。
- 审计关系清晰。
- 仍然保留恢复前状态。
- 页面恢复不会自动撤销后续订单和库存变动。

**这是第一版 Site Release 最终采用的恢复语义。**

## 7.2 端到端测试流程

### Test 01：安装和初始化

从空白服务器环境开始：

```text
启动 PostgreSQL
        ↓
启动 Go API
        ↓
启动 Astro SSR
        ↓
启动 Caddy
        ↓
执行数据库迁移
        ↓
初始化管理员身份
        ↓
系统 Ready
```

验收条件：

- 所有数据库迁移成功。
- Go API 健康检查通过。
- Astro SSR 能调用内部 API。
- 媒体持久化目录可写。
- 不需要商业对象存储账号。
- 不需要 Redis、Kafka 或 Kubernetes。
- 没有默认公开的管理员密码。

开发测试可以使用本地 HTTP；正式部署必须通过受信任的 HTTPS 入口管理认证凭证。

### Test 02：创建企业和网站

调用 API：

```http
POST /api/v1/organizations
POST /api/v1/sites
```

预期：

- 创建一个 Tenant 下的 Organization。
- 创建一个 Site。
- Site 与企业关联正确。
- 当前站点尚未发布。
- 未认证用户不能修改企业数据。

### Test 03：创建商品和两个 SKU

```http
POST /api/v1/products
POST /api/v1/products/{id}/options
POST /api/v1/products/{id}/variants
```

数据：

```text
Product:
  Reed Diffuser 200ml

Variants:
  REED200-GARDENIA
  REED200-LAVENDER
```

需要检查：

- 两个 SKU 均属于同一 Product。
- 规格组合正确。
- 重复 SKU 被拒绝。
- 无效规格组合被拒绝。
- 跨租户引用被拒绝。

### Test 04：上传商品图片

使用本地图片测试夹具，而不是依赖外部图片服务。

```http
POST /api/v1/media/uploads
PUT  /api/v1/media/uploads/{id}/content
POST /api/v1/media/uploads/{id}/complete
```

验证：

- 原始文件写入 LocalFS。
- SHA-256 与源文件一致。
- 记录文件大小和 MIME。
- 媒体进入 READY 状态。
- 商品成功绑定 Media Asset。
- 商品引用中没有物理文件路径。

然后模拟上传中断和处理失败。

失败任务必须可安全清理或重试。

### Test 05：创建企业资料和博客

通过 API 写入：

- 企业简介。
- 公开邮箱。
- 企业展示图片。
- 博客标题。
- 博客正文。
- 博客封面图片。

验证：

- 内容具有独立资源 ID。
- 企业私有资料不会自动公开。
- 博客草稿无法被匿名用户读取。
- 已发布文章可通过公开路由访问。

### Test 06：创建网站页面

创建：

```text
Home
About
Contact
Product Detail Template
Blog Listing Template
Blog Article Template
```

通过 Component Registry 选择组件。

通过 Data Resolver 绑定商品及企业数据。

验证：

- 每个组件均有已注册版本。
- 属性符合 Schema。
- 商品网格返回实际商品数据。
- 企业介绍组件从企业内容服务读取资料。
- 博客组件从 CMS 获取数据。

### Test 07：通过 API 修改页面

例如修改首页：

```text
原标题：
Welcome

新标题：
Discover Our Fragrance Collection
```

调用 Page Operation API。

验证：

- Draft Revision 增加。
- 已发布网站保持原版本。
- 通过预览可以看到新标题。
- 修改记录包含操作者和版本信息。
- 重复提交同一幂等操作不产生重复节点。

### Test 08：正式发布

调用：

```http
POST /api/v1/sites/{id}/drafts/{draft_id}/publish
```

发布前检查：

- 页面结构。
- 商品和博客数据。
- 媒体状态。
- URL 冲突。
- Renderer 版本。
- 权限。
- Release 基线。

发布成功后：

```text
Site → Release 1
```

公开网站能够访问：

```text
/
 /products/reed-diffuser-200
 /about
 /blog
 /blog/how-to-use-reed-diffuser
 /contact
```

所有商品图片及文章媒体正常展示。

商品详情页面的内容来自 Product 和 Product Listing，而不是一份手工复制的静态 HTML。

### Test 09：真实提交询盘

访客在商品详情页填写：

```text
Product: Reed Diffuser 200ml
Quantity: 500
Email: buyer@example.com
Message: Please provide a quotation.
```

提交后：

- 数据写入 `inquiries`。
- 正确关联 Site 和 Product。
- 管理后台可以读取询盘。
- 其他租户无法读取。
- 重复请求按照幂等或反重复策略处理。
- 通知失败不丢失询盘本身。

至此，第一个网站已经具备真实的 B2B 获客入口。

### Test 10：修改、发布和回滚

将首页 Hero 修改为另一个标题。

发布 Release 2。

验证公开站点显示新标题。

然后恢复 Release 1。

系统创建 Release 3，其展示配置来自 Release 1。

必须验证：

- 首页恢复。
- 商品数据不被删除。
- 询盘记录不被删除。
- 博客的独立发布记录不被随意改写。
- 媒体引用仍然有效。
- 审计记录可以追踪恢复操作。

**只有这十项测试形成完整闭环，才可以声称第一份最小独立站架构得到了端到端验证。**

# 八、必须增加的故障与安全测试

正常流程跑通还不够。

对于将来允许 Agent 批量操作的网站平台，异常恢复更加重要。

## 8.1 故障注入

| 场景 | 预期行为 |
|---|---|
| PostgreSQL 暂时不可用 | API 返回受控错误，不伪报成功 |
| 上传期间进程退出 | 不留下已发布的损坏媒体 |
| 图片哈希不一致 | 拒绝进入 READY |
| 发布事务中断 | 旧 Release 保持可用 |
| 两个管理员同时发布 | 后发布者检测版本冲突 |
| Agent 重复请求 | 不重复创建组件或商品 |
| 旧 Renderer 缺失组件 | 拒绝不兼容回滚 |
| SMTP 发送失败 | 询盘仍被保存 |
| 用户尝试访问其他租户 | 拒绝 |
| 私有证照被引用到公开页面 | 发布验证失败 |

另外需要模拟异常 JSON、大量嵌套组件、恶意 HTML、非法文件路径和伪造 MIME。

尤其要确保页面配置不能注入任意 SQL、服务端 JavaScript 或未经授权的外部数据请求。

## 8.2 Agent 的最低验收

V0.6 不要求 AI 从一句自然语言自动完成所有建站工作。

第一阶段只需要证明：

**Agent 能够通过公开、受授权的 API，完成与 React 编辑器相同的确定性操作。**

建议测试：

```text
Agent 查询站点
      ↓
读取组件 Schema
      ↓
创建草稿
      ↓
添加商品网格
      ↓
绑定商品数据
      ↓
修改首页标题
      ↓
执行 Validate
      ↓
生成 Preview
      ↓
申请发布
```

然后验证：

- 不存在 Agent 专用的数据库后门。
- 不存在绕过 Schema 的修改通道。
- 不存在未经授权的正式发布。
- 每一步都有结果、错误和审计。
- 同一个操作可以通过 API 重试。

这套能力稳定后，再扩展 V0.4 已设计的 SiteSpec 和 Site Plan 自动建站流程。

# 九、服装行业的大规模测试

香氛样例负责验证业务闭环。

服装测试负责验证大商品数量。

两者不能混为一谈。

## 9.1 固定数据集

| 指标 | 测试规模 |
|---|---:|
| SPU | 10,000 |
| 每款颜色 | 6 |
| 每色尺码 | 5 |
| 总 SKU | 300,000 |
| 商品图片 | 80,000 |
| 商品分类 | 500 |
| 商品属性定义 | 100 |
| 网站 | 2 |
| 主题 | 2 |

目标是验证：

**10,000 个商品使用少量模板时，不会因为商品增加而导致页面模板数量线性增长。**

两个站点可以共享 Catalog，但使用不同模板及商品上架规则。

### 测试对象

重点测：

- SKU 精确查询。
- 商品全部变体读取。
- 颜色与尺码筛选。
- 批量导入。
- 商品分页。
- 分类页面。
- Media Asset 关联。
- 两个站点的商品隔离。
- 模板切换。
- Astro SSR。
- 数据库索引大小。
- Worker 资源占用。

首轮应记录实际 p50、p95、p99 和内存峰值，再根据结果建立性能回归阈值。

不应直接承诺某个固定 QPS。

## 9.2 特别检查大量图片的存储成本

80,000 张图片、平均 2MB 原文件，意味着约 160GB 原始存储需求。

如果增加派生尺寸、视频和独立备份，实际需要更多空间。

所以 V0.6 应至少具备：

- 原文件复用。
- 按需派生图片。
- 文件哈希校验。
- 媒体引用保护。
- 存储容量统计。
- 可恢复备份。

**本地硬盘是免费的软件存储方案，不是零硬件成本方案。**

这项边界需要在开源安装文档中明确说明。

## 最终结论

**OpenSite Commerce V0.6 的工程方向已经可以明确冻结：**

| 层级 | 最终选择 |
|---|---|
| 核心语言 | Go |
| 核心数据库 | PostgreSQL 18 |
| 数据库访问 | pgx + sqlc |
| 后台任务 | River |
| 前端工具链 | Bun |
| 管理后台 | React + TypeScript |
| 网站渲染 | Astro SSR |
| 组件体系 | Component Registry + JSON Schema |
| 页面编辑 | PageDocument + Operation API |
| 企业内容 | CMS + 内容版本 |
| 商品系统 | Product + Variant + Attribute + Listing |
| 免费媒体存储 | LocalFS |
| 扩展媒体存储 | S3 Adapter |
| 网站发布 | Immutable Revision + Site Release |
| Agent 接口 | OpenAPI + MCP Adapter |
| 部署 | Docker Compose + Caddy |

我认为现在最重要的已经不是继续讨论 Go、Bun、Rust 或增加新的技术组件。

**真正决定这个开源项目能否成功的是：一份商品数据能否被多个网站、模板和 Agent 共同使用；一个网站能否通过 API 完整创建、修改、预览和发布；以及整套系统能否在普通自有服务器上稳定运行。**

V0.6 已将这些目标拆解为具体的数据库约束、接口行为和验收场景。

**下一阶段应该进入工程实现，而不是 V0.7 的概念扩展。** 优先完成 PostgreSQL 迁移、OpenAPI 契约和三个基础组件的真实渲染闭环，再向博客、询盘及 Agent 批量管理扩展。这能够尽早验证整个架构，同时控制单人开发和多编码代理协作的复杂度。
