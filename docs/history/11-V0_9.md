# OpenSite Commerce V0.9
## 前端 UI 技术选型、设计系统、视觉审查与全链路 CI 架构

**版本：V0.9 — Frontend Architecture & Visual Quality Engineering**  
**日期：2026 年 10 月 11 日**  
**目标：建立统一的前端组件体系，让所有 UI 修改都经过自动化检查、视觉审查和独立验收。**

## 一、总体结论

经过重新研究，我认为此前 V0.8 的模块化方向正确，但**前端工程质量体系存在明显缺口**。

之前主要解决了：

- React 管理后台的业务模块划分。
- Astro Storefront 的展示模块划分。
- Go API 与前端的数据契约。
- 页面模板和组件注册。
- PR、独立审核和分层 CI。

但尚未真正解决：

1. 选择哪一套开源 UI 组件体系。
2. 谁负责维护组件的视觉规范。
3. 如何保证不同模块使用相同的颜色、字体、间距及交互方式。
4. 如何自动检查 PC、手机、平板的视觉问题。
5. 如何检查按钮、表单、弹窗、商品卡片等组件的各种状态。
6. 如何阻止不合格 UI 通过 CI。
7. 如何在不依赖付费视觉测试服务的情况下完成视觉回归。
8. 如何保证网站主题可自由定制，而管理后台仍保持一致性。

这八个问题需要作为正式工程架构处理，不能仅依靠编码代理生成页面后人工查看。

### 我建议的技术组合

| 层级 | 选择 | 用途 |
|---|---|---|
| UI 基础交互 | **Base UI** | 无样式、可访问性基础组件 |
| UI 组件源码 | **shadcn/ui 官方开源版本** | 作为组件起点，纳入自有组件库 |
| 样式体系 | **Tailwind CSS + CSS Variables** | 统一组件样式与主题 |
| 设计规范 | **Design Tokens** | 颜色、字体、间距、布局等 |
| 大数据表格 | **TanStack Table + TanStack Virtual** | 商品、订单、SKU 管理 |
| 服务端数据 | TanStack Query | React 后台数据缓存与请求状态 |
| 表单 | React Hook Form + Schema 校验 | 商品、企业、后台配置 |
| 富文本编辑 | **Meta Lexical** | 博客、企业介绍、商品富文本 |
| 页面拖拽 | dnd-kit | 可视化页面编辑器 |
| 图片上传 | Uppy（按需要引入） | 批量上传、进度及可恢复上传 |
| 组件文档 | **Storybook** | 组件开发、状态展示、测试 |
| 单元测试 | Vitest + React Testing Library | 组件逻辑、交互 |
| 浏览器测试 | **Playwright** | 页面、交互、截图及回归 |
| 无障碍审查 | axe-core + Storybook + Playwright | WCAG 相关自动检查 |
| 视觉回归 | **Playwright Screenshots** | 免费、自部署截图比较 |
| 性能检查 | Lighthouse CI | 页面性能与资源预算 |
| CI 平台 | GitHub Actions | 自动执行、保存报告、合并门禁 |

**核心原则：使用开源组件解决复杂交互，不从零重写按钮、弹窗和表格；但整个项目必须拥有自己的 Design System 和组件公共 API。**

# 二、先厘清 Meta 的前端开源技术

你提到 Meta 有前端 UI 库，这一点值得纳入研究，但需要区分它开源的不同项目。

| Meta 项目 | 实际作用 | 是否推荐 |
|---|---|---|
| [React](https://react.dev/) | UI 渲染框架 | 已采用 |
| [StyleX](https://stylexjs.com/) | 原子化 CSS 与样式系统 | 暂不采用 |
| [Lexical](https://lexical.dev/) | 可扩展富文本编辑器 | **采用** |

Meta 的 StyleX 是专门的样式系统，不是包含各种按钮、弹窗和表单的完整成品组件库。它采用 MIT 许可证。Lexical 同样采用 MIT，支持结构化编辑、React 集成和丰富的编辑扩展。

### 为什么不直接采用 StyleX？

StyleX 本身有价值，但 OpenSite Commerce 的特殊需求是：

- 商家能够通过 API 调整网站视觉。
- 主题需要动态切换。
- Admin 和 Storefront 需要共享 Design Tokens。
- 第三方可以开发主题。
- Tailwind 和现有 React 组件生态便于快速扩展。

如果同时引入 Tailwind、StyleX 和组件库自己的样式系统，会增加样式编译、变量映射和主题兼容的复杂度。

因此当前选择：

**Tailwind CSS + Design Tokens + CSS Variables。**

StyleX 保留为后续技术对照，不作为第一版必需依赖。

### 为什么采用 Lexical？

博客和企业介绍不能只使用普通的 HTML Textarea。

需要支持：

- 标题、段落、列表。
- 图片和视频。
- 商品引用。
- 超链接。
- 撤销与重做。
- 草稿版本。
- 结构化内容存储。
- API 创建及更新文章。

Lexical 适合作为 React 后台富文本编辑器的底层技术。

但是，**Lexical 的内部编辑器状态不能直接成为整个 CMS 的永久数据标准**。

应建立受版本控制的 CMS ContentDocument，由适配器负责 Lexical 编辑状态与 CMS 内容块之间的转换。

这样未来即使替换 Lexical，也不需要迁移整个网站的全部商品和博客业务数据。

# 三、开源 UI 库选型比较

## 3.1 主要候选

我重点比较了以下开源方案。

| UI 库 | 类型 | 优势 | 对 OpenSite Commerce 的限制 |
|---|---|---|---|
| [Base UI](https://base-ui.com/) | Headless React | 无样式、可访问性、可组合 | 需要自己的视觉设计 |
| [Radix UI](https://www.radix-ui.com/) | Headless React | 生态成熟、交互基础扎实 | 需要自行设计样式 |
| [shadcn/ui](https://ui.shadcn.com/) | 开源组件源码 | 易于修改、适合建立自有组件库 | 组件源码需要自己维护 |
| [MUI](https://mui.com/) | 完整 React UI | 组件丰富、后台开发快 | Material 风格较明显，部分高级 X 功能另有授权 |
| [Ant Design](https://ant.design/) | 完整企业级 UI | 复杂后台和表单生态成熟 | 自定义独立视觉体系时需适配既有设计规范 |
| [Mantine](https://mantine.dev/) | 完整 React UI | 免费、组件多、开发效率高 | 更适合以 Mantine 主题系统为基础 |
| [React Aria](https://react-spectrum.adobe.com/react-aria/) | Headless React | 无障碍、国际化及交互能力强 | 需要自己的样式和组件封装 |

这几种方案并不是简单的性能排名。

它们分成三类：

**第一类：Headless Primitives**

Base UI、Radix、React Aria。

主要提供交互行为、键盘操作、焦点管理和可访问性基础。

**第二类：完整 UI 框架**

MUI、Ant Design、Mantine。

已经包含丰富的默认视觉设计。

**第三类：开放组件源码**

shadcn/ui。

提供可以直接纳入自己项目并修改的组件源码。官方明确将其定位为构建自有组件库的基础，而不是传统黑盒式 npm 组件库。

## 3.2 一个重要的 2026 年变化

**shadcn/ui 已于 2026 年 7 月将 Base UI 设为新项目的默认底层组件体系。**

Radix 仍然得到支持。

而且，当前 Base UI 应使用：

```text
@base-ui/react
```

不应再为新项目采用已弃用的：

```text
@mui/base
```

这些变化均有官方文档记录。

### 最终选择

对于一个全新的 OpenSite Commerce 项目，我建议：

**Base UI + shadcn/ui 官方组件源码 + 自有 Design System。**

具体关系是：

```text
Base UI
   │
   ▼
交互与无障碍基础
   │
   ▼
官方 shadcn/ui 开源组件实现
   │
   ▼
OpenSite UI Components
   │
   ├── Button
   ├── Dialog
   ├── Select
   ├── Tabs
   ├── Form
   ├── Navigation
   └── DataTable
```

**最终业务代码只依赖 OpenSite UI 的公开组件接口。**

这样以后更换某个底层组件库时，不需要修改全部商品管理、企业管理和 CMS 页面。

### 一个必须注意的开源许可证问题

官方 [shadcn/ui GitHub 仓库](https://github.com/shadcn-ui/ui) 采用 MIT 许可证。

但第三方网站 `shadcn.io` 提供的商业 Pro Blocks 并不属于同一份开源授权，其许可证甚至明确限制将相关商业组件用于某些网站构建器产品。

因此：

**OpenSite Commerce 只能默认纳入许可证明确允许开源再分发和网站构建用途的组件。**

不能看到组件名称里有 shadcn，就认为它能够免费放入我们的开源建站平台。

这必须进入 CI 的依赖与许可证检查。

# 四、前端整体架构：必须区分三套组件体系

这是我认为整个项目最重要的前端架构决定。

**管理后台组件、网站展示组件和可视化编辑器组件不能全部混在同一个 UI 库里。**

它们可以共享设计令牌、数据契约和部分基础能力，但承担不同职责。

## 4.1 最终前端架构

```text
                    OpenSite Frontend
                            │
          ┌─────────────────┼───────────────────┐
          │                 │                   │
          ▼                 ▼                   ▼
     React Admin       Astro Storefront     Page Builder
          │                 │                   │
          ▼                 ▼                   ▼
    Admin Features    Storefront Modules   Editor Features
          │                 │                   │
          ▼                 ▼                   ▼
     OpenSite UI       Theme Components    Builder UI
          │                 │                   │
          ▼                 ▼                   ▼
     Base UI            Astro / CSS        Base UI + dnd-kit
     shadcn/ui          React Islands      Astro iframe
          │                 │                   │
          └─────────────────┼───────────────────┘
                            │
                            ▼
                     Shared Contracts
                            │
          ┌─────────────────┼───────────────────┐
          │                 │                   │
          ▼                 ▼                   ▼
     Design Tokens      JSON Schema         OpenAPI SDK
          │                 │                   │
          └─────────────────┼───────────────────┘
                            │
                            ▼
                       Go Business API
```

### 第一层：Admin UI

管理后台使用统一的 OpenSite UI 组件库。

所有业务模块必须使用相同的基础组件。

例如商品模块、博客模块、订单模块使用相同的：

- Button。
- Dialog。
- FormField。
- Select。
- DataTable。
- Pagination。
- Notification。
- Loading State。
- Error State。

不允许 Catalog 自己制作一套按钮，CMS 又制作另一套外观和行为不同的按钮。

### 第二层：Storefront Components

商城与企业官网使用独立的展示组件系统。

例如：

```text
catalog.product-card
catalog.product-grid
catalog.product-gallery
catalog.variant-selector

company.profile
company.gallery
company.contact

cms.blog-list
cms.article-content

b2b.quote-form
b2b.volume-pricing

commerce.add-to-cart
commerce.checkout-summary
```

这些不是普通 UI Primitives。

它们是可以绑定业务数据的**网站组件**。

用户可以通过 Page Builder、API 或 Agent 选择和配置它们。

### 第三层：Page Builder UI

Page Builder 本身使用 React Admin 的基础 UI。

但是页面预览直接使用 Astro 正式渲染器。

```text
React Editor
    │
    ├── Component Palette
    ├── Component Tree
    ├── Properties Panel
    ├── Responsive Controls
    └── Operation History
              │
              ▼
         PageDocument
              │
              ▼
          Go API
              │
              ▼
       Astro SSR Preview
```

这样，后台编辑器和正式网站不会演变成两套完全不同的页面实现。

**V0.9 决定：Admin UI、Storefront Components、Builder UI 分离；只共享正式契约和明确可复用的基础能力。**

# 五、细分功能应该使用哪些开源库？

不建议整个后台全部自己开发，也不建议引入十几套相互竞争的 UI 框架。

我建议按照功能选用专门的开源库。

| 功能 | 首选库 | 选择理由 |
|---|---|---|
| 基础 UI | Base UI | 弹窗、菜单、选择器等交互基础 |
| 组件视觉 | shadcn/ui 官方源码 | 可修改、可纳入自有设计系统 |
| 数据表格 | TanStack Table | 表格逻辑与视觉解耦 |
| 大数据虚拟滚动 | TanStack Virtual | 降低大量行的 DOM 开销 |
| API 请求和缓存 | TanStack Query | 查询状态、缓存、失效 |
| 表单管理 | React Hook Form | 大型表单和字段管理 |
| 表单校验 | Schema 驱动 | 统一字段约束 |
| 博客编辑 | Meta Lexical | 富文本、可扩展节点 |
| 页面拖拽 | dnd-kit | 结构化组件拖动 |
| 文件上传 | Uppy | 批量文件、进度和可恢复上传 |
| 图标 | Lucide | 统一图标体系 |
| 日期、金额和地区格式 | Intl API | 减少自定义格式化逻辑 |

TanStack Table 和 TanStack Virtual 是分工不同的两个库：前者负责表格数据与状态，后者负责可见区域渲染。即使采用虚拟滚动，也不能因此把几十万条 SKU 全部下载到浏览器，仍然需要后端分页和筛选。

dnd-kit 当前的 React 集成可以使用 `@dnd-kit/react`。Uppy 为 MIT 开源项目，支持多种上传方式和可恢复上传协议，但前提是服务端也实现对应协议。

## 5.1 商品后台：大表格是重点

服装行业可能存在几十万 SKU。

因此商品后台需要：

```text
Catalog Admin
│
├── Product List
├── Product Editor
├── Variant Editor
├── Attribute Manager
├── Bulk Import
├── Media Manager
└── Category Manager
```

尤其是商品列表：

**TanStack Table + TanStack Virtual + 后端 Cursor Pagination。**

必须实现：

- 服务端筛选。
- 服务端排序。
- 分页。
- 批量选中。
- 批量修改。
- 导入任务进度。
- 行级错误展示。
- 长任务恢复。

一个容易忽略的问题是批量选择。

用户选择了“当前筛选结果中的全部 12,000 个 SKU”，并不意味着需要将全部 SKU ID 先加载到浏览器。

应由后台生成受权限控制的批量操作集合或任务快照。

否则会出现前端内存与请求体不断膨胀的问题。

## 5.2 博客：使用 Lexical，但不绑定永久存储格式

推荐：

```text
Lexical Editor
      │
      ▼
Content Adapter
      │
      ▼
CMS ContentDocument
      │
      ▼
Go CMS API
      │
      ▼
PostgreSQL
      │
      ▼
Astro Article Renderer
```

富文本中的图片和视频需要使用 Media Asset ID。

文章中的商品推荐需要使用 Product ID。

不能直接保存来自编辑器的任意可执行 HTML。

## 5.3 页面编辑器：使用 dnd-kit

第一版支持结构化拖拽：

```text
Page
 └── Section
      └── Container
           └── Components
```

不用第一版就实现类似 Figma 的任意绝对定位画布。

这样有利于移动端响应式、模板升级、Agent 操作和 API 编辑。

# 六、建立正式的 OpenSite Design System

**选择 UI 库只是起点。设计系统才是视觉一致性的权威。**

建议新建：

```text
packages/
├── design-tokens/
├── ui/
├── icons/
├── component-contracts/
└── ui-test-utils/
```

## 6.1 使用 Design Tokens 作为视觉规范

建议按 DTCG Design Tokens 格式管理设计令牌。

W3C Design Tokens Community Group 已于 2025 年 10 月发布首个稳定版本，包括格式、颜色和解析模块。

令牌分为四层。

| 层级 | 示例 | 用途 |
|---|---|---|
| Primitive | blue-500、spacing-4 | 基础设计值 |
| Semantic | color-primary、text-muted | 语义角色 |
| Component | button-height、input-radius | 组件规范 |
| Theme | 品牌色、字体、页面宽度 | 网站主题覆盖 |

例如：

```json
{
  "color": {
    "primary": {
      "$type": "color",
      "$value": "#202B3B"
    }
  },
  "spacing": {
    "md": {
      "$type": "dimension",
      "$value": "16px"
    }
  }
}
```

由设计令牌生成：

- CSS Variables。
- Tailwind 主题配置。
- React UI 的公共样式。
- Astro 主题变量。
- 组件文档中的 Token 展示。

Tailwind 当前使用 `@theme` 和 CSS 变量表示设计令牌，能够与这种方式结合。

### 6.2 管理后台与商家网站不能共享全部视觉配置

建议区分：

**Admin Design System**

由 OpenSite 项目维护。

整个后台始终使用一致的视觉设计。

**Storefront Theme System**

由商家选择或配置。

商家可以使用黑白、米白、粉色、深蓝或其他品牌色。

例如：

```text
Design Tokens
     │
     ├── Admin Theme
     │     └── OpenSite 官方后台视觉
     │
     └── Storefront Themes
           ├── Corporate
           ├── Fashion
           ├── Fragrance
           └── Wholesale
```

商家切换网站主题不能改变整个管理后台的按钮和对话框样式。

### 6.3 必须制定的视觉规范

| 规范 | 最低要求 |
|---|---|
| 颜色 | 使用语义 Token，不散落硬编码 |
| 字体 | 标题、正文、说明文字分级 |
| 间距 | 统一间距等级 |
| 圆角 | 统一半径体系 |
| 阴影 | 统一层级 |
| 图标 | 统一图标库和尺寸规范 |
| 表单 | Label、错误、帮助文本位置一致 |
| 弹窗 | 焦点、遮罩、关闭方式一致 |
| 表格 | 表头、筛选、分页、选中状态一致 |
| 响应式 | 采用明确布局断点 |
| 无障碍 | WCAG 2.2 AA 作为目标基线 |
| 状态 | Loading、Empty、Error、Disabled 均有标准表现 |

其中字体、间距等不能只有视觉说明，还应转化为 Token 和自动检查规则。

### 6.4 组件必须支持完整状态

以 Button 为例：

```text
Button
├── Default
├── Hover
├── Focus
├── Active
├── Disabled
├── Loading
├── Error Context
└── Dark Mode
```

以商品表格为例：

```text
Product Table
├── Loading
├── Empty
├── Normal
├── Filtering
├── Pagination
├── Multi Selection
├── API Error
├── Very Long Text
└── Large Dataset
```

这些状态都需要形成可测试的组件示例。

不能只验收一个正常状态下的漂亮截图。

# 七、视觉审查必须成为 CI 的正式门禁

这是你本次强调的重点。

我建议为前端建立**七类质量检查**。

| 检查 | 技术 | 主要发现的问题 | PR 门禁 |
|---|---|---|---|
| UI 代码规范 | ESLint、TypeScript、Token Lint | 非法属性、错误引用、设计规范偏离 | 必需 |
| 组件行为 | Vitest、Testing Library | 交互、状态、表单错误 | 必需 |
| 视觉回归 | Playwright Screenshot | 布局、尺寸、颜色、可见变化 | UI 相关 PR 必需 |
| 无障碍 | axe-core、键盘测试 | ARIA、标签、焦点、对比度 | 必需 |
| 响应式 | Playwright 多视口 | 溢出、错位、裁切 | UI 相关 PR 必需 |
| 浏览器兼容 | Chromium、Firefox、WebKit | 浏览器行为差异 | 关键路径必需 |
| 性能与资源 | Lighthouse CI、Bundle Budget | JS、图片、页面性能回归 | 按影响范围执行 |

其中视觉回归不需要购买 Chromatic 等商业服务。

Playwright 原生支持 `toHaveScreenshot()`，能够比较页面和基线截图，并提供像素差异阈值。官方同时明确提醒，不同操作系统、浏览器和运行环境可能产生截图差异。

**因此，我们将 Playwright 作为免费视觉回归主引擎。**

Storybook 主要负责 React 组件开发、状态组织和交互测试。

Astro 原生页面则直接使用 Playwright 测试真实 SSR 页面，不强行套用 React Storybook 渲染器。

# 八、视觉测试的完整执行流程

建议：

```text
UI Pull Request
       │
       ▼
检测受影响的前端模块
       │
       ▼
构建 React / Astro
       │
       ▼
加载固定测试数据
       │
       ▼
启动测试网站
       │
       ▼
Playwright 打开实际页面
       │
       ├── Desktop
       ├── Tablet
       ├── Mobile
       ├── Light / Dark
       └── Component States
       │
       ▼
生成 Actual Screenshot
       │
       ▼
读取 Approved Baseline
       │
       ▼
生成 Pixel Diff
       │
       ├── 没有非预期差异 → PASS
       │
       └── 存在差异 → REVIEW / FAIL
                     │
                     ▼
             独立视觉审查
                     │
                     ▼
             更新基线或修复 UI
```

## 8.1 固定截图环境

视觉测试必须尽可能确定性运行。

要求：

- 固定 Playwright 和浏览器版本。
- 固定 Docker 镜像。
- 固定测试字体。
- 固定语言。
- 固定时区。
- 固定测试商品和图片。
- 固定动画状态。
- 固定测试时间。
- 禁止依赖随机展示内容。
- 禁止使用不稳定的第三方图片接口。

尤其要固定字体。

同一段文字在不同字体下产生的换行差异，可能让整张页面截图发生变化。

### 不允许随意遮罩关键内容

Playwright 支持通过样式或遮罩降低动态区域造成的截图波动，但需要有严格限制。

不能因为商品图片经常变化，就在视觉测试中直接遮住商品图片。

否则商品主图变形、错误裁切等真正重要的问题反而无法发现。

**商品主体、价格、规格选择器、标题、购买按钮不能随意排除出视觉检测。**

## 8.2 视口测试矩阵

建议第一阶段：

| 视口 | 宽度 | 检查重点 |
|---|---:|---|
| Small Mobile | 320px | 最窄布局 |
| Mobile | 375px | 常规手机 |
| Large Mobile | 390px | 手机响应式 |
| Tablet | 768px | 栏目变化 |
| Desktop | 1280px | 标准桌面 |
| Wide Desktop | 1440px | 宽屏排版 |

不需要每个组件都进行全部组合。

可以按照组件类型选择必要视口。

例如 Dialog 更关注桌面与手机。

商品详情需要重点检查 375px、768px 和 1440px。

大型 Admin DataTable 需要检查滚动、分页和列可见性。

Playwright 支持设置视口、设备、语言、时区、触摸模式和颜色方案，适合建立这样的固定测试矩阵。

# 九、视觉审查不能只看 Pixel Diff

这是一个特别重要的架构问题。

**截图与旧截图一致，不代表页面设计质量合格。**

例如第一版的字体本来就很小。

后续每次截图都和第一版一致，视觉测试可能全部通过。

但用户仍然看不清文字。

因此需要两种独立检查。

## 9.1 自动可测检查

例如：

| 问题 | 检查方式 |
|---|---|
| 页面出现横向溢出 | DOM 尺寸与视口比较 |
| 图片加载失败 | 资源状态和图片尺寸检查 |
| 商品图片发生意外变化 | 媒体 ID、哈希与截图比较 |
| 按钮不可点击 | Playwright 交互 |
| 表单无 Label | axe-core |
| 标题被隐藏 | 可见性与布局断言 |
| 移动端导航不可用 | 真实交互测试 |
| UI 出现异常控制台错误 | Console/Error 检查 |
| 页面回归 | Screenshot Diff |
| 缺失必要组件 | PageDocument 与 DOM 断言 |

这些能够自动阻止一部分明显错误。

但是 CSS Overflow 检查不能完整识别全部文字重叠，Screenshot Diff 也不能证明文案与商品事实正确。

## 9.2 独立视觉审查

建议独立审查者查看：

- 新旧截图。
- 差异截图。
- 手机与桌面版本。
- 关键交互状态。
- 对应 Design Tokens。
- 商品真实媒体引用。
- 组件契约变化。

重点审查：

**视觉层次、内容可读性、间距、对齐、产品展示真实性、响应式质量和整体一致性。**

这类判断可以使用 AI 辅助，但不能把 AI 的视觉评价等同于实际像素认证或浏览器测试。

### 特别增加商品视觉身份检查

对于电商项目，商品图片不仅是装饰。

它还涉及：

- 商品颜色。
- 形状和规格。
- 配件数量。
- 真实包装。
- 品牌印刷。
- 商品主图与 SKU 的对应关系。

因此应加入独立的 **Product Media Integrity** 检查。

它至少验证：

1. 页面引用的是正确的 Media Asset。
2. 原始图片文件的哈希没有意外变化。
3. SKU 对应的媒体关系正确。
4. 页面图片没有意外拉伸。
5. 图片裁切行为符合组件规则。
6. 商品主体不会被覆盖或完全裁掉。

更细的品牌文字真实性、附件数量和微小印刷细节，仍需要真实来源和专门审核，不能仅靠普通 UI 截图差异自动判定。

# 十、无障碍审查必须进入 CI

建议正式以 **WCAG 2.2 AA** 为项目目标。

包括：

- 键盘操作。
- 焦点可见性。
- 屏幕阅读器语义。
- 表单 Label。
- 错误提示。
- 文本颜色对比度。
- 交互目标尺寸。
- 弹窗焦点管理。
- 响应式放大。
- Reduced Motion。

WCAG 2.2 的完整规范由 W3C 发布。

### Storybook + axe-core

Storybook 官方提供基于 axe-core 的无障碍检查插件，并支持通过 Vitest 将相关错误纳入 CI。

但是，自动化无障碍工具只能覆盖部分问题。

因此需要补充关键组件的真实键盘交互测试：

| 组件 | 必测行为 |
|---|---|
| Dialog | 打开、焦点管理、关闭 |
| Select | 键盘选择 |
| Combobox | 搜索、导航、选中 |
| Dropdown | 键盘导航、Escape |
| Form | 错误关联与焦点定位 |
| Page Builder | 不依赖鼠标也能调整组件 |
| Mobile Menu | 打开、关闭、焦点恢复 |

**Page Builder 尤其不能只允许鼠标拖拽。**

至少需要提供按钮或键盘操作来移动组件顺序。

# 十一、性能检查也必须进入前端 CI

OpenSite Commerce 的用户可能有数万款商品。

但高 SKU 数量主要应由后端查询、索引和分页承载。

前端需要重点控制：

- 首屏 JavaScript。
- 图片大小。
- CSS 体积。
- DOM 节点数。
- Hydration 数量。
- 大表格渲染。
- 页面布局偏移。
- 第三方脚本数量。

## 推荐性能检查策略

| 项目 | 检查方式 |
|---|---|
| JS Bundle | 构建产物大小 |
| CSS Bundle | 构建产物大小 |
| 图片传输 | Lighthouse / Network |
| DOM Size | Lighthouse |
| 页面性能 | Lighthouse CI |
| 首屏渲染 | LCP |
| 布局稳定性 | CLS |
| 用户交互 | E2E + 实际运行指标 |
| 后台大表格 | 固定数据集性能测试 |

Lighthouse CI 可以根据资源大小、性能审计结果和自定义阈值返回错误状态，也支持纯本地的收集与断言流程，不要求使用外部付费平台。

### 不建议第一天就使用不现实的性能门槛

例如所有页面必须 Lighthouse 100 分。

这种门槛容易受到 CI 硬件波动、测试环境和外部资源影响。

建议先建立基线，再确定：

**硬门槛：**

- 不能引入未授权的大型第三方脚本。
- 不能出现明显的图片无尺寸布局偏移。
- 不能意外将整个后台 React 包加载到 Storefront。
- 不能出现严重资源大小回归。
- 不允许动态主题引入任意外部脚本。

**逐步收紧的性能门槛：**

- LCP。
- CLS。
- JS 资源预算。
- 图片传输预算。
- DOM 节点预算。

INP 更适合结合真实用户交互数据评估，不能把一次 Lighthouse 实验室测试当作完整的实际用户 INP 结果。

# 十二、两套视觉质量流水线：GitHub CI 与网站发布检查

这里有一个前几轮没有充分区分的问题。

OpenSite Commerce 既是一个开源软件项目，又是一个允许商家通过 API 随时修改网站的平台。

因此，视觉审查必须有**两套不同的执行机制**。

## 12.1 第一套：GitHub 软件开发 CI

负责检查开发者修改的：

- React Admin。
- Astro Storefront。
- OpenSite UI。
- Component SDK。
- 官方主题。
- 官方行业模板。
- 组件渲染实现。

开发者提交 PR 时执行。

```text
Code PR
   ↓
Build
   ↓
Component Tests
   ↓
Accessibility
   ↓
Visual Regression
   ↓
Responsive Tests
   ↓
E2E
   ↓
Independent Review
   ↓
Merge
```

### 第二套：商家网站发布质量检查

假设某商家通过 Agent 修改了自己的网站。

这种修改发生在 PostgreSQL 的 PageDocument 草稿中，并没有修改 GitHub 仓库代码。

**不应该每次用户修改 Banner，就启动一次 GitHub Actions。**

正确流程：

```text
商家编辑页面
     │
     ▼
保存 Site Draft
     │
     ▼
Schema Validation
     │
     ▼
Component Validation
     │
     ▼
Responsive / Accessibility Checks
     │
     ▼
Astro Preview
     │
     ▼
Site Readiness Check
     │
     ▼
用户审核
     │
     ▼
Site Release
```

这套检查由 Go API、Astro Renderer 和后台任务执行。

对于不同大小的站点，可以设置不同的检查预算。

例如：

- 简单文案修改：快速 Schema 与内容检查。
- 修改首页布局：增加真实页面预览和响应式检查。
- 更换主题：增加跨页面视觉验证。
- 安装新的组件代码：必须先经过软件部署和组件兼容测试。

用户网站的视觉检查记录应该与对应的 Site Draft 和 Release 关联。

这样可以追溯每次发布时的实际页面状态。

**GitHub CI 保证软件代码质量；Site Publication QA 保证商家配置的网站能够安全发布。**

两者不能互相替代。

# 十三、最终 CI 架构

考虑到你希望多编码代理并行开发，又不希望每个 PR 都启动几十个 Job，我建议把 UI 质量检查整合进已有的分层 CI。

## 13.1 建议的工作流

```text
Pull Request
     │
     ▼
Impact Analysis
     │
     ├── API / Contract
     │
     ├── Go / PostgreSQL
     │
     ├── React / TypeScript
     │
     ├── Astro Build
     │
     ├── UI Quality
     │     ├── Storybook Tests
     │     ├── Accessibility
     │     ├── Visual Regression
     │     └── Responsive Checks
     │
     ├── E2E / Browser
     │
     └── Performance / Security
              │
              ▼
          ci-required
              │
              ▼
      independent-review
              │
              ▼
          Merge
```

## 13.2 Job 设计

| Job | 核心内容 | 触发条件 |
|---|---|---|
| impact | 计算受影响模块 | 所有 PR |
| contracts | OpenAPI、Schema、组件契约 | 契约变化 |
| backend-db | Go、PostgreSQL、RLS、sqlc | 后端或 DB 变化 |
| frontend-static | TS、Lint、React/Astro Build | 前端变化 |
| ui-quality | Storybook、a11y、视觉截图、响应式 | UI 变化 |
| e2e | 用户操作与跨模块流程 | 关键功能变化 |
| performance-security | 资源预算与安全检查 | 高影响变更 |
| ci-required | 验证所有必要结果 | 所有 PR |

初期尽量把实际并发控制在 4–6 个 Job 左右。

`ci-required` 是唯一的综合 CI 必需状态。

独立审核状态另外管理。

### 对 UI 的特殊规则

当修改以下目录：

```text
packages/ui/
packages/design-tokens/
apps/admin/src/features/
apps/storefront/src/modules/
themes/
```

必须至少评估是否需要运行 UI Quality。

其中：

- 修改公共 Token：影响所有相关组件。
- 修改 UI Primitive：影响所有引用它的业务组件。
- 修改商品卡片：影响商品列表、推荐和首页商品网格。
- 修改页面组件 Schema：影响 Page Builder、Astro 和发布兼容性。
- 修改官方主题：影响相应模板的所有关键页面。

不能仅凭改动文件很少，就跳过下游视觉回归。

### 视觉测试失败的产物

CI 应保存：

```text
visual-report/
├── screenshots/
│   ├── expected/
│   ├── actual/
│   └── diff/
├── accessibility/
├── responsive/
├── performance/
├── playwright-traces/
└── report.html
```

测试报告应明确指出：

- 哪个页面失败。
- 哪个视口失败。
- 哪个组件受影响。
- 实际差异是什么。
- 是否属于预期视觉修改。
- 谁批准了新的基线。

不需要把所有截图永久保存。

只需将经过审核的基线纳入版本控制，并为失败报告设置适当的 Artifact 保留期。

### 不允许自动接受视觉基线

这是明确的合并规则。

如果某个 PR 修改了组件布局，截图发生差异：

**编码代理不能简单运行 `--update-snapshots` 后直接把 CI 变绿。**

必须提交新旧差异供独立审查。

只有确认修改符合视觉设计和功能要求后，才更新 Golden Baseline。

否则视觉回归测试将失去意义。

# 十六、实施顺序：先建 UI 基础，再让业务模块并行

我建议把前端工作分成四个小阶段。

| 阶段 | 交付目标 | 主要内容 |
|---|---|---|
| UI-01 | Design System Foundation | Base UI、shadcn/ui、Tokens、基础组件 |
| UI-02 | Component Quality Pipeline | Storybook、Vitest、Playwright、axe、视觉 CI |
| UI-03 | Admin + Storefront Reference | 商品列表、商品详情、企业页面 |
| UI-04 | Page Builder Integration | 组件配置、真实 Astro 预览、发布检查 |

### UI-01：组件库验证

先实现五个具有代表性的组件：

**Button、Dialog、Select、DataTable、FormField。**

它们能够覆盖基础视觉、表单、焦点管理和数据交互。

建议用 Base UI 作为默认方案，再用 Radix 或 React Aria 做有限对照。

比较指标：

- API 使用复杂度。

# 十八、最终审查结论

整个 OpenSite Commerce 的目标架构现在可以整理成五个相互协作的系统。

| 系统 | 负责什么 |
|---|---|
| **Business Core** | Go、PostgreSQL、商品、企业、客户、价格、订单 |
| **Admin Platform** | React、OpenSite UI、后台各业务模块 |
| **Storefront Engine** | Astro、主题、组件、SEO、B2B/B2C 展示 |
| **Automation Platform** | OpenAPI、Agent、批量任务、发布审批 |
| **Quality Platform** | 组件测试、视觉审查、无障碍、性能、CI、独立审核 |

其中，**Quality Platform 应该成为正式的横向工程基础设施**，而不是在开发完成后补充几条截图测试。

同时应坚持三个边界：

**第一，UI 组件库不决定业务架构。** Base UI、shadcn/ui 等为我们提供界面实现，商品、订单和页面发布规则仍由 Go 服务负责。

**第二，视觉正确性不能等同于截图相似。** 必须联合检查组件行为、响应式、文字可读性、媒体引用、无障碍和真实业务流程。

**第三，所有 UI 代码修改都必须进入质量门禁。** 无论由 Codex、其他编码代理还是人工开发，提交 PR 后都遵循相同的视觉测试和独立审核标准。

### 目前最应该执行的工作

我建议把下一轮实际工程任务定为：

**PR-UI-001：OpenSite Design System + 组件库选型 POC + Visual CI Foundation。**

这份 PR 不需要开发全部后台功能，只需证明：

- Base UI 与官方 shadcn/ui 可以建立统一组件库。
- Design Tokens 能够同时用于 React Admin 和 Astro Storefront。
- Storybook 能够测试组件状态。
- Playwright 能够在固定环境中产生、比较和审查截图。
- 无障碍错误能够导致 CI 失败。
- 非预期 UI 视觉变化无法绕过审查直接合并。
- 视觉测试报告能够作为 GitHub Artifact 保存。
- 所有工具均可使用免费开源方案，不强制购买商业视觉测试服务。

**需要同时强调：V0.9 是架构与选型审查，尚未实际安装组件、创建该 PR 或运行视觉 CI。** 此前 PR-01 的 PostgreSQL 18 实库验收也仍未完成，不能因为新增 UI 规划而将其视为已通过。

我的总体建议是：**正式确立 Base UI + shadcn/ui + Tailwind/Design Tokens 作为前端设计基线，Storybook + Playwright + axe-core + Lighthouse CI 作为质量基础，再以模块化开发、独立视觉审核和统一 CI 门禁推进整个开源项目。**
