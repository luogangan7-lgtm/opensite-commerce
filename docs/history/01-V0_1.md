# OpenSite Commerce — 开源独立站与智能建站平台架构设计

**版本：Architecture V0.1**  
**设计日期：2026 年 10 月 11 日**  
**项目定位：开源、自部署、API First、Agent Native、支持 B2B/B2C 的独立站系统**

## 一、总体设计结论

我建议把这个项目定位为：

> **一个以商品交易、企业展示和内容管理为基础，以组件化建站为界面，以 API 和 AI Agent 为操作入口的开源独立站平台。**

它不是简单的 Shopify 替代品，也不应该只是一个包含商品和购物车的电商后台。

它应该能够让不同用户构建：

- **B2B 外贸独立站**：企业介绍、产品目录、批发询盘、MOQ、阶梯报价、资质展示、WhatsApp 联系。
- **B2C 品牌商城**：商品零售、购物车、支付、物流、优惠券、订单、会员。
- **B2B+B2C 混合站**：普通消费者看到零售价，批发客户登录后看到对应的采购价。
- **企业展示官网**：企业信息、业务介绍、工厂展示、案例、新闻、博客、联系方式。
- **行业垂直商城**：服装、鞋包、香薰、家具、电子产品、工业配件等。
- **多语言国际独立站**：不同国家、语言、币种、产品目录及价格规则。

这些能力应共享同一套基础架构，而不是为每种网站分别开发一套系统。

### 1.1 六项核心设计原则

| 设计原则 | 实际要求 |
|---|---|
| API First | 后台所有核心业务操作均通过标准 API 实现 |
| Agent Native | AI Agent 能在授权范围内查询、创建、修改和批量管理数据 |
| Component First | 网站通过可组合、可配置、可复用的组件构建 |
| Commerce First | 商品、价格、库存、订单、支付等使用可靠的电商领域模型 |
| Self-host First | 用户能够在自己的服务器安装、升级、备份和迁移 |
| Lightweight First | 尽量减少服务数量、内存占用及不必要的基础设施 |

**最重要的设计决定：将业务数据、网站内容、页面模板、主题样式和前端渲染完全解耦。**

例如，用户更换网站主题时，商品、博客、企业资料、订单不应发生任何改变。

AI Agent 修改页面时，也不应直接改动前端源码，而应通过标准 API 修改经过验证的页面配置。

这样才能形成真正可维护、可自动化的建站平台。

## 二、技术栈选择

综合运行性能、开发效率、开源生态、自部署和维护成本，我建议采用以下组合。

| 层级 | 推荐技术 | 选择原因 |
|---|---|---|
| 核心后端 | **Go** | 编译型、并发模型简单、内存开销较低、部署方便 |
| 数据库 | **PostgreSQL 18** | 事务、关系数据、JSONB、索引、数据完整性 |
| 数据访问 | pgx + sqlc | SQL 显式、类型安全、避免复杂 ORM |
| 后台任务 | River | 基于 PostgreSQL，无须单独部署消息队列 |
| API | REST + OpenAPI | 适合后台、第三方应用和 Agent |
| 管理后台 | React + TypeScript + Vite | 组件生态成熟，适合复杂表单与可视化编辑 |
| 网站前端 | **Astro + TypeScript** | SSR/静态混合渲染、组件化、减少不必要的前端 JS |
| 交互组件 | React Islands | 用于购物车、筛选、用户中心等动态区域 |
| UI 组件 | Tailwind CSS + 自有组件库 | 样式令牌、主题扩展和响应式布局 |
| 对象存储 | S3 API 兼容存储 | 存储大量商品图片、视频和企业资料 |
| 图片处理 | imgproxy | 图片尺寸、格式转换和缩略图处理 |
| 缓存 | PostgreSQL/HTTP 缓存起步，Valkey 可选 | 避免初期部署过多服务 |
| 搜索 | PostgreSQL 起步，独立搜索服务可选 | 按商品规模和检索需求扩展 |
| 部署 | Docker Compose + Caddy | 便于个人和中小企业自行部署 |
| 扩展机制 | 插件接口 + Webhook + SDK | 支持支付、物流、ERP、AI 和第三方服务 |

### 为什么优先选择 Go，而不是 Rust？

Rust 在许多计算密集场景中可以取得更高的性能，但开发和维护复杂业务系统的成本通常也更高。

对于电商平台，主要瓶颈往往来自数据库查询、商品搜索、图片传输、缓存失效和外部支付接口，并不单纯由编程语言决定。

Go 的优势是：

1. 单个编译产物即可部署核心后端。
2. 内置网络和并发能力适合 API 服务。
3. PostgreSQL、任务队列、对象存储等生态成熟。
4. 更适合快速迭代大量电商业务规则。
5. 有利于 AI 编码代理理解和维护模块化项目。

截至 2026 年 10 月，Go 官方已经发布 1.27 系列，可将受支持的稳定版本作为开发基线。

### 为什么网站前端选择 Astro？

你的平台包含大量偏展示型的页面：

- 商品详情页
- 企业介绍
- 工厂展示
- 博客文章
- 品牌故事
- 营销落地页

这些页面不需要全部运行复杂的浏览器端 JavaScript。

Astro 的 Islands 架构可以将大部分内容直接渲染为 HTML，仅在购物车、商品筛选等需要交互的区域加载客户端组件。它也支持服务器按需渲染，不要求每次修改商品都重新构建整个网站。

**因此，建议采用 Astro 负责店铺展示，React 负责管理后台，Go 负责业务处理。**

不过，这是一项工程选型，而不是认定 Astro 在所有负载下都比 Next.js 快。正式开发前仍应通过原型测试多主题动态渲染、缓存和交互复杂度。

## 三、整体系统架构

### 3.1 推荐架构：模块化单体 + 可插拔服务

不建议项目一开始就采用几十个微服务。

电商系统的核心操作具有很强的事务关联性。例如：

用户提交订单 → 校验价格 → 校验库存 → 预留库存 → 创建订单 → 发起支付。

如果一开始拆成商品服务、订单服务、库存服务、支付服务，再使用分布式事务协调，会大幅增加开发、测试和部署难度。

更合适的结构是：

```text
                    ┌─────────────────────────────┐
                    │        网站访问者            │
                    │  B2B买家 / B2C消费者 / 企业客户 │
                    └──────────────┬──────────────┘
                                   │
                    ┌──────────────▼──────────────┐
                    │   CDN / Caddy / HTTPS       │
                    └──────────────┬──────────────┘
                                   │
               ┌───────────────────┼─────────────────┐
               │                   │                 │
        ┌──────▼───────┐   ┌───────▼──────┐  ┌───────▼──────┐
        │ Astro 网站   │   │ React 管理台│  │ 外部 API 客户端│
        │ 模板渲染引擎 │   │ 可视化建站器│  │ Agent/ERP/PIM │
        └──────┬───────┘   └───────┬──────┘  └───────┬──────┘
               │                   │                 │
               └───────────────────┼─────────────────┘
                                   │
                      ┌────────────▼───────────┐
                      │       Go API          │
                      │  Auth / RBAC / OpenAPI│
                      └────────────┬───────────┘
                                   │
        ┌──────────────────────────▼─────────────────────┐
        │               Go 模块化业务内核                │
        │                                                │
        │  商品/PIM       企业资料      CMS/博客         │
        │  分类/属性      询盘/CRM       主题/模板         │
        │  B2B报价        B2C交易       内容发布         │
        │  客户/会员      库存/订单      支付/物流         │
        │  多语言         SEO/营销       Agent/Bulk       │
        └───────────┬───────────────────┬────────────────┘
                    │                   │
         ┌──────────▼─────────┐  ┌──────▼────────────┐
         │  PostgreSQL 18    │  │   媒体管理模块     │
         │  业务数据/事务     │  │ 上传/校验/转换     │
         │  River后台任务     │  │ 图片/视频处理      │
         └──────────┬─────────┘  └──────┬────────────┘
                    │                   │
            ┌───────▼────────┐  ┌───────▼───────────┐
            │ 可选搜索/缓存  │  │ S3 兼容对象存储  │
            │ Meilisearch    │  │ 商品图片/视频     │
            │ Valkey         │  │ 企业资料/博客     │
            └────────────────┘  └───────────────────┘
```

注意，图中的 API 代表统一的业务能力，不意味着所有接口都对互联网公开。

管理操作、公开查询、Agent 操作应分别执行身份校验和授权。

### 3.2 为什么采用模块化单体？

系统从代码层面划分模块，但初期不要求每个模块独立运行。

例如：

```text
opensite/
├── apps/
│   ├── api/                  Go API 服务
│   ├── worker/               后台任务进程
│   ├── admin/                React 管理后台
│   └── storefront/           Astro 网站渲染器
│
├── internal/
│   ├── identity/             身份与权限
│   ├── tenant/               安装实例与站点
│   ├── company/              企业资料
│   ├── catalog/              商品与分类
│   ├── pricing/              价格规则
│   ├── inventory/            库存
│   ├── commerce/             购物车、订单
│   ├── payment/              支付抽象
│   ├── fulfillment/          物流和售后
│   ├── customer/             客户与会员
│   ├── inquiry/              询盘与报价
│   ├── cms/                  页面与博客
│   ├── media/                图片与视频
│   ├── theme/                主题和模板
│   ├── localization/         多语言和地区
│   ├── seo/                  SEO
│   ├── automation/           Agent和批量操作
│   └── integration/          外部系统集成
│
├── packages/
│   ├── api-client/           TypeScript SDK
│   ├── theme-sdk/            主题开发SDK
│   ├── component-registry/   标准组件定义
│   └── plugin-sdk/           插件接口定义
│
├── themes/
│   ├── corporate/            企业官网主题
│   ├── wholesale/            B2B批发主题
│   ├── retail/               B2C商城主题
│   └── fashion/              服装行业主题
│
├── api/
│   └── openapi/              API契约
│
├── migrations/               数据库迁移
├── deploy/                   Compose和服务器配置
└── docs/                     架构和开发文档
```

这是**建议的目标目录组织**，不是现有仓库结构。

Go 后端可以用同一套代码编译 API 和 Worker 两个入口。小规模部署也可将后台任务运行在同一进程中，同时限制任务并发，避免图片处理抢占订单接口资源。

River 官方支持将 PostgreSQL 事务与后台任务入队绑定，可以避免业务事务回滚而任务已经执行的问题。([River 文档](https://riverqueue.com/docs/unique-jobs?utm_source=chatgpt.com))

### 3.3 必须区分三种业务模式

这里有一个容易被忽略的设计问题。

**B2B/B2C、多个店铺、多个商家入驻，并不是同一个概念。**

| 概念 | 含义 | 架构处理 |
|---|---|---|
| B2B/B2C | 交易和客户类型不同 | 共用商品内核，使用不同交易规则 |
| 多站点 | 同一企业运营多个官网或品牌站 | 使用 Site、Channel、Domain 模型 |
| 多租户 | 一个部署服务多个独立企业 | 使用 Tenant 和数据隔离 |
| Marketplace | 多个卖家入驻同一交易平台 | 涉及平台结算、商户账本、平台责任，另行设计 |

建议从第一版开始支持**单实例、单企业、多站点**，同时在数据库中保留 `tenant_id`。

后续可以扩展为多租户托管平台，但没有必要立即实现 Marketplace。

这样既保持自部署简单，也为未来商业化托管留下空间。

你已经提到了商品、企业信息、博客、视频、模板和 Agent。

但一个可用于真实经营的网站，还需要覆盖采购决策、交易、信任、内容、运营和数据管理。

| B2B 询盘 | 询价单、报价单、样品申请 | 必需 | 可选 |
| B2C 购物车 | 加购、结算、订单 | 可选 | 必需 |
| 客户管理 | 账户、客户组、企业采购账户 | 必需 | 必需 |
| 库存管理 | 多仓、预留库存、库存变更 | 推荐 | 必需 |
| 支付中心 | 支付渠道、退款、支付状态 | 可选 | 必需 |
| 物流中心 | 配送方式、运费、发货、追踪 | 推荐 | 必需 |
| CMS 内容 | 页面、博客、新闻、案例 | 必需 | 必需 |
| 可视化建站 | 主题、组件、页面模板 | 必需 | 必需 |
| 媒体中心 | 图片、视频、文件及素材引用 | 必需 | 必需 |
| SEO | URL、Meta、站点地图、结构化数据 | 必需 | 必需 |
| 多语言 | 站点语言、翻译、语言回退 | 推荐 | 推荐 |
| 多币种 | 市场定价、币种、地区规则 | 推荐 | 推荐 |
| 营销 | 优惠券、活动、订阅、转化分析 | 推荐 | 推荐 |

其中有三个模块需要特别深入设计：

**第一，PIM（Product Information Management）。** 它不仅是商品录入表单，还负责商品事实、变体、属性、素材、版本和批量导入。

**第二，CMS + Theme Engine。** 它决定网站如何展示这些内容，使网站界面不依赖固定页面源码。

**第三，API + Agent Execution。** 它决定系统是否能够被自动化控制，而不仅仅由人点击后台完成操作。

这三部分是该项目区别于普通开源商城的重要能力。

## 五、数据库架构设计

### 5.1 数据库必须围绕业务实体设计

### 5.3 商品模型：SPU 与 SKU 必须分离

这对你提到的服装行业尤其重要。

例如：

一款衬衫：

- 颜色：黑、白、蓝、灰、红、绿
- 尺码：XS、S、M、L、XL

这是：

**1 个商品 SPU，30 个 SKU。**

假设一个服装商家有：

- 10,000 个款式；
- 每款 6 种颜色；
- 每种颜色 5 个尺码。

最终是：

**10,000 SPU × 6 × 5 = 300,000 SKU。**

因此不能把每一种颜色、尺码都当成一份完整商品记录，重复存储标题、详情、视频和大量图片。

建议的数据模型：

```text
Product（商品）
  id
  tenant_id
  product_type
  brand_id
  default_title
  description
  status
  ...

ProductVariant（SKU）
  id
  product_id
  sku
  barcode
  option_combination
  weight
  dimensions
  status
  ...

ProductOption
  product_id
  name: Color / Size

ProductOptionValue
  option_id
  value: Black / White / XL

ProductMedia
  product_id
  variant_id (nullable)
  media_asset_id
  role
  sort_order
```

SKU 的库存、价格和部分图片是独立的。

标题、品牌介绍、基本详情、尺码说明等能够共享的数据，只存储或维护一份。

图片通过引用关联商品，而不是重复保存文件。

### 5.4 支持行业专属属性模板

商品属性不能只有一个无限扩展的 JSON 字段。

建议引入 **Attribute Schema**。

| 行业 | 典型属性 |
|---|---|
| 服装 | 尺码、颜色、材质、版型、季节、洗护说明 |
| 鞋类 | 鞋码、鞋面材质、鞋底材质、跟高 |
| 香薰 | 容量、香型、扩香方式、包装规格、起订量 |
| 家具 | 尺寸、材质、颜色、承重、安装方式 |
| 电子产品 | 型号、功率、电压、接口、兼容性 |
| 工业配件 | 材质、规格、公差、标准、适配型号 |

属性模板需要支持：

- 文本、数字、布尔值、枚举、多选、日期。
- 单位及单位换算。
- 必填条件和取值范围。
- 是否允许作为 SKU 选项。
- 是否用于商品筛选。
- 是否出现在商品详情页。
- 是否允许翻译。
- 是否允许通过 Agent 修改。

高频筛选、唯一性约束和报价计算需要使用明确类型的数据结构；行业长尾属性可以使用受 Schema 约束的 JSONB。

这样既能支持服装，也能支持工业产品和日用品，而不需要每增加一个类目就修改核心代码。

### 5.5 定价必须是独立领域

不建议在商品表里仅放一个 `price`。

更完整的价格规则应考虑：

```text
基础价格
    │
    ├── 销售渠道
    ├── 国家/市场
    ├── 币种
    ├── 客户类型
    ├── 客户价格表
    ├── 采购数量
    ├── 生效时间
    └── 促销条件
```

例如同一个 SKU：

| 客户 | 数量 | 单价 |
|---|---:|---:|
| 普通消费者 | 1 | ¥89 |
| 普通批发客户 | 24 | ¥62 |
| 普通批发客户 | 100 | ¥58 |
| 合同客户 A | 100 | ¥55 |

这些数字仅用于说明定价模型。

价格引擎需要明确优先级、适用范围、舍入规则、税前税后口径及冲突处理，而不是简单找到最低价格。

同样重要的是：**订单成交后必须保存价格快照**。未来修改商品价格，不得改变历史订单金额。

## 六、商品与媒体系统：面向数万款商品设计

这是整个项目最需要重视的性能领域。

### 6.1 商品与媒体分离

PostgreSQL 不应该直接承担海量商品图片和视频的主要存储任务。

建议采用：

```text
商品数据库
   │
   └── media_asset_id
             │
             ▼
       媒体元数据
             │
             ├── 文件哈希
             ├── MIME类型
             ├── 原始尺寸
             ├── 存储路径
             ├── 图片版本
             ├── 视频元数据
             └── 引用关系
                      │
                      ▼
                 对象存储
```

一个图片文件可以被多个商品、页面和博客引用。

例如企业上传一张真实工厂照片，既可以放在企业介绍中，也可以放在博客和联系页面中，不需要保存三份文件。

### 6.2 图片管理

每个图片资产建议具备：

| 字段 | 功能 |
|---|---|
| asset_id | 唯一标识 |
| tenant_id | 所属企业 |
| storage_key | 对象存储路径 |
| sha256 | 文件内容校验与去重 |
| width / height | 图片尺寸 |
| mime_type | 文件类型 |
| original_filename | 原始文件名 |
| alt_text | 图片替代文本 |
| usage_count | 引用统计 |
| processing_status | 处理状态 |
| created_at | 上传时间 |

商品图片还需要区分：

- 主图
- 商品相册
- 颜色对应图片
- 详情页图片
- 尺码表
- 包装图片
- 证书或说明图片

这些属于**业务用途**，不是文件格式。

### 6.3 自动生成适配版本

用户上传一张 4000×4000 的高清商品图后，不应让手机端直接下载整个原图。

系统可以根据前端请求生成：

- 缩略图
- 列表图
- 商品详情图
- 高清放大图
- WebP/AVIF 等格式

使用 imgproxy 进行按需转换，并利用 CDN 缓存结果。imgproxy 的开源版本采用 Apache-2.0 许可证。([imgproxy GitHub](https://github.com/imgproxy/imgproxy))

需要增加图片处理防护，限制输入文件大小、解码像素量、处理时间和并发数量，避免异常图片消耗服务器资源。

### 6.4 视频管理

建议支持：

- 商品展示视频
- 产品使用视频
- 企业宣传视频
- 工厂视频
- 博客嵌入视频
- 视频封面
- 外部视频链接

上传采用分片或 S3 Multipart Upload。

视频转码通过异步任务执行，不能阻塞普通 API 请求。

初期可以保存原视频并生成必要的封面；达到实际播放规模后，再增加多码率转码和 HLS。

没有必要从第一版开始搭建完整视频流媒体平台。

### 6.5 实际存储规模

以服装行业为例：

假设某商家拥有 10,000 款商品，每款 8 张原图，平均每张 2MB。

仅原始商品图片就需要约 **160GB**。

如果每款还上传一段平均 20MB 的视频，则额外增加约 **200GB**。

这还没有包括缩略图、不同颜色的图片、备份及其他企业资料。

因此，必须从第一版开始：

1. 将文件存储与业务数据库分离。
2. 支持 S3 API 兼容存储。
3. 支持按需图片处理和缓存。
4. 支持文件去重与引用计数。
5. 支持媒体生命周期及垃圾回收。
6. 支持存储容量统计和配额。
7. 支持媒体迁移和对象完整性校验。

这里有一个 2026 年的技术变化值得特别指出：

**MinIO 原 GitHub 仓库已于 2026 年 4 月 25 日归档。** 因此，不建议新项目直接依赖其已归档社区仓库作为长期维护的默认对象存储实现。([MinIO GitHub](https://github.com/minio/minio))

可以评估：

- [RustFS](https://github.com/rustfs/rustfs)：Rust 实现的 S3 兼容对象存储，Apache-2.0。
- [SeaweedFS](https://github.com/seaweedfs/seaweedfs)：支持 S3 接口，Apache-2.0，适合大量文件存储。
- 外部 S3 兼容服务：用户自行配置。

RustFS 官方已于 2026 年 9 月宣布 1.0 GA，但其生产成熟度仍应结合你实际使用的 S3 功能进行兼容性测试。([RustFS 官方公告](https://rustfs.com/blog/announcing-rustfs-1-0-0-ga/))

**架构应依赖 S3 接口，而不是绑定任何一家存储产品。**

## 七、模板化建站系统：项目的核心差异化能力

这是我认为最值得投入设计的模块。

网站不应该只是提供几套预先写好的 HTML 模板。

它需要形成一个完整的：

**Theme Engine + Component Registry + Page Builder + Content Binding**

系统。

### 7.1 将模板拆成四层

| 层级 | 负责内容 |
|---|---|
| Theme | 网站整体视觉风格 |
| Design Tokens | 颜色、字体、间距、圆角等设计参数 |
| Components | 图片、文字、商品卡片、导航等组件 |
| Page Templates | 首页、商品页、博客页等页面结构 |

假设一个用户选择了服装主题。

主题初始包含：

```text
Fashion Theme
 │
 ├── Design Tokens
 │    ├── Brand Colors
 │    ├── Typography
 │    ├── Spacing
 │    └── Layout
 │
 ├── Global Components
 │    ├── Header
 │    ├── Navigation
 │    ├── Footer
 │    └── Mobile Menu
 │
 ├── Page Templates
 │    ├── Home
 │    ├── Product Listing
 │    ├── Product Detail
 │    ├── Blog Listing
 │    ├── Blog Article
 │    └── Contact
 │
 └── Commerce Components
      ├── Product Card
      ├── Product Gallery
      ├── Variant Selector
      ├── Size Selector
      └── Shopping Cart
```

更换主题时，业务数据保持不变。

用户也可以只替换首页 Banner、商品卡片或导航组件。

### 7.2 组件必须可以通过 API 管理

例如某个首页：

```json
{
  "schema_version": 1,
  "template": "home",
  "theme": "fashion",
  "blocks": [
    {
      "id": "hero-01",
      "type": "hero-banner",
      "props": {
        "title": "2026 Autumn Collection",
        "layout": "split",
        "image_id": "asset_123"
      }
    },
    {
      "id": "products-01",
      "type": "product-grid",
      "props": {
        "title": "New Arrivals",
        "columns": 4
      },
      "data_source": {
        "type": "collection",
        "collection_id": "new-arrivals",
        "limit": 8
      }
    }
  ]
}
```

这份 JSON 不应该直接存放商品查询结果。

它只保存：

- 页面使用什么组件。
- 组件的参数。
- 组件的数据来源。
- 排列顺序。
- 页面版本。

真正的商品数据，在渲染时从商品 API 获取。

因此，当用户新增商品并将它放入 `new-arrivals` 集合，首页商品区域可以自动更新。

不需要重新修改页面代码。

### 7.3 Component Registry

所有组件需要注册到统一组件库。

例如：

```text
hero-banner
product-grid
product-gallery
image-gallery
text-section
rich-text
video-player
company-profile
contact-form
whatsapp-button
blog-grid
testimonials
faq
category-navigation
price-table
quote-request
```

每个组件至少定义：

```text
Component Definition
 ├── type
 ├── version
 ├── display_name
 ├── prop_schema
 ├── data_source_schema
 ├── default_props
 ├── supported_slots
 ├── responsive_rules
 └── renderer
```

组件属性使用 JSON Schema 验证。

这样管理后台、API 和 Agent 都遵守相同的组件契约。

**关键限制：普通用户和 Agent 可以通过 API 修改组件配置，但不能通过上传任意 JavaScript 来修改服务器执行逻辑。**

自定义代码组件应属于有权限的开发者扩展机制，与普通内容编辑隔离。

### 7.4 实现可视化页面编辑器

管理后台需要具有以下能力：

| 功能 | 说明 |
|---|---|
| 页面预览 | 修改时立即看到效果 |
| 组件选择 | 从组件库选择模块 |
| 拖拽排序 | 调整组件顺序 |
| 属性编辑 | 修改文字、图片、布局 |
| 数据绑定 | 选择商品分类、集合等 |
| 响应式配置 | 桌面端和移动端适配 |
| 草稿版本 | 修改但暂不发布 |
| 发布管理 | 发布指定版本 |
| 版本回滚 | 恢复以前的页面 |
| 主题切换 | 更换网站整体视觉 |
| API 编辑 | 无需进入页面编辑器即可修改 |

### 7.5 模板继承非常重要

例如一个服装网站有 10,000 款商品。

绝不能为每款商品创建完全独立的页面结构。

应采用：

```text
全站商品详情模板
         │
         ├── 上衣分类模板
         │      └── 个别商品的可选覆盖
         │
         ├── 裤装分类模板
         │
         └── 鞋类分类模板
```

默认模板用于大多数商品。

只有特殊商品才需要覆盖某些组件或配置。

这样商家修改商品详情页模板，一次操作即可影响数千个商品页面。

这是真正有价值的**规模化模板能力**。

### 7.6 模板版本与内容版本分离

推荐分别管理：

- Theme Version
- Component Version
- Page Version
- Content Revision

例如：

企业修改商品名称，不应该升级主题版本。

开发者更新商品卡片组件，也不应该改动所有商品记录。

主题版本升级需要兼容性检查及配置迁移能力。

用户通过 API 编辑页面后，系统应先生成草稿、验证组件属性和数据来源，再进行发布。已发布版本不可直接被未验证的草稿覆盖。

## 八、API 架构：所有功能均可编程管理

### 8.1 API 统一规范

推荐：

**REST + OpenAPI 3.1 + JSON**

OpenAPI 可以作为服务端、管理后台、SDK 和 Agent 工具定义的共同契约。([OpenAPI 官方规范](https://spec.openapis.org/oas/v3.1))

采用三组逻辑接口：

| 接口类型 | 用途 |
|---|---|
| Public API | 网站展示、商品查询、博客读取 |
| Admin API | 后台管理及受授权的数据修改 |
| Automation API | Agent、ERP、批量导入、外部系统操作 |

不需要三套独立业务实现。

它们共享同一个业务服务层，区别主要在授权、资源过滤及操作限制。

### 8.2 主要 API 规划

**商品与分类**

```http
GET    /api/v1/products
POST   /api/v1/products
GET    /api/v1/products/{id}
PATCH  /api/v1/products/{id}
DELETE /api/v1/products/{id}

GET    /api/v1/products/{id}/variants
POST   /api/v1/products/{id}/variants

GET    /api/v1/categories
POST   /api/v1/categories
```

**企业资料**

```http
GET    /api/v1/company
PATCH  /api/v1/company

GET    /api/v1/company/contacts
POST   /api/v1/company/contacts

GET    /api/v1/company/documents
POST   /api/v1/company/documents
```

**博客与网站内容**

```http
GET    /api/v1/posts
POST   /api/v1/posts
PATCH  /api/v1/posts/{id}

GET    /api/v1/pages
POST   /api/v1/pages
PATCH  /api/v1/pages/{id}
```

**主题与模板**

```http
GET    /api/v1/themes
POST   /api/v1/themes/{id}/activate

GET    /api/v1/components
GET    /api/v1/pages/{id}/draft
PATCH  /api/v1/pages/{id}/draft

POST   /api/v1/pages/{id}/preview
POST   /api/v1/pages/{id}/publish
POST   /api/v1/pages/{id}/rollback
```

**媒体**

```http
POST   /api/v1/media/uploads
POST   /api/v1/media/uploads/{id}/complete

GET    /api/v1/media
PATCH  /api/v1/media/{id}
DELETE /api/v1/media/{id}
```

**自动化**

```http
POST   /api/v1/bulk/product-imports
POST   /api/v1/bulk/product-updates

GET    /api/v1/bulk/jobs/{id}
GET    /api/v1/bulk/jobs/{id}/results

POST   /api/v1/bulk/jobs/{id}/validate
POST   /api/v1/bulk/jobs/{id}/commit
```

API 还需要覆盖客户、订单、报价、支付、物流、库存和营销等领域。

上述是建议的路由结构，正式开发时应由 OpenAPI 契约进一步定义请求格式、分页、错误码、权限和状态变化。

### 8.3 API 不只是 CRUD

真实经营系统还需要：

- 分页、排序、过滤、字段选择。
- 批量创建和批量更新。
- 幂等请求。
- 乐观锁与版本冲突检测。
- 异步任务及进度查询。
- Webhook。
- API 访问日志。
- API Key 管理。
- 操作权限范围。
- 数据导入与导出。

例如商品修改需要支持：

```http
PATCH /api/v1/products/{id}
If-Match: "revision-12"
Idempotency-Key: 7c6e...
```

其中：

- `If-Match` 用于避免覆盖其他人的更新。
- `Idempotency-Key` 用于避免网络重试造成重复操作。

批量操作不能简单地让客户端同时发送一万次单条商品修改请求。

正确方法是创建异步批量任务，由后台控制并发、校验数据并分批提交。

### 8.4 删除操作需要区分数据类型

虽然 API 应该支持删除，但不是所有数据都适合直接物理删除。

例如：

- 商品：下架、归档或软删除。
- 博客：撤回发布或归档。
- 媒体：没有其他引用后再清理。
- 订单：取消、退款、关闭，而不是随意删除财务记录。
- 客户个人信息：按隐私请求及适用的数据保留规则进行删除或匿名化。

这样能够同时满足 API 可操作性和交易记录的完整性。

## 九、Agent Native：让 AI 真正管理网站

我建议从第一版就把 Agent 作为正式的系统调用者设计，而不是最后加一个 AI 聊天框。

Agent 应通过经过授权的工具和 API 操作系统。

### 9.1 核心架构

```text
AI Agent
   │
   ▼
MCP Server / API SDK
   │
   ▼
Identity + Scope + Policy
   │
   ▼
Operation Planner
   │
   ▼
Validate / Dry Run
   │
   ├── 查询
   ├── 创建草稿
   ├── 批量更新
   ├── 页面修改
   └── 内容发布申请
   │
   ▼
Approval / Commit
   │
   ▼
Go Business Services
   │
   ▼
PostgreSQL + River Jobs
   │
   ▼
Audit + Result Report
```

2026 年 7 月发布的 MCP 规范支持标准化工具暴露与调用，并明确强调工具调用过程中的授权和人工控制。可以将 MCP 作为适配层，但核心业务规则仍由 Go API 执行。([MCP 官方工具规范](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx))

### 9.2 Agent 工具定义

例如：

| Tool | 功能 |
|---|---|
| `product.search` | 搜索已有商品 |
| `product.get` | 获取完整商品 |
| `product.create_draft` | 创建商品草稿 |
| `product.batch_upsert` | 批量创建或更新 |
| `product.validate` | 检查商品数据 |
| `product.publish` | 发布商品 |
| `media.upload` | 上传素材 |
| `media.bind` | 绑定商品媒体 |
| `company.update` | 更新企业信息 |
| `blog.create_draft` | 创建博客草稿 |
| `page.update_draft` | 修改页面配置 |
| `theme.configure` | 修改主题参数 |
| `catalog.audit` | 发现缺失字段 |
| `job.get_status` | 查看批量任务状态 |

### 9.3 示例：Agent 批量上架 5,000 款服装

用户上传一个 Excel 文件和商品图片目录。

系统处理流程：

**阶段一：解析**

解析 SKU、款号、颜色、尺寸、价格、库存、图片文件名。

识别商品之间的变体关系。

**阶段二：匹配**

自动匹配：

- 商品分类
- 属性模板
- 图片和对应颜色
- 尺码表
- 商品描述
- 已存在的商品与 SKU

**阶段三：数据校验**

检查：

- SKU 是否重复
- 必填属性是否缺失
- 图片是否匹配
- 价格是否有效
- 颜色和尺码组合是否冲突
- 已存在商品是否会被覆盖

**阶段四：差异预览**

例如：

```text
导入任务：5,000 个商品款式

新增商品：4,500
更新商品：300
数据冲突：120
缺失资料：80

新增SKU：135,000
待审核媒体：240

状态：等待确认
```

这是示例输出，不代表系统已有上述能力。

**阶段五：提交**

系统将经过批准的数据按批次写入数据库。

图片异步处理。

搜索索引异步更新。

最后执行发布和缓存失效。

**阶段六：报告**

返回：

- 成功记录
- 失败记录
- 冲突记录
- 修改差异
- 审计记录
- 可恢复版本

这里的重要原则是：**失败的部分可以重试，已经成功的部分不会因为重试而重复创建。**

### 9.4 Agent 操作权限

不能给 Agent 一个拥有全部数据库权限的 Token。

建议至少划分：

| 权限范围 | 示例 |
|---|---|
| Catalog Read | 读取商品 |
| Catalog Write | 修改商品草稿 |
| Catalog Publish | 发布商品 |
| Media Write | 上传和管理媒体 |
| CMS Write | 修改页面与博客草稿 |
| Theme Write | 修改页面布局 |
| Pricing Write | 修改价格 |
| Inventory Write | 修改库存 |
| Orders Read | 查看授权订单 |
| Company Write | 修改企业公开资料 |

修改正式价格、库存、支付设置和敏感企业资料，应设置更严格的授权策略。

Agent 读取商品图片后自动推断属性，也不能把不确定的判断当成事实。例如商品材质、产地、认证和品牌授权必须有可靠来源。

建议所有 AI 补全字段记录来源、置信状态和审查结果。

## 十、企业官网与 CMS 内容体系

这部分不能只做一个“企业介绍”文本框。

### 10.1 企业信息模型

建议覆盖：

| 分类 | 字段 |
|---|---|
| 基本信息 | 企业名称、品牌名称、简介 |
| 注册资料 | 注册号、注册国家或地区、企业类型 |
| 地理位置 | 注册地址、营业地址、展示地址 |
| 联系方式 | 邮箱、电话、WhatsApp |
| 社交媒体 | Facebook、Instagram、TikTok、LinkedIn、YouTube 等 |
| 企业展示 | Logo、封面图、办公环境、工厂、仓库 |
| 业务能力 | 产品类别、服务范围、OEM/ODM |

**企业资料必须区分“内部存档”和“允许公开展示”。**

例如营业执照的完整文件可以保存在受保护的存储区域，而前台只展示企业明确授权公开的信息。

不能因为用户上传了企业文件，就默认向所有网站访客开放。

### 10.2 企业官网标准页面

系统应该支持自动组合：

```text
首页
├── 企业介绍
├── 产品分类
├── 品牌故事
├── 工厂与仓库
├── 服务能力
├── 企业案例
├── 新闻与博客
├── FAQ
├── 联系我们
└── 法律与隐私页面
```

所有页面采用统一 CMS 结构。

这意味着企业可以：

- 用后台编辑。
- 用 API 编辑。
- 通过 Agent 创建草稿。
- 用模板重新排列。
- 多语言发布。
- 回滚到历史版本。

### 10.3 博客系统

博客不仅需要标题和正文，还应有：

```text
Blog Post
 ├── Title
 ├── Slug
 ├── Excerpt
 ├── Cover Image
 ├── Content Blocks
 ├── Images
 ├── Videos
 ├── Author
 ├── Category
 ├── Tags
 ├── Related Products
 ├── Related Articles
 ├── Language
 ├── SEO Metadata
 ├── Status
 └── Publish Schedule
```

正文建议采用结构化 Block，而不是仅保存不可控的 HTML 字符串。

这样可以将博客中的商品推荐、视频、图片画廊和询盘组件作为结构化内容使用。

### 10.4 SEO 能力

系统需要自动支持：

- 自定义 URL。
- 页面标题及描述。
- Canonical URL。
- Open Graph 信息。
- Sitemap。
- robots.txt。
- 多语言 hreflang。
- 商品及文章结构化数据。
- 301 重定向。
- 分类和分页的索引策略。
- 图片 Alt 文本。
- 页面发布及下架后的搜索索引处理。

还应有 SEO 批量诊断 API，例如检查缺失标题、重复 URL 和无效图片等问题。

## 十一、B2B 和 B2C 共用交易内核

建议只维护一套基础商品与订单系统，通过 Sales Channel 和交易规则区分不同客户。

### B2B 典型流程

```text
查看商品
   ↓
选择规格与数量
   ↓
提交询盘 / 申请样品
   ↓
销售人员报价
   ↓
买家确认
   ↓
生成采购订单
   ↓
付款或账期处理
   ↓
发货
```

B2B 需要进一步考虑企业采购账户、采购角色、MOQ、报价有效期、合同价、付款条款和报价转订单。

### B2C 典型流程

```text
查看商品
   ↓
选择SKU
   ↓
加入购物车
   ↓
结算
   ↓
支付
   ↓
库存确认与订单处理
   ↓
发货
   ↓
售后
```

B2C 的重点是购物车、实时价格计算、税费、支付、配送及退货。

两种流程可以共享商品、库存、客户基础资料和订单内核，但不能强行使用完全相同的结算规则。

支付对接应通过适配器处理，让具体商家绑定自己的合规支付账户。不要把平台替不同商家代收货款作为默认设计；那属于需要单独核查的支付和结算业务模式。

### 库存正确性

库存扣减需要遵守事务一致性：

- 可售库存不等于数据库中的简单数量字段。
- 需要区分实际库存、已预留库存和可售库存。
- 并发下单不能造成超卖。
- 支付失败或超时，需要释放预留。
- 库存变更必须有可追溯的流水。

这些业务规则必须在后端执行，不能依赖前端或 Agent 自行计算。

## 十二、大规模商品检索和性能架构

### 12.1 搜索引擎采用可选部署

第一阶段：

**PostgreSQL + B-tree/GIN 索引 + 适当的查询优化。**

需要加强复杂全文检索、错别字容忍、筛选及排序时，可以增加 Meilisearch。

它的 Community Edition 使用 MIT 许可证，但 Enterprise Edition 包含单独授权的功能，不能将企业版功能默认视为自由开源能力。([Meilisearch GitHub](https://github.com/meilisearch/meilisearch))

商品搜索索引应尽量面向商品展示实体，而不是把所有 SKU 作为独立商品进行重复索引。

例如一款服装的全部尺码可以聚合到商品搜索结果中，再由商品详情页查询具体 SKU 库存。

这样搜索列表不会出现同一款商品几十次。

### 12.2 不要过早增加 Redis

第一版可以使用：

- PostgreSQL 管理可靠任务和数据。
- HTTP 缓存处理公开资源。
- CDN 缓存图片和静态文件。
- 进程内小型缓存处理低成本配置数据。

只有在出现跨实例缓存、热点数据或复杂限流等实际需求时，再引入 Valkey。

这样能有效减少部署组件数量。

### 12.3 性能测试目标

建议从第一阶段就建立基准测试数据集。

| 测试场景 | 基础测试规模 |
|---|---|
| 商品主数据 | 10,000 SPU |
| 商品变体 | 300,000 SKU |
| 商品分类 | 多层级分类树 |
| 媒体关联 | 100,000+ 记录 |
| 商品批量导入 | 10,000 SPU/任务 |
| 页面模板 | 1,000 个页面实例 |
| 商品查询 | 并发查询、过滤、排序 |
| B2B 价格 | 不同客户组与采购数量 |
| 下单库存 | 并发预留、取消、超时释放 |
| 数据隔离 | 跨租户、跨站点访问 |

这些是**建议测试规模，不是当前系统已达到的性能指标**。

应在实际部署硬件上测量 API p50/p95/p99、内存、CPU、数据库查询时间、批量任务吞吐及页面核心性能指标。

不建议在没有压测数据时承诺“支持百万商品”或某个固定 QPS。

### 12.4 缓存隔离问题

尤其需要避免一个错误：

B2B 登录客户的合同价不能进入普通公共 CDN 缓存。

公开商品页可以缓存，但客户专属价格、库存承诺及采购权限必须根据认证上下文处理。

否则可能造成其他买家看到不属于自己的价格，甚至发生数据泄漏。

插件类别：

| 插件类型 | 示例 |

## 十四、部署与运维架构

### 14.1 最小部署方式

建议普通用户可以通过 Docker Compose 部署。

基础组件：

```text
Caddy
  │
  ├── Storefront (Astro)
  │
  ├── Admin (静态构建)
  │
  └── Go API
        │
        ├── PostgreSQL
        └── Worker

Media
  └── S3-Compatible Storage
```

小规模环境可以让 Go API 和 Worker 运行于同一程序，并使用本地或外部对象存储。

React 管理后台构建后可以通过静态服务器提供，不必长期运行一个额外的 Node 开发服务器。

Astro 使用官方 Node 适配器部署 SSR。([Astro Node Adapter](https://docs.astro.build/en/guides/integrations-guide/node/))

Caddy 可负责 HTTPS 和反向代理。([Caddy 官方文档](https://caddyserver.com/docs/automatic-https))

### 14.2 服务器配置建议

以下只是初步部署档位，需要通过压测校准。

| 部署级别 | 参考资源 | 适用情况 |
|---|---|---|
| 开发与测试 | 2 vCPU / 4GB | 功能开发、小样本 |
| 小型正式站 | 4 vCPU / 8GB | 轻量商品站，搜索/媒体服务可外置 |
| 较大商品站 | 4–8 vCPU / 16GB+ | 大量 SKU、后台任务 |
| 更高流量 | 分离 Web、数据库、Worker 和媒体存储 | 根据真实压力扩容 |

如果在同一台服务器上运行数据库、对象存储、搜索引擎和视频转码服务，所需资源会显著提高。

因此不应把上述配置理解为能承载任意数量图片、视频和并发的保证。

### 14.3 必须内置运维能力

开源自部署系统的用户不一定懂服务器管理。

因此建议提供：

- 安装向导。
- 环境变量模板。
- 健康检查。
- 数据库迁移。
- 版本升级检查。
- 自动备份配置。
- 数据恢复工具。
- 日志与指标。
- 存储容量统计。
- 邮件配置检查。
- 域名验证。
- TLS 状态检查。

生产环境还需要 PostgreSQL 可恢复备份策略、媒体对象备份和定期恢复演练。

备份不仅需要保存业务数据库，还要保存媒体对象、主题配置、密钥恢复材料及应用版本信息。

## 十五、安全、权限与数据隔离

这项系统未来可能由不同企业部署或托管，因此安全不能等到最后补。

建议基础能力包括：

| 领域 | 设计要求 |
|---|---|
| 数据隔离 | Tenant/Site 作用域验证 |
| 数据库 | RLS、最小权限、事务级上下文 |
| 管理后台 | RBAC、可选 MFA |
| API | Scope、速率限制、Token 轮换 |
| Agent | 工具授权、操作审批、审计 |
| 上传 | 类型检查、大小限制、恶意文件检测 |
| 页面编辑 | Schema 校验、防止脚本注入 |
| 支付 | Webhook 签名、幂等处理 |
| 订单 | 状态转换约束、审计 |
| 敏感文件 | 私有对象存储、短期授权访问 |
| 备份 | 加密、访问控制、恢复验证 |

PostgreSQL RLS 可以作为租户数据隔离的第二道防线，但不能代替 API 授权。

使用连接池时，需要在事务内设置可信的租户上下文，并防止上下文在不同请求之间泄漏。

同时要注意，PostgreSQL 超级用户及拥有 `BYPASSRLS` 权限的角色不受普通 RLS 限制。([PostgreSQL 官方文档](https://www.postgresql.org/docs/18/sql-createrole.html))

建议运行时使用最小权限数据库角色，迁移角色与应用角色分离。

## 十六、是否应该直接基于现有开源项目开发？

这也是需要认真评估的决策。

你希望做的是开源独立站平台，并不意味着必须从零重写所有订单和库存逻辑。

我核对了三个比较相关的项目。

| 项目 | 技术 | 优势 | 与本项目的差异 |
|---|---|---|---|
| [Medusa](https://github.com/medusajs/medusa) | Node.js / TypeScript | 商品、订单、价格、库存等模块成熟 | 核心采用 Node.js；模板和 Agent 体系仍需定制 |
| [Vendure](https://github.com/vendurehq/vendure) | TypeScript / GraphQL | B2B、B2C、渠道和插件体系 | GPLv3 许可及部分企业功能的授权边界需要考虑 |
| [Payload CMS](https://github.com/payloadcms/payload) | TypeScript | CMS、内容块、后台管理 | 更偏内容管理，不是完整交易内核 |

需要注意当前开源授权情况：

Medusa 核心为 MIT，但仓库中标记的部分企业版材料需要商业协议。([来源](https://github.com/medusajs/medusa))

Vendure 使用 GPLv3，其商业版和企业能力需要区分。([来源](https://github.com/vendurehq/vendure/blob/master/license/license-faq.md))

Payload 支持自部署，核心使用 MIT 许可证。([来源](https://payloadcms.com/get-started))

### 两条实际路线

**路线 A：自己开发 Go 商业内核。**

优点是架构轻、控制完整、适合深度集成 Agent 与模板引擎。

缺点是订单、价格、库存、支付、物流和售后的正确实现需要大量测试。

**路线 B：使用已有商业内核，自己开发建站与 Agent 层。**

优点是更快获得成熟的交易基础能力。

缺点是会受到已有框架、扩展模型和运行时的约束。

结合你的目标，我倾向于路线 A，但有一个前置要求：

**在正式实现交易内核前，用 Medusa 作为业务功能对照样本，进行一次 Build vs. Reuse 评估。**

不要花大量时间重复开发已经成熟、又无法形成差异化的电商能力。

真正值得重点自主研发的是：

**API 驱动的模板建站系统、统一 PIM、多行业属性系统、Agent 批量管理及轻量自部署体验。**

## 十七、开源项目许可证与社区架构

建议项目核心使用 **Apache-2.0**，作为初步许可证方案。

选择原因是它具有相对宽松的使用和再分发条件，并包含明确的专利授权条款。

但正式发布前，仍需要对直接引用的代码和依赖进行许可证兼容性审查。

项目应该包含：

```text
LICENSE
README.md
CONTRIBUTING.md
CODE_OF_CONDUCT.md
SECURITY.md
CHANGELOG.md

docs/
 ├── architecture/
 ├── api/
 ├── database/
 ├── themes/
 ├── plugins/
 ├── agents/
 ├── deployment/
 └── decisions/
```

建议明确一个原则：

**商品管理 API、Agent API、模板编辑和自部署核心能力均属于开源基础能力。**

否则，如果把这些最关键的模块全部放入商业授权层，项目就很难真正形成开放生态。

可以将托管服务、企业支持和定制开发作为后续商业模式，但它们不是基础架构必须实现的功能。

## 十八、开发顺序与版本规划

不建议同时开发全部功能。

要先完成一个可以真实创建商品、搭建官网、发布内容并完成 B2B 询盘的最小闭环。

然后逐步补齐 B2C 交易。

### Phase 0：架构基线

目标是让关键设计具有可验证的技术基础。

| 工作 | 交付结果 |
|---|---|
| 领域边界 | 核心模块架构 |
| 数据模型 | ERD 与关键约束 |
| API 设计 | OpenAPI 初版 |
| 页面模型 | 组件 Schema、版本规则 |
| 技术验证 | Astro 多模板动态渲染 |
| 性能基线 | PostgreSQL 大 SKU 原型测试 |
| 部署验证 | 最小 Docker Compose |
| 安全基线 | 认证、租户隔离、权限测试 |

### Phase 1：企业官网 + 商品展示

实现最小可用系统：

- 登录与企业资料。
- 站点创建与域名。
- 商品和 SKU。
- 商品图片和视频上传。
- 分类及行业属性。
- 企业页面和博客。
- 基础主题与组件。
- 页面预览、发布。
- 商品 CSV 批量导入。
- 商品和页面 API。
- B2B 询盘和联系表单。
- 基础 SEO。

这一阶段完成后，用户应能够真正部署一个外贸或企业展示独立站。

### Phase 2：交易能力

增加：

- 购物车与结算。
- 客户账户。
- 价格规则。
- 支付适配。
- 库存预留。
- 订单及售后状态。
- 运费规则与物流接口。
- B2B 客户组与阶梯价格。

## 最终建议

我认为这个项目最合理的总体结构是：

**Go + PostgreSQL + Astro + React + S3-Compatible Storage**

采用：

**模块化业务内核 + API First + PIM + CMS + Theme Engine + Agent Automation**

但真正决定项目竞争力的不是编程语言，而是下面三个能力能否形成统一架构。

**1. 一个商品数据源，支持任意行业和 B2B/B2C 交易模式。**

商品信息只需维护一次，就能够用于商品目录、商城、营销页面、博客推荐、报价及第三方渠道。

**2. 一个模板系统，支持人、API 和 Agent 使用相同的方式修改网站。**

用户既可以拖拽组件，也可以直接通过 API 改页面，还可以让 Agent 执行批量布局或内容修改。

**3. 一个自动化执行系统，能够安全管理数万款商品。**

AI 不仅负责生成标题或描述，还能读取商品数据、识别缺失字段、关联媒体、组织 SKU、批量创建草稿、提交修改并报告结果。

如果这三点设计正确，平台就不仅仅是一个开源电商程序，而是一个**可以由传统后台、第三方软件和 AI Agent 共同操作的开源商业网站基础设施**。

**下一版最应该深入的不是继续增加功能列表，而是 ARCH-002 数据模型与 ARCH-004 模板引擎之间的关系。** 这两个设计一旦确定，就能建立商品、企业内容、博客和网站组件的统一数据契约，后续 API、Agent 和管理后台都可以围绕它稳定开发。
