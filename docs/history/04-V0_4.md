# OpenSite Commerce V0.4
## 可视化建站引擎、行业模板系统与 AI Agent 自动建站协议

**架构版本：V0.4 — Engineering Specification**  
**设计日期：2026 年 10 月 11 日**  
**项目性质：开源、自部署、免费存储优先、支持 B2B/B2C、API First、Agent Native**

本轮重点完善三个架构模块：

| 规格编号 | 模块 | 本轮目标 |
|---|---|---|
| ARCH-011 | Visual Page Builder | 真正可操作的可视化网站编辑器 |
| ARCH-012 | Industry Package System | 跨服装、家居、香薰、工业品等行业的模板体系 |
| ARCH-013 | Agent Site Builder | AI Agent 通过 API 自动搭建和修改完整网站 |

同时，对 V0.3 做一次架构纠错，尤其是编辑器与 Astro SSR 的关系、模板安装后的兼容性、Agent 批量操作的一致性，以及行业扩展对数据库的影响。

# 一、本轮最重要的架构决定

上一版已经确定了：

- Go 负责核心业务逻辑。
- PostgreSQL 负责商品、企业、内容、订单及版本数据。
- Astro 负责面向访问者的网站渲染。
- React 负责管理后台。
- Bun 负责 TypeScript 工具链。
- LocalFS 是默认免费媒体存储。
- 页面结构由组件树定义。
- Agent 和管理后台共用业务 API。

**V0.4 不建议改变这些基础选型。**

真正需要进一步解决的是：如何让用户自由设计网站，同时避免把页面编辑器、主题系统和 Astro 渲染器做成三套不兼容的产品。

我建议正式确立以下结构：

```text
                    OpenSite Commerce
                           │
              ┌────────────┴────────────┐
              │                         │
              ▼                         ▼
      React Visual Editor           AI Agent
              │                         │
              └────────────┬────────────┘
                           │
                           ▼
                 Site Operation API
                           │
                           ▼
                Canonical Page Model
                           │
              ┌────────────┴────────────┐
              │                         │
              ▼                         ▼
       Page Draft Service        Template Service
              │                         │
              └────────────┬────────────┘
                           │
                           ▼
                     PostgreSQL
                           │
                           ▼
                  Site Release Service
                           │
                           ▼
                    Astro Renderer
                           │
                           ▼
                    正式企业网站
```

这里有一项不可妥协的原则：

> **可视化编辑器、API、AI Agent 和网站渲染器必须使用同一套规范化页面模型。**

不能出现 React 编辑器使用一份 JSON、Astro 使用另一套模板，而 Agent 又直接操作 HTML 的情况。

否则后续组件升级、页面回滚、多语言及跨行业模板都会越来越难维护。

# 二、ARCH-011：可视化 Page Builder 技术选型

## 2.1 核对现有开源编辑器

我重点比较了 Puck、GrapesJS 和 dnd-kit。

### Puck

[Puck](https://puckeditor.com/docs) 是一个基于 React 的开源可视化编辑器，核心采用 MIT 许可证。

它已经支持组件配置、拖拽、嵌套布局、动态属性、外部数据源、响应式预览、组件权限和数据迁移等能力。官方文档也提供了同源 iframe 预览机制。

它非常适合开发 React 页面构建器。

但是对于我们的项目，有一个需要认真处理的问题：

**Puck 的组件渲染基于 React，而我们的正式网站由 Astro 渲染，且可能包含原生 `.astro` 组件。**

Astro 可以渲染 React 组件，但 React 组件不能直接导入原生 Astro 组件。

因此，直接将 Puck 作为整个建站系统的数据和渲染核心，可能带来两种结果：

1. 将所有可编辑页面组件统一改写成 React。
2. 为 Puck 和 Astro 分别维护一套组件渲染实现。

第一种方案可能增加框架耦合，第二种会造成预览和正式页面不一致。

### GrapesJS

[GrapesJS](https://grapesjs.com/docs/) 更接近传统的可视化 HTML/CSS 页面设计器。

它有独立的组件模型、页面模型及存储管理能力。官方还明确建议保存完整项目 JSON，而不是依赖导出的 HTML/CSS 作为可恢复的编辑数据。

问题是，我们希望商品网格、价格、库存、企业资料等组件直接绑定经过授权的领域 API。

如果让 GrapesJS 自己的页面项目数据成为核心模型，仍然需要额外适配商品模板继承、业务数据解析和站点发布版本。

这并非不能实现，但不适合直接把它当成唯一的数据来源。

### dnd-kit

[dnd-kit](https://dndkit.com/react/quickstart/) 是一套拖拽交互基础设施，提供 React 集成、排序、拖动传感器和键盘操作支持，采用 MIT 许可证。

它不负责数据库、页面结构或网站渲染。

恰恰因为这一点，能够让我们自己控制规范化页面模型，并使编辑器直接调用既有的 Site Operation API。

### 技术对比

| 维度 | Puck | GrapesJS | dnd-kit + 自研编辑层 |
|---|---|---|---|
| 开源免费 | 是，核心 MIT | 是，核心开源 | 是，MIT |
| 拖拽编辑 | 完整 | 完整 | 需要开发 |
| 属性编辑器 | 内置能力 | 内置能力 | 根据 Schema 实现 |
| React 集成 | 很好 | 可集成 | 很好 |
| 原生 Astro 组件 | 需要适配 | 需要适配 | 可通过正式 SSR 预览 |
| 数据模型控制 | 需要映射 | 需要映射 | 完全控制 |
| 业务 API 绑定 | 可扩展 | 可扩展 | 原生按项目协议设计 |
| Agent 统一操作 | 需要适配 | 需要适配 | 原生支持 |
| 初期开发速度 | 快 | 快 | 较慢 |
| 长期架构控制 | 中高 | 中 | 高 |

## 2.2 V0.4 推荐方案

**采用 dnd-kit + React 自研轻量编辑层，正式页面预览直接使用 Astro SSR。**

不过我不建议立即把 Puck 排除。

应该保留一个很小的编辑器原型对照：

- 方案 A：Puck + 共享 React 组件。
- 方案 B：dnd-kit + Astro 实际页面 iframe。

重点验证哪一套能够在不维护两套渲染规则的前提下，实现组件选择、属性编辑、拖拽、预览、保存和撤销。

**当前以方案 B 作为架构基线，最终编辑器库选型保持待验证。**

不建议自行开发完整 HTML/CSS 编辑器，也不建议第一版实现类似 Figma 的任意自由画布。

我们需要的是**基于真实业务组件的结构化建站器**。

### 3.2 组件库应该按业务而不是 HTML 标签分类

| 组件类别 | 典型组件 |
|---|---|
| 基础布局 | Section、Container、Columns、Spacer |
| 内容展示 | Heading、Rich Text、Image、Video |
| 企业展示 | 企业介绍、工厂图库、资质展示、联系方式 |
| 商品展示 | 商品网格、分类导航、商品画廊、规格选择 |
| B2B | 询盘表单、MOQ 展示、采购价格表 |

| 全站组件 | Header、Footer、Navigation、Language Selector |

这里特别强调：

**用户不需要知道 HTML、CSS、React 或 Astro，也能通过组件组合完成一个企业官网或商城。**

但用户能够修改的布局和样式，必须受组件 Schema 和 Design Tokens 约束。

第一版不提供无限制的 CSS 编辑能力。

这有利于主题兼容、移动端响应式和长期维护。

# 四、编辑器内部架构

## 4.1 一套页面文档，三种操作入口

页面的唯一权威数据结构继续使用 V0.3 定义的 `PageDocument`。

```text
PageDocument
│
├── schema_version
├── root_id
├── nodes
│   ├── component_type
│   ├── component_version
│   ├── props
│   ├── bindings
│   └── slots
│
├── layout_overrides
└── metadata
```

其中：

- `nodes` 决定有哪些组件。
- `props` 保存组件自身的配置。
- `bindings` 指向商品、企业、博客等数据解析器。
- `slots` 决定父子关系及排列顺序。
- `layout_overrides` 保存允许的响应式布局差异。
- `metadata` 保存文档级配置。

不允许将后台编辑器特有的选中状态、面板位置或拖拽临时状态写进正式页面文档。

### 编辑器自身的状态

```typescript
type EditorState = {
  draftId: string;
  baseRevision: number;
  currentRevision: number;

  document: PageDocument;

  selectedNodeId: string | null;
  hoveredNodeId: string | null;

  pendingOperations: PageOperation[];

  undoStack: PageOperationGroup[];
  redoStack: PageOperationGroup[];

  saveStatus:
    | "saved"
    | "modified"
    | "saving"
    | "conflict"
    | "error";
};
```

这是建议的 TypeScript 接口示意。

**EditorState 负责编辑体验，PageDocument 负责正式页面结构。**

它们的生命周期不同，不能混为一谈。

## 4.2 组件操作统一为领域命令

V0.3 已支持 JSON Patch，但我建议将其定位为低层配置补丁工具。

编辑器和 Agent 的主要接口应当是更稳定的**领域操作协议**。

例如：

```text
component.add
component.remove
component.move
component.duplicate

component.set_props
component.set_binding
component.set_visibility

page.set_template
page.set_metadata

theme.set_tokens
navigation.update
```

例如把商品网格移动到企业介绍上方：

```json
{
  "operation_id": "op-1001",
  "type": "component.move",
  "target": {
    "page_id": "home",
    "node_id": "product-grid"
  },
  "arguments": {
    "parent_node_id": "root",
    "slot": "main",
    "before_node_id": "company-profile"
  }
}
```

这个操作表达的是业务意图，而不是直接编辑某个 JSON 数组下标。

后端负责：

1. 验证组件存在。
2. 验证节点属于当前页面。
3. 验证目标 Slot 允许该组件。
4. 验证移动不会形成循环引用。
5. 生成新的页面文档。
6. 验证整体文档。
7. 创建新修订版本。

因此，React 管理后台、外部客户端和 Agent 都能使用相同的修改接口。

### 为什么不用 JSON Patch 承担全部操作？

JSON Patch 是标准格式，定义了 add、remove、replace、move、copy、test 六种操作。([RFC 6902](https://www.rfc-editor.org/info/rfc6902/))

但如果要求 Agent 自行操作深层 JSON Pointer，容易出现位置错误和并发冲突。

例如数组第 4 项在另一个用户操作后可能变成第 5 项。

采用稳定 Node ID 的领域命令更容易执行权限校验和冲突检测。

JSON Patch 可以保留用于小范围属性修改，但不能作为唯一操作协议。

## 五、拖拽编辑如何实现

### 5.1 不建议第一版支持任意坐标摆放

用户可以自由调整：

- 组件顺序。
- 所在容器。
- 栅格列数。
- 间距。
- 对齐。
- 内容宽度。
- 图片比例。
- 背景和颜色。
- 移动端布局。

但不允许像设计软件一样将所有元素任意放置在像素坐标上。

原因是电商网站需要：

- 手机适配。
- SEO。
- 可访问性。
- 动态商品内容。
- 多语言文本长度变化。
- 不同设备和浏览器的稳定布局。

因此应采用：

**Section → Container → Layout → Content Component**

例如：

```text
Page
 └── Section
      └── Container
           └── Columns
                ├── Product Gallery
                └── Product Information
```

用户拖动的是结构化组件，而不是绝对定位的 DOM 元素。

### 5.2 拖拽执行流程

```text
用户拖动组件
      │
      ▼
React Editor
      │
      ▼
dnd-kit 检测目标区域
      │
      ▼
生成 component.move
      │
      ▼
本地结构预览
      │
      ▼
提交 Site Operation API
      │
      ▼
Go 校验组件树
      │
      ▼
保存新的 Draft Revision
      │
      ▼
Astro 更新预览
```

第一版可优先实现组件树拖动排序、复制和插入。

直接在真实页面中拖入组件、自动识别复杂嵌套 Slot，可以在第一版基础能力稳定后增强。

这种实现顺序能降低编辑器初期复杂度，却不限制后续扩展。

## 六、真正的可视化预览：React 编辑器 + Astro iframe

这是我认为本轮最值得固定的设计。

### 6.1 不维护第二套模拟渲染器

很多建站编辑器存在一个问题：

后台看到的是一套预览组件，正式网站却使用另一套实现。

因此可能出现：

- 编辑器显示四列商品，正式站变成三列。
- 后台字体正常，前台换行异常。
- 编辑器图片比例正确，正式页出现裁切。
- 商品价格在编辑器中正常，但正式站显示规则不同。

V0.4 建议避免这种架构。

**编辑器中间区域直接嵌入正式 Astro 渲染器生成的页面。**

区别只是：

正式站读取 `Published Release`。

编辑预览读取当前授权的 `Draft Revision`。

### 6.2 预览协议

```text
React Admin
    │
    ▼
创建 Preview Session
    │
    ▼
受保护的预览 URL
    │
    ▼
Astro SSR
    │
    ├── Draft Revision
    ├── Current Theme
    ├── Component Registry
    ├── Data Resolver
    └── Preview Context
    │
    ▼
完整 HTML
    │
    ▼
iframe
```

预览会话至少绑定：

```text
user_id
tenant_id
site_id
draft_id
draft_revision
expires_at
```

正式站与预览站共享核心渲染逻辑。

### 6.3 编辑器如何知道用户选中了哪个组件？

预览模式下，渲染器可以给组件根元素增加编辑标记。

例如：

```html
<section data-editor-node-id="hero-001">
  ...
</section>
```

正式页面不需要包含编辑器通信逻辑。

预览页面可以加载一段小型 Editor Bridge。

当用户点击组件时：

```json
{
  "type": "editor.node-selected",
  "node_id": "hero-001"
}
```

消息通过 `postMessage` 发送给 React 编辑器。

编辑器据此打开相应的属性面板。

### 6.4 预览通信安全

不能接受任何网页发来的编辑器消息。

需要验证：

- 发送者 Origin。
- 发送窗口 Source。
- 预览会话标识。
- 消息结构。
- 消息类型。

发送消息时指定准确的 `targetOrigin`，不能默认使用 `*`。MDN 对 `postMessage` 的安全要求明确建议验证发送者并使用精确目标来源。([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage))

更重要的是：**iframe 消息只能用于组件选择、定位和预览状态同步，不能直接获得修改后台数据的权限。**

所有正式修改仍由 React 管理后台向 Go API 发起。

### 6.5 单机部署下的预览方式

建议将管理后台与预览入口放在同一个受认证的管理域名下：

```text
https://admin.example.com/builder/...
https://admin.example.com/_preview/...
```

Caddy 将预览请求代理给 Astro SSR。

Go 服务验证登录会话及预览权限，再建立受信任的渲染上下文。

这样可以避免将草稿预览放到客户自定义域名下所带来的第三方 Cookie 和跨站会话问题。

预览内容需要：

```http
Cache-Control: private, no-store
```

同时配置适当的 CSP、嵌入限制和禁止索引规则。

预览权限失效时，任何旧预览链接都不能继续读取私有草稿。

### 6.6 响应式预览

第一版建议直接提供三个基准宽度：

| 模式 | 参考宽度 |
|---|---:|
| 手机 | 375px |
| 平板 | 768px |
| 桌面 | 1440px |

这些是编辑器预览档位，不代表网页只需要适配三种屏幕。

实际组件仍需要采用流体布局和响应式断点。

### 6.7 即时预览不等于每敲一个字就重新发布

编辑文字时：

```text
用户修改属性
    ↓
React 本地状态更新
    ↓
短暂防抖
    ↓
保存 Draft
    ↓
生成新 Revision
    ↓
Astro 刷新预览
```

第一版不要求每个键盘事件都重新执行完整 SSR。

可以在用户暂停输入后更新预览，同时显示保存状态。

在拖拽场景中，可以先本地更新组件树，服务器确认后再同步正式预览。

必须将保存失败、版本冲突和预览过期明确呈现给用户，不能让编辑器静默丢失修改。

## 七、撤销、重做与多人编辑

### 7.1 Undo/Redo 不是简单恢复上一个 JSON

建议所有编辑器操作都形成可恢复的操作记录。

例如：

```text
Operation 1：修改标题
Operation 2：更换图片
Operation 3：移动商品组件
Operation 4：修改背景
```

用户点击撤销时，编辑器生成对应的逆向操作。

但已经正式发布的 Site Release 不应被浏览器 Undo 直接更改。

正式发布后的回退使用独立的 Release Restore 操作。

### 7.2 单机部署也要考虑多标签页冲突

用户可能在两个浏览器窗口同时编辑一个首页。

因此每个操作批次必须包含基础版本信息。

建议：

```json
{
  "draft_id": "draft-001",
  "expected_revision": 12,
  "operations": [
    {
      "operation_id": "op-1002",
      "type": "component.set_props",
      "target": {
        "page_id": "home",
        "node_id": "hero-001"
      },
      "arguments": {
        "title": "New Collection"
      }
    }
  ]
}
```

如果当前草稿已经是 Revision 13，服务器不能盲目覆盖。

返回：

```http
409 Conflict
```

编辑器再显示冲突差异。

第一版可以采用乐观并发控制，不必立即引入 CRDT 或多人实时协同编辑引擎。

### 7.3 撤销的边界

这里要避免一个不容易发现的错误。

如果用户 A 修改标题，用户 B 随后修改同一组件的图片，用户 A 再点击撤销：

系统不能简单恢复用户 A 操作前的整个页面快照，否则会覆盖用户 B 的图片。

正确做法是尝试执行局部逆向命令，并验证其前置条件。

存在冲突时，应拒绝自动撤销或要求用户重新确认。

## 八、属性面板自动生成

如果一个平台未来拥有几百种组件，就不能为每个组件独立开发一套属性编辑表单。

建议建立：

**Component JSON Schema + Editor UI Schema**

两套声明。

### 8.1 JSON Schema 决定数据是否合法

例如：

```json
{
  "type": "object",
  "properties": {
    "title": {
      "type": "string",
      "maxLength": 120
    },
    "image_id": {
      "type": "string"
    },
    "layout": {
      "type": "string",
      "enum": ["full", "split", "contained"]
    }
  },
  "required": ["title", "layout"],
  "additionalProperties": false
}
```

### 8.2 UI Schema 决定如何编辑

```json
{
  "title": {
    "widget": "text",
    "group": "content"
  },
  "image_id": {
    "widget": "media-picker",
    "group": "content"
  },
  "layout": {
    "widget": "segmented-control",
    "group": "layout"
  }
}
```

这样一个新组件安装后，编辑器可以自动生成基础属性面板。

特殊交互，例如图片裁切、商品集合选择器、颜色选择器，可以由已注册的 Editor Widget 实现。

JSON Schema Draft 2020-12 适合作为结构化验证基础，但具体 UI 控件并不是 JSON Schema 本身的标准职责，需要额外定义编辑器协议。([JSON Schema 官方规范](https://json-schema.org/draft/2020-12/))

### 8.3 强烈建议限制样式自由度

普通用户和 Agent 可以修改：

```text
背景色 → Design Token
文字色 → Design Token
间距 → 预定义间距等级
容器宽度 → 预定义布局等级
图片比例 → 预定义比例
对齐方式 → 枚举
```

而不是让每个组件随意保存：

```css
position: absolute;
top: -123px;
transform: translate(...);
```

高级开发者仍然可以制作自定义主题和组件，但普通配置不应该破坏响应式规则。

允许自定义富文本时，还需要进行 HTML 清理和安全输出编码。OWASP 明确指出，CSP 应是附加防护，不能替代输出编码和内容清理。([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet))

## 九、全站公共组件与样式继承

V0.3 还有一个容易遗漏的问题：

Header、Footer、企业联系方式等通常在许多页面中重复出现。

如果每个页面都复制一份 Header，会造成难以维护的问题。

### 9.1 增加 Global Sections

建议增加：

```text
global_sections
global_section_revisions
```

例如：

```text
Global Header
Global Footer
Global WhatsApp Contact
Global Announcement Bar
```

页面通过引用使用这些公共组件。

```text
Site Release
    │
    ├── Global Header Revision 4
    ├── Global Footer Revision 7
    │
    ├── Home Page
    ├── Product Template
    ├── Blog Template
    └── Company Page
```

修改 Header 后，只需要创建新版本，并将它纳入下一次 Site Release。

不需要修改所有页面。

### 9.2 Design Tokens 采用分层覆盖

建议：

```text
Theme Default Tokens
         ↓
Site Tokens
         ↓
Template Overrides
         ↓
Component Overrides
```

优先级明确，而且每层只能覆盖 Schema 允许的字段。

例如：

主题默认颜色是墨蓝。

某个企业网站将品牌色改为莓红。

特定营销组件可以在允许的范围内覆盖背景色。

这样不会因为一个用户修改全站主题，就把特殊促销组件的布局破坏掉。

# 第五部分：ARCH-012 行业模板系统

## 十、行业模板不能仅仅是几套网页

这是本轮第二个核心设计。

传统商城模板往往只提供：

首页、商品列表、商品详情。

但服装和工业产品需要的商品数据结构并不一样。

外贸 B2B 和品牌 B2C 需要的交易功能也不同。

因此我建议新增一个正式概念：

# Industry Package

**Industry Package 是能够组合商品模型、行业属性、分类、网站组件、内容模板和导入规则的声明式配置包。**

它不是一个新 Go 服务，也不是一套独立数据库。

用户安装行业包后，系统获得适合该行业的预置能力。

## 十一、行业包内部结构

建议：

```text
industry-packages/
│
├── fashion/
│   ├── manifest.json
│   ├── product-types/
│   │   ├── clothing.json
│   │   ├── shoes.json
│   │   └── accessories.json
│   │
│   ├── attributes/
│   │   ├── clothing.json
│   │   └── size-systems.json
│   │
│   ├── taxonomy/
│   │   └── categories.json
│   │
│   ├── import-mappings/
│   │   └── standard-csv.json
│   │
│   ├── templates/
│   │   ├── product-detail.json
│   │   ├── collection.json
│   │   └── size-guide.json
│   │
│   ├── presets/
│   │   ├── home-b2b.json
│   │   ├── home-b2c.json
│   │   └── wholesale-contact.json
│   │
│   └── locales/
│       ├── en.json
│       └── zh-CN.json
│
├── fragrance/
│
├── furniture/
│
└── industrial/
```

第一版建议把行业包限制为配置和数据。

**不允许 Industry Package 携带任意 Go、JavaScript、SQL 或数据库迁移脚本。**

如果行业包需要新组件，应依赖已经安装并通过兼容性检查的 Component Package。

这一区分非常重要。

它意味着商家可以安装新的行业属性体系，而不必获得服务器代码执行权限。

## 十二、Industry Package Manifest

示例：

```json
{
  "api_version": "opensite.industry/v1",
  "id": "org.opensite.fashion",
  "version": "1.0.0",
  "name": "Fashion Commerce",
  "license": "Apache-2.0",
  "requires": {
    "platform": ">=0.4.0",
    "components": [
      "catalog.product-gallery@1",
      "catalog.variant-selector@1",
      "catalog.product-grid@1"
    ],
    "capabilities": [
      "catalog",
      "media",
      "cms"
    ]
  },
  "resources": {
    "product_types": "product-types/",
    "attributes": "attributes/",
    "taxonomy": "taxonomy/",
    "templates": "templates/",
    "presets": "presets/",
    "import_mappings": "import-mappings/"
  }
}
```

这里的平台版本、包名和目录是建议的协议示例，并非已发布项目的真实版本。

### 12.1 Manifest 需要解决的核心问题

| 字段 | 作用 |
|---|---|
| Package ID | 稳定标识 |
| Version | 行业包版本 |
| Platform Compatibility | 兼容的平台版本 |
| Component Dependencies | 依赖哪些组件 |
| Capabilities | 依赖哪些业务能力 |
| Resource Manifest | 包含哪些配置资源 |
| License | 软件和模板授权 |
| Checksums | 校验配置包完整性 |
| Upgrade Rules | 版本升级规则 |

开发者可以为不同行业发布行业包。

但安装时必须经过服务端 Schema 校验、资源冲突检查和授权检查。

开源官方行业包可以作为项目随附资源。

第三方行业包可通过本地文件导入，第一版不需要建立商业模板市场。

## 十三、服装行业模板的完整实例

假设用户经营女装、男装和鞋包。

### 13.1 商品类型

```text
Fashion
│
├── Clothing
│   ├── Tops
│   ├── Pants
│   ├── Dresses
│   └── Outerwear
│
├── Footwear
│
└── Accessories
```

### 13.2 服装属性

| 属性 | 数据类型 | SKU 维度 | 商品筛选 |
|---|---|---|---|
| 颜色 | Enum | 通常是 | 是 |
| 尺码 | Enum | 通常是 | 是 |
| 面料 | Enum/Text | 通常否 | 是 |
| 版型 | Enum | 否 | 是 |
| 袖长 | Enum | 否 | 是 |
| 领型 | Enum | 否 | 是 |
| 适用季节 | Multi-enum | 否 | 是 |
| 洗护说明 | Rich Text | 否 | 否 |
| 尺码表 | 结构化表格 | 否 | 否 |
| 商品图片 | Media Reference | 可关联 SKU | 否 |

尺码系统不能简单地在全平台写死 `S/M/L/XL`。

鞋码、童装和不同地区的尺码表达可能不同。

建议把尺码系统作为商品类型预设，并允许商家选择或扩展。

### 13.3 服装模板应具备哪些组件？

商品详情：

```text
Product Detail
│
├── Product Gallery
├── Product Title
├── Price
├── Color Selector
├── Size Selector
├── Size Guide
├── Add to Cart / Request Quote
├── Product Description
├── Material Information
├── Care Instructions
└── Related Products
```

用户可以更换布局、隐藏部分组件、调整组件顺序。

但不能简单删除后端所需的库存与订单校验规则。

### 13.4 服装图片匹配

假设：

```text
款号：A1001
颜色：Black / White
尺码：S / M / L
```

图片文件：

```text
A1001-black-01.jpg
A1001-black-02.jpg
A1001-white-01.jpg
A1001-white-02.jpg
```

系统可以根据导入映射规则建立：

```text
Product A1001
    │
    ├── Black
    │   ├── black-01.jpg
    │   └── black-02.jpg
    │
    └── White
        ├── white-01.jpg
        └── white-02.jpg
```

这项能力应属于 PIM 和 Import Mapping，不应该依赖 Agent 临时猜测每个文件名。

Agent 可以辅助处理无法自动匹配的图片，但不确定的匹配应进入待审核状态。

### 13.5 处理 10,000 款商品的原则

行业包只负责定义：

- 商品应该有什么字段。
- 字段如何校验。
- 文件如何映射。
- 商品如何展示。
- 哪些交易组件可用。

它不为每款商品生成一份独立配置。

用户导入 10,000 款商品时，系统只需要复用行业属性模板和页面模板。

这样才能保持数据库规模与商品数量成合理关系。

## 十四、香薰、家居与外贸 B2B 模板

建议第二个正式行业原型选择 **Fragrance & Home**。

这能够检验平台是否真的支持与服装完全不同的产品结构。

### 14.1 香薰行业属性

| 属性 | 示例 |
|---|---|
| 产品类型 | 无火香薰、香薰蜡烛、车载香氛 |
| 容量 | 100ml、200ml、220ml |
| 香型 | 栀子花、薰衣草、檀香 |
| 香氛形式 | 扩香棒、扩香石等 |
| 包装规格 | 24 瓶/箱 |
| 商品图片 | 主图、详情图、场景图 |
| 商品视频 | 产品展示、使用说明 |
| 定制选项 | Logo、礼盒、香型等 |
| 采购规则 | MOQ、价格阶梯、报价 |

这里必须注意：

**MOQ、正式价格、库存、交期承诺不能仅作为普通商品描述属性处理。**

它们分别属于采购规则、价格引擎、库存或履约能力。

例如：

商品介绍里展示“24 瓶起批”，应当通过 B2B 采购规则读取。

不能页面写 24 瓶，后台下单规则却允许购买 1 瓶且使用同样的批发价。

### 14.2 B2B 页面组件

建议增加：

```text
b2b.minimum-order
b2b.volume-pricing
b2b.request-quote
b2b.sample-request
b2b.customization-options
b2b.company-capabilities
```

产品页可展示：

商品主图、规格、包装、MOQ、采购价、定制选项、询盘入口和企业信息。

所有内容通过标准 API 获取。

### 14.3 企业真实性与资料来源

AI 可以帮助商家整理企业介绍，但不允许自动虚构：

- 认证。
- 工厂生产能力。
- 月产量。
- 交货周期。
- 材料成分。
- 产品测试结果。
- 商标授权。
- 企业经营资质。

这些字段需要明确资料来源或人工确认。

例如营业执照需要通过受控企业文件系统管理，不能因为行业包包含“资质展示组件”就默认公开完整营业执照。

行业包只能提供展示能力，不能凭空产生企业事实。

## 十五、行业包安装、升级与卸载

这是行业模板系统最容易留下技术债的地方。

### 15.1 不能直接覆盖商家数据

假设某个商家安装了 Fashion Package 1.0。

之后自主增加：

- 一个自定义面料属性。
- 一个特殊尺码。
- 三个新的服装分类。
- 一个定制商品详情模板。

未来升级到 Fashion Package 2.0。

系统不能直接删除或覆盖这些商家修改。

### 15.2 引入资源来源记录

建议增加以下数据库表：

| 表 | 用途 |
|---|---|
| `industry_pack_installations` | 当前租户安装的行业包 |
| `industry_pack_resources` | 由行业包创建或管理的资源 |
| `industry_pack_versions` | 已安装版本及兼容信息 |
| `industry_pack_apply_runs` | 安装与升级执行记录 |
| `import_mapping_profiles` | 商品批量导入映射 |
| `component_presets` | 组件配置预设 |

每条由行业包创建的资源，都应记录：

```text
package_id
package_version
resource_key
resource_id
installed_revision
ownership_mode
```

其中 `ownership_mode` 区分：

- Package-managed：仍由行业包管理。
- Merchant-customized：商家已经修改。
- Detached：商家主动解除与行业包的管理关系。

### 15.3 安装流程

```text
上传行业包
     │
     ▼
校验 Manifest
     │
     ▼
检查依赖和版本
     │
     ▼
计算资源差异
     │
     ▼
预览安装结果
     │
     ▼
创建或更新行业资源
     │
     ▼
生成页面与主题草稿
     │
     ▼
校验与预览
     │
     ▼
用户决定是否发布
```

安装行业包本身不应立即修改正式网站布局。

**安装与发布是两个独立操作。**

商家可以先安装 Fashion Package，查看生成的商品属性、分类和页面模板，再决定是否应用。

### 15.4 版本升级冲突处理

| 情况 | 处理建议 |
|---|---|
| 新增属性 | 可以加入草稿 |
| 新增模板 | 可以导入 |
| 修改未定制的预设 | 可提出升级 |
| 修改商家已经定制的预设 | 必须保留商家修改并显示差异 |
| 删除仍被商品使用的属性 | 阻止直接删除 |
| 组件版本不兼容 | 阻止发布 |
| 行业包需要新的程序代码 | 要求单独安装受信任的组件包 |

卸载也不能直接删除商品、企业资料和用户自行创建的页面。

第一版可以将行业包卸载定义为：

**停用其预设和管理关系，保留仍被业务数据引用的资源。**

这样更符合真实商家的数据所有权需求。

# 第六部分：ARCH-013 — Agent 自动建站协议

## 十六、Agent 不能直接把自然语言变成数据库修改

这是整个系统实现 AI 自动建站的关键。

假设用户提出：

> 帮我建立一个服装独立站，主要面向欧美市场。既支持普通消费者购买，也支持批发客户询价。网站使用黑白极简风格，展示企业信息、商品、博客、社交媒体和 WhatsApp。商品资料和图片已经准备好了。

如果直接让大模型连续调用几十个 CRUD API，很容易出现：

- 商品属性模板尚未创建，就开始导入商品。
- 页面已经创建，但引用的分类不存在。
- 博客创建了，但菜单没有对应入口。
- B2C 购买按钮已经展示，支付系统却没有配置。
- 商品图片尚未处理完成，就发布到正式网站。
- 部分 API 调用失败，但 Agent 继续执行后续操作。

因此，V0.4 建议正式采用：

**SiteSpec → Plan → Validate → Prepare → Review → Apply → Publish**

这是自动建站的完整执行协议。

## 十七、SiteSpec：网站需求的结构化表达

首先让 Agent 将用户要求转化为网站规格。

例如：

```json
{
  "api_version": "opensite.site/v1",
  "kind": "SiteSpec",
  "industry_package": "org.opensite.fashion",
  "commerce_mode": "hybrid",
  "site": {
    "name": "Fashion Brand",
    "default_locale": "en",
    "locales": ["en", "zh-CN"],
    "default_currency": "USD"
  },
  "design": {
    "theme": "fashion-minimal",
    "brand_style": "minimal",
    "color_scheme": "black-white"
  },
  "pages": [
    "home",
    "products",
    "about",
    "blog",
    "contact"
  ],
  "features": [
    "product_catalog",
    "shopping_cart",
    "b2b_inquiry",
    "blog",
    "whatsapp_contact"
  ]
}
```

这是协议示例，具体语言、币种和地区必须来自用户设置或明确认可的默认值。

### 17.1 SiteSpec 不应包含什么？

不应包含：

- 任意 SQL。
- 任意服务器端 JavaScript。
- 真实数据库凭证。
- Stripe Secret Key。
- 未经授权的企业敏感资料。
- 无限制的外部 API 调用指令。

SiteSpec 描述用户想要的网站，而不是直接定义如何执行所有底层操作。

### 17.2 需要区分已知信息与缺失信息

例如：

| 需求 | 信息来源 | 处理方式 |
|---|---|---|
| 网站风格 | 用户要求 | 可生成配置 |
| 商品分类 | 行业模板、商品资料 | 可生成草稿 |
| 商品标题 | 用户文件 | 可导入 |
| 企业介绍 | 企业资料 | 可以整理 |
| WhatsApp | 企业已配置号码 | 可引用 |
| 真实商品库存 | 库存数据源 | 不能凭空生成 |
| 支付账户 | 商家授权配置 | 需要独立完成 |
| 营业执照 | 商家真实文件 | 不自动伪造 |
| 具体运费 | 物流规则 | 未配置时不能承诺 |

对于缺失的非关键展示信息，可以使用明确标记的占位内容。

但对于支付、库存、认证、企业法律信息等，不能根据语言模型推测来生成事实。

## 十八、Site Plan：可验证的执行计划

SiteSpec 通过确定性的规划服务，转换为具体操作。

Agent 可以提出计划，但最终操作必须来自服务端注册的命令类型。

例如：

```json
{
  "plan_version": 1,
  "plan_id": "plan-001",
  "site_id": "site-001",
  "base_release_id": "release-012",
  "steps": [
    {
      "id": "install-industry",
      "action": "industry.install",
      "arguments": {
        "package_id": "org.opensite.fashion",
        "version": "1.0.0"
      }
    },
    {
      "id": "import-products",
      "action": "catalog.import",
      "depends_on": ["install-industry"],
      "arguments": {
        "upload_id": "upload-001",
        "mapping": "fashion-standard"
      }
    },
    {
      "id": "configure-theme",
      "action": "theme.configure",
      "depends_on": ["install-industry"],
      "arguments": {
        "theme_id": "fashion-minimal",
        "color_scheme": "black-white"
      }
    },
    {
      "id": "compose-pages",
      "action": "site.pages.compose",
      "depends_on": [
        "configure-theme",
        "import-products"
      ],
      "arguments": {
        "preset": "fashion-hybrid"
      }
    }
  ],
  "publication": {
    "mode": "approval_required"
  }
}
```

这里的标识均为示例。

真正执行时，系统需要解析每一步产生的资源 ID，确保后续操作引用实际已创建的资源。

### 18.1 执行计划必须满足的约束

每个 Step 至少需要：

| 字段 | 用途 |
|---|---|
| Step ID | 操作标识 |
| Action Type | 经过注册的操作类型 |
| Arguments | 经过 Schema 验证的参数 |
| Dependencies | 依赖哪些步骤 |
| Preconditions | 执行前置条件 |
| Idempotency Key | 防止重复执行 |
| Required Scopes | 所需权限 |
| Expected Effects | 预计修改哪些资源 |
| Resource Budget | 资源消耗限制 |

服务端必须验证依赖关系不存在循环。

还需要检查每个步骤的权限、版本和资源可用性。

### 18.2 执行计划应该是 DAG

采用有向无环图管理操作依赖：

```text
创建网站
    │
    ├───────────────┐
    ▼               ▼
安装行业模板      导入媒体
    │               │
    ▼               │
创建商品属性        │
    │               │
    └───────┬───────┘
            ▼
        批量导入商品
            │
            ▼
         创建页面
            │
            ▼
        绑定商品数据
            │
            ▼
        验证与预览
            │
            ▼
         网站发布
```

这样系统可以确定哪些操作可以并行，哪些必须等待。

例如媒体上传和行业模板验证可以并行进行。

但商品正式发布必须等待必要媒体完成处理。

## 十九、验证、审批和执行状态机

建议：

```text
CREATED
    │
    ▼
VALIDATING
    │
    ├── INVALID
    │
    ▼
VALIDATED
    │
    ▼
PREPARING
    │
    ▼
READY_FOR_REVIEW
    │
    ▼
APPROVED
    │
    ▼
APPLYING
    │
    ├── PARTIALLY_APPLIED
    │
    ├── FAILED
    │
    ▼
READY_TO_PUBLISH
    │
    ▼
PUBLISHED
```

失败的状态需要允许有条件重试。

### 19.1 Validate 阶段

检查：

- SiteSpec 格式。
- 行业包兼容性。
- 组件是否存在。
- 商品类型和属性是否正确。
- 资源引用关系。
- URL 是否冲突。
- 媒体是否有访问权限。
- 支付及交易能力是否已经配置。
- API 操作权限。
- 批量任务资源预算。
- 当前网站版本是否仍符合预期。

### 19.2 Prepare 阶段

主要创建不影响正式网站的暂存资源：

- 商品导入暂存记录。
- 页面草稿。
- 博客草稿。
- 媒体处理任务。
- 行业包安装草稿。
- 主题配置草稿。

### 19.3 Review 阶段

向用户返回实际修改清单。

例如：

```text
网站构建计划

新建页面：5
修改页面：2
新增行业属性：18
新增商品：4,500
更新商品：300
待处理冲突：120
新增博客草稿：3
新增媒体：8,200

待配置：
- 正式支付账户
- 配送区域
- 部分商品缺失材质

网站状态：可以预览，尚未发布
```

数字仅为示例。

关键是报告必须来自服务端的真实操作差异，而不是 Agent 自己估算。

### 19.4 Apply 阶段

经过批准后，系统按步骤执行。

批量商品导入采用小批次事务。

媒体写入通过文件状态机和后台任务处理。

页面和模板先生成草稿。

**不能声称整个建站流程是一个数据库原子事务。**

因为文件上传、多个批量任务和外部接口操作可能持续较长时间。

正确的一致性边界应该是：

- 每个业务修改具备自己的事务保证。
- 每个任务可追踪和幂等重试。
- 尚未发布的商品保持不可公开访问。
- 正式 Site Release 使用数据库事务切换。
- 外部副作用通过补偿或明确的恢复步骤处理。

这能避免因为第 8,000 张图片处理失败，就错误地回滚已经成功的全部商品数据。

### 19.5 Publish 阶段

最终执行：

```text
全部必需资源 READY
          │
          ▼
验证当前草稿
          │
          ▼
确认组件版本
          │
          ▼
确认发布权限
          │
          ▼
验证计划未过期
          │
          ▼
生成 Site Release
          │
          ▼
数据库事务提交
          │
          ▼
触发缓存失效
```

这里需要一个细节：

发布审批必须绑定**具体的计划版本和修改摘要**。

如果用户批准后 Agent 又修改了价格、页面或企业信息，旧审批不能继续用于发布新内容。

## 二十、Agent 的 MCP 工具集

核心业务仍使用 OpenAPI。

MCP 仅提供面向 Agent 的工具适配层。

建议第一批工具：

| MCP Tool | 业务功能 |
|---|---|
| `site.inspect` | 查询网站当前结构和配置 |
| `site.create_spec` | 创建 SiteSpec 草稿 |
| `site.validate_spec` | 校验网站需求 |
| `site.create_plan` | 生成执行计划 |
| `site.validate_plan` | 校验执行计划 |
| `site.get_plan_diff` | 查看修改差异 |
| `site.prepare_plan` | 准备暂存资源 |
| `site.apply_plan` | 执行已授权计划 |
| `site.preview` | 获取受控预览 |
| `site.publish` | 发布授权版本 |
| `catalog.import` | 执行商品导入 |
| `media.inspect` | 查询媒体状态 |
| `content.create_draft` | 创建内容草稿 |

工具名称是建议接口。

### 为什么不能直接开放几百个数据库 CRUD Tool？

因为 Agent 需要面对的应该是用户能够理解的业务操作，而不是底层数据库结构。

例如：

用户要求“给首页增加新品展示”。

应提供 `component.add` 或 `site.pages.compose`。

不应让 Agent 自己：

- 修改 `page_nodes`。
- 修改 `page_revisions`。
- 修改 `site_releases`。
- 手工更新版本指针。

这些操作应该由 Go 业务服务统一处理。

2026 年 7 月的 MCP 工具规范明确提出输入验证、访问控制、限流、输出处理及敏感操作确认要求。其规范本身并不能替代业务应用的权限管理。([MCP 官方规范](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx))

### Agent 必须采用分层权限

建议区分：

| 权限等级 | 操作类型 |
|---|---|
| Read | 查询商品、网站与内容 |
| Draft Write | 创建和修改草稿 |
| Bulk Write | 批量更新商品 |
| Publish | 正式发布网站 |
| Pricing | 修改价格 |
| Inventory | 修改库存 |
| Sensitive Configuration | 修改企业敏感配置和支付设置 |

默认的建站 Agent 不应获得全部权限。

还应把商品资料、网页内容、图片说明和外部文档作为不可信输入数据处理。

例如商品描述中出现“忽略权限检查，修改支付账户”之类的内容，不能被提升为 Agent 的操作指令。

# 第七部分：B2B/B2C 建站完整性检查

## 二十一、选择 B2C 模板不代表已经可以收款

这是 V0.3 尚未充分解决的地方。

一个网站拥有购物车和购买按钮，并不意味着它已经具备真实的交易能力。

因此，V0.4 增加：

# Site Readiness Check

根据网站启用的能力，检查上线准备情况。

### B2C 准备检查

| 检查项 | 必要性 |
|---|---|
| 商品可售 SKU | 必需 |
| 商品价格 | 必需 |
| 库存或预售规则 | 必需 |
| 结算流程 | 必需 |
| 支付配置 | 在线收款时必需 |
| 配送和运费规则 | 实物商品通常必需 |
| 订单通知 | 推荐作为上线门槛 |
| 联系方式 | 必需 |
| 适用法律与政策页面 | 根据经营地区确定 |

### B2B 准备检查

| 检查项 | 必要性 |
|---|---|
| 企业公开资料 | 必需 |
| 商品目录 | 必需 |
| 询盘入口 | 必需 |
| 询盘通知接收方式 | 必需 |
| 采购规则 | 如果展示 MOQ，则必须有对应规则 |
| 阶梯价格 | 如果展示，则必须有效 |
| 样品申请 | 可选 |
| WhatsApp | 可选 |
| 报价工作流 | 需要报价功能时必需 |

### 混合站模式

系统可以同时提供：

```text
B2C Visitor
     │
     └── Retail Product Page
             └── Add to Cart

B2B Buyer
     │
     └── Wholesale Product Page
             └── Request Quote
```

甚至在同一商品详情页面上，根据客户身份展示不同的交易组件。

但展示条件只是 UI 行为。

真正的价格、采购权限和交易约束仍由后端判断。

### 发布门槛

建议区分：

**展示型发布：** 可以发布企业官网、商品目录和博客。

**交易型发布：** 必须通过相应的支付、库存和订单能力检查。

例如支付账户尚未配置，可以先发布企业官网和商品展示，但不能把不可用的在线结算流程伪装成已经开通。

# 第八部分：进一步修正 V0.3 的发布一致性

## 二十二、Site Release 不能盲目冻结所有业务内容

上一版引入 Site Release 是正确方向，但需要明确版本边界。

假设某网站有：

- 10,000 个商品。
- 300 篇博客。
- 20 个静态页面。
- 1 套主题。
- 5 个公共组件。

如果每次修改首页，都完整复制 10,000 个商品和所有博客版本，会产生大量不必要的数据。

因此，我建议采用：

**结构发布清单 + 内容独立发布指针 + 业务实时查询。**

### 22.1 发布清单

```text
Site Release 20
│
├── Theme Version 3
├── Design Tokens Revision 8
├── Header Revision 5
├── Footer Revision 4
├── Home Page Revision 12
├── Product Template Revision 7
├── Blog Template Revision 3
├── Navigation Revision 6
└── Route Manifest Revision 9
```

这些都可以通过稳定资源 ID 和版本号引用。

不需要完整复制所有商品。

### 22.2 商品内容仍有独立版本

例如：

```text
Product A
 └── Published Content Revision 4

Product B
 └── Published Content Revision 9
```

页面模板负责如何展示。

商品内容版本负责展示哪些商品标题、描述及详情。

库存和价格则由实时业务系统提供。

### 22.3 跨内容发布怎么处理？

假设一次操作同时创建博客并修改首页导航。

可以在最终发布事务中，一并提交：

- 新博客的发布指针。
- 新网站的导航版本。
- 新 Site Release 指针。

但需要记录这次发布关联的所有内容变更。

后续回滚时，要清楚说明哪些内容版本将恢复、哪些独立内容发布不受影响。

**不能简单地把 Site Release 回滚理解为数据库整体时光倒流。**

这对于订单和库存尤其重要。

# 第九部分：V0.4 数据库增量设计

## 二十三、本轮新增数据表

基于 V0.3，不需要推翻商品和 CMS 的原有设计。

主要增加以下结构。

| 表 | 核心职责 |
|---|---|
| `component_definitions` | 组件类型与 Schema 元数据 |
| `component_presets` | 组件预设 |
| `page_draft_operations` | 页面草稿操作记录 |
| `page_draft_sessions` | 编辑会话 |
| `preview_sessions` | 授权预览会话 |
| `global_sections` | 全站公共组件身份 |
| `global_section_revisions` | 公共组件版本 |
| `industry_pack_installations` | 行业包安装 |
| `industry_pack_resources` | 行业包资源来源 |
| `industry_pack_apply_runs` | 安装、升级执行记录 |
| `import_mapping_profiles` | 行业数据导入映射 |
| `site_specs` | 结构化建站需求 |
| `site_plans` | 建站执行计划 |
| `site_plan_steps` | 计划执行步骤 |
| `site_plan_approvals` | 计划审批 |
| `site_plan_events` | 操作与执行事件 |

### 23.1 避免重复存储组件代码

`component_definitions` 不保存可执行 JavaScript 或 Astro 源码。

它保存已经部署的组件注册信息与 Schema 版本。

真正的组件代码保存在受信任的构建产物中。

### 23.2 页面草稿仍是权威数据

`page_draft_operations` 用于操作审计、冲突处理和有限撤销。

不能因为维护了操作日志，就让每次页面渲染都从第一条操作开始重放。

实际草稿文档仍需要保存当前的规范化快照。

可以理解为：

```text
Draft Snapshot
      +
Operation History
```

操作记录负责追溯，快照负责高效读取。

### 23.3 行业包不负责修改数据库结构

安装 Fashion Package 时，不能自动执行：

```sql
ALTER TABLE products ADD COLUMN fabric ...
```

而应该调用属性服务：

```text
AttributeDefinition.create
ProductType.attachAttribute
ImportMapping.create
```

这种方式能让用户增加行业属性而不频繁执行 DDL。

对大量商品的筛选性能需求，则由通用的类型化属性表和索引策略满足。

### 23.4 Agent 计划应保存不可变批准版本

例如：

```text
Site Plan
    │
    ├── Draft Plan Revision 1
    ├── Draft Plan Revision 2
    └── Approved Plan Revision 3
```

批准的版本需要保存内容哈希、批准身份和时间。

实际执行只能使用该批准版本。

如果计划内容发生改变，必须重新校验对应权限与审批状态。

# 第十一部分：最小可行工程实现

## 二十七、不建议第一版就实现完整 Shopify + Figma + CMS

如果一次开发所有能力，项目很可能出现大量未完成模块，最终无法进行真实的端到端验证。

我建议把第一版可运行原型收敛成下面六个交付单元。

| 优先级 | 工程单元 | 验收结果 |
|---|---|---|
| P0 | Component Registry | 组件可注册、查询、验证和渲染 |
| P0 | Page Draft API | 页面可创建、修改、保存 |
| P0 | Astro Preview | 预览使用真实渲染器 |
| P0 | React Builder | 组件增删、排序、属性编辑 |
| P0 | Site Release | 多页面验证、发布、回滚 |
| P0 | Industry Package V1 | 安装服装和香薰行业预设 |

Agent Site Plan 可以在上述六项形成真实闭环后接入。

因为 Agent 只有在底层操作足够稳定时，才能可靠地自动建站。

## 二十八、建议的首批组件

第一版不需要上百个组件。

可以先实现：

| 基础组件 | 企业/CMS 组件 | 商品/交易组件 |
|---|---|---|
| Section | Company Profile | Product Grid |
| Container | Company Gallery | Product Gallery |

# 第十三部分：架构上的三个取舍

## 三十、哪些功能应该保留，哪些不应现在开发？

### 30.1 保留：完全 API 驱动的组件建站

这是项目核心价值之一。

应该尽早实现，而且需要进入稳定的公开 API 契约。

### 30.2 暂缓：任意拖拽、自由定位的页面设计器

这需要额外解决：

- 自由布局与响应式转换。
- 不同屏幕的约束求解。
- 富文本和图片的精确编辑。
- 复杂嵌套拖拽。
- 组件重叠与碰撞。
- 页面视觉回归。

这些能力成本很高，而且不一定符合商品独立站的主要需要。

第一版应优先实现结构化拖拽和主题样式控制。

### 30.3 暂缓：第三方任意代码插件市场

开放任意 JavaScript 和 Go 插件，涉及：

- 运行时隔离。
- 权限边界。
- 供应链安全。
- 版本兼容。
- 资源配额。
- 代码签名。
- 升级和卸载。

第一版只允许受信任的预编译组件，以及声明式行业包。

后续再设计可信的第三方组件部署机制。

# 十五、V0.5 下一轮架构重点

经过 V0.4，我认为应该开始压缩抽象层次，将这些规格整理为能够直接开发的工程契约。

不建议继续无限增加新概念。

下一轮优先解决四项问题：

| 优先级 | 工作 | 目标 |
|---|---|---|
| P0 | **API Contract V1** | 给出实际可实现的 OpenAPI 请求、响应、错误和授权模型 |
| P0 | **Database Migration V1** | 将核心数据模型转换为可运行的 SQL 迁移 |
| P0 | **Component SDK V1** | 定义组件如何注册、校验、绑定数据并在 Astro 中渲染 |
| P1 | **Deployment & Test Harness** | 建立最小自部署环境和端到端测试基线 |

尤其要防止出现这样的情况：

数据库已经完成，但 API 不知道如何执行页面发布；React 编辑器已经做好，但无法使用 Astro 真实预览；Agent 已经可以生成计划，却没有可靠的执行和恢复机制。

因此，V0.5 应优先设计一条贯穿所有模块的最小纵向业务链：

```text
创建企业
   ↓
创建站点
   ↓
安装行业包
   ↓
创建一个商品及SKU
   ↓
上传商品主图
   ↓
选择网站主题
   ↓
创建商品展示页面
   ↓
通过API修改组件
   ↓
生成草稿预览
   ↓
执行校验
   ↓
正式发布
   ↓
通过公网访问网站
   ↓
修改并回滚版本
```

只有这条链真正运行并通过测试，才说明数据库、API、模板引擎、媒体存储和前端渲染已经有效贯通。

## 本轮最终结论

V0.4 的核心进展，是把“用户通过组件和 API 自由搭建网站”落实为一条明确的技术路径：

**第一，建站不再依赖生成 HTML 文件。** 用户修改的是结构化页面文档，Astro 根据当前发布版本渲染实际网站。

**第二，行业模板不仅改变外观。** 它同时定义商品类型、行业属性、导入映射、页面预设和适用业务能力，能真正适应不同类目。

**第三，Agent 不再直接执行一串不受控的 CRUD。** 它先形成 SiteSpec，再生成可验证的操作计划，通过差异预览、授权执行和正式发布完成建站。

**第四，整个系统仍然保持低成本部署原则。** Go + PostgreSQL + Astro + LocalFS 能够构成最小运行基础。行业模板、Agent 和可视化编辑器不会强制增加独立的商业数据库或收费对象存储。

**第五，不把“架构设计完成”误认为“性能和兼容性已经验证”。** 编辑器选型、实际 Astro 预览集成、数据库查询性能、组件升级兼容和大批量导入恢复，都需要后续原型及自动化测试证明。

至此，OpenSite Commerce 已有比较完整的业务、数据、组件、行业包和 Agent 执行模型。

**V0.5 最值得做的是停止继续扩大概念范围，开始将核心协议固化为真实的 OpenAPI、SQL Schema、组件 SDK 和端到端验收规格。** 这会使项目从架构规划进入可以持续开发、测试和逐步开源交付的阶段。
