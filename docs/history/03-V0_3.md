# OpenSite Commerce V0.3
## 开源 B2B/B2C 独立站：数据库与可编程建站协议详细设计

**架构版本：V0.3 / Engineering Design**  
**日期：2026 年 10 月 11 日**  
**本轮范围：ARCH-002 数据库设计 + ARCH-004 模板建站引擎 + 两者的 API 契约**

本轮从总体架构进入工程设计，重点不是继续扩充功能列表，而是把数据库、页面模板、商品属性和 Agent 操作之间的关系设计清楚。

目标是让同一套系统能够完成以下工作：

> 一个服装商家导入 10,000 款服装、300,000 个 SKU，选择一个服装主题，通过可视化编辑器搭建网站，再由 Agent 批量补全商品、修改页面布局、发布博客及维护企业资料。整个过程不需要为每个商品生成独立代码，也不要求重新部署网站。

同时，系统需要能够在普通自有服务器上运行，**不强制使用付费对象存储、商业 CMS、商业搜索或商业建站服务。**

# 第一部分：重新审查 V0.2

## 一、发现四个必须解决的架构缺口

上一版的总体技术方向基本合理，但有四个地方如果不进一步约束，真正开发时很容易出现严重的架构问题。

### 1. Astro 并不能直接执行数据库中的任意组件

V0.2 设计了通过 JSON 配置页面。

但不能简单地认为：

用户新增一个组件名称 → 存进 PostgreSQL → Astro 就能自动渲染这个组件。

Astro 的组件通常需要在构建阶段被纳入应用。

**正确区分两种操作：**

| 操作 | 是否需要重新构建应用 |
|---|---|
| 调整已有组件位置 | 不需要 |
| 修改标题、颜色、图片 | 不需要 |
| 修改组件绑定的商品分类 | 不需要 |
| 切换已安装的兼容主题 | 不需要 |
| 增加一个新的组件配置实例 | 不需要 |
| 安装包含新代码的主题或组件 | 通常需要构建或部署新代码 |
| 修改组件底层 React/Astro 实现 | 需要构建或部署 |

所以我们需要的是：

**预编译组件注册表 + 数据驱动页面配置 + 动态 SSR 渲染。**

而不是让系统执行数据库里保存的任意前端源码。

Astro 官方支持按需 SSR，动态页面不必在构建时枚举所有商品 URL，这与大量商品共享页面模板的需求一致。

### 2. 页面版本管理还不够

上一版设计了每个页面的 Draft 和 Published Revision。

但考虑一个实际操作：

Agent 同时修改首页、导航栏、页脚和企业介绍。

如果四个部分分别发布，可能出现：

- 新首页配旧导航。
- 新导航指向尚未发布的页面。
- 新主题配旧组件参数。
- 新页面引用了还未发布的媒体。

因此，必须增加**站点级发布版本 Site Release**。

一次发布可以包含多个页面、主题配置、导航和 SEO 路由的修改。

只有整个发布包验证通过，才能切换正式站点版本。

### 3. 商品属性不能完全依赖 JSONB

行业属性具有很大差异，JSONB 确实有必要。

但服装商品的颜色、尺码、SKU、价格和库存必须有明确约束。

例如：

- 不允许同一商品出现两个完全相同的规格组合。
- 不允许同一租户出现冲突的 SKU 编号。
- 不允许尺寸和颜色的无效组合进入正式商品。
- 商品属性更新后，筛选索引必须同步或最终一致地更新。

因此需要：

**标准字段 + 类型化属性定义 + SKU 选项组合 + 扩展 JSONB。**

不能只有一张 `products` 表和一个巨大的 `attributes` JSON。

### 4. 模板更新与业务数据更新不能共用一种发布机制

网站内容和商品交易数据具有不同的一致性要求。

例如：

| 数据 | 正确处理方式 |
|---|---|
| 首页布局 | 草稿、预览、发布 |
| 博客文章 | 草稿、审核、发布 |
| 商品标题与详情 | 可审核、版本化发布 |
| 商品实际库存 | 实时事务更新 |
| 客户合同价格 | 受权限控制的实时业务查询 |
| 订单 | 事务状态机 |
| 支付结果 | 支付事件验证及幂等处理 |

**不能为了页面版本化，把库存和订单也纳入同一个静态页面快照。**

本轮正式将系统分为三个独立但协作的机制：

1. **Business Transaction：** 处理真实交易和实时业务状态。
2. **Content Revision：** 处理商品描述、企业资料和博客内容。
3. **Site Release：** 处理整个网站的公开展示版本。

这是 V0.3 最重要的架构修正。

# 第二部分：ARCH-002 V1 数据库详细设计

## 二、确定系统的数据边界

使用 PostgreSQL 18，继续采用 Go + pgx + sqlc。

数据库设计遵循以下原则：

**第一，单实例优先。** 用户自行部署时，默认只有一个经营主体，不需要先配置复杂的 SaaS 租户管理。

**第二，预留多租户能力。** 数据模型支持将来一套部署承载多个企业，但不会为了尚未实现的托管模式增加大量运行组件。

**第三，业务对象不能与页面混为一谈。** 商品、企业和博客是独立内容资源，页面只是它们的一种展示方式。

**第四，使用数据库约束保护关键不变量。** 唯一性、跨租户关系和部分生命周期规则不能只依赖 Go 代码检查。

**第五，不为高商品数量预先分库分表。** 先用 PostgreSQL 的索引、批量写入和查询优化解决实际压力。

## 三、数据模型分成八个领域

| 领域 | 负责的数据 | 主要模块 |
|---|---|---|
| Identity | 用户、角色、API Key、授权 | identity |
| Organization | 企业主体、联系方式、证照 | company |
| Site | 网站、域名、市场、语言 | site |
| Catalog | 商品、SKU、属性、分类 | catalog |
| Content | 博客、页面、内容版本、翻译 | cms |
| Presentation | 主题、组件、模板、发布版本 | theme |
| Media | 图片、视频、文件、引用关系 | media |
| Commerce | 定价、客户、库存、订单 | commerce |

自动化任务和审计属于横向基础设施，单独管理。

## 四、顶层表结构：Tenant、Organization、Site

### 4.1 必须实现的表

| 表 | 关键字段 | 业务作用 |
|---|---|---|
| `tenants` | id、name、status | 数据所有权边界 |
| `users` | id、email、password_hash | 用户身份 |
| `tenant_memberships` | tenant_id、user_id、role_id | 企业成员关系 |
| `organizations` | tenant_id、id、legal_name | 企业法律主体 |
| `company_contacts` | organization_id、type、value | 邮箱、电话、WhatsApp 等 |
| `company_documents` | organization_id、media_id、visibility | 营业执照等资料 |
| `sites` | tenant_id、id、organization_id | 独立网站 |
| `site_domains` | site_id、hostname、verified_at | 网站域名 |
| `site_locales` | site_id、locale、enabled | 网站语言 |
| `markets` | tenant_id、id、currency、region | 经营市场 |
| `sales_channels` | tenant_id、id、channel_type | B2B/B2C 渠道 |
| `site_channels` | site_id、channel_id | 网站与销售渠道关联 |

### 4.2 企业资料不应该完全归属于网站

一个企业可能拥有两个独立站。

例如：

```text
Organization：某服装企业
       │
       ├── 企业营业执照
       ├── 企业地址
       ├── 企业联系方式
       │
       ├── Site A：零售品牌站
       │
       └── Site B：批发采购站
```

两个网站可以共享企业基础资料。

但企业也可以在不同网站上展示不同的公开联系入口、语言、品牌介绍和联系方式。

因此建议区分：

**Organization Profile：** 企业真实资料。

**Site Company Presentation：** 当前网站选择公开展示的资料及具体展示方式。

例如营业执照归企业管理，网站是否展示、展示哪个版本、是否隐藏部分信息，则由公开展示配置决定。

### 4.3 域名必须全局唯一

在多租户模式下不能允许：

- 企业 A 使用 `example.com`。
- 企业 B 也绑定 `example.com`。

域名需要归一化和所有权验证。

包括小写、国际化域名转换、末尾点号及端口处理。

只有验证通过且已启用的域名，才可用于将公开请求映射到对应的 Tenant 和 Site。

不允许仅凭用户传递的 `site_id` 或任意 HTTP Host 值决定其可以访问哪个站点。

## 五、商品数据库：面向数万款商品

### 5.1 商品核心表

建议以下表属于商品领域的第一批必需表。

| 表 | 关键字段 | 说明 |
|---|---|---|
| `products` | tenant_id、id、product_code、status | 商品主实体 |
| `product_variants` | product_id、sku、option_key | 具体可售 SKU |
| `product_options` | product_id、code、position | 规格维度，如颜色、尺码 |
| `product_option_values` | option_id、value、position | 规格选项，如黑色、XL |
| `variant_option_values` | variant_id、option_id、value_id | SKU 与规格值关联 |
| `product_listings` | product_id、channel_id、status | 商品在渠道中的上架关系 |
| `categories` | id、parent_id、slug | 商品分类 |
| `product_categories` | product_id、category_id | 商品与分类关联 |
| `collections` | id、type、rules | 商品集合 |
| `collection_products` | collection_id、product_id | 手工集合成员 |
| `product_media` | product_id、variant_id、media_id、role | 商品图片和视频引用 |

此时商品身份与网站展示是分离的。

例如商品 `SHIRT-001` 可以同时用于批发站和零售站，而不必在数据库里保存两份商品。

### 5.2 商品与 SKU 的关系

```text
Product：SHIRT-001
│
├── Option：Color
│   ├── Black
│   ├── White
│   └── Blue
│
├── Option：Size
│   ├── S
│   ├── M
│   └── L
│
└── Product Variants
    ├── BLACK-S
    ├── BLACK-M
    ├── BLACK-L
    ├── WHITE-S
    ├── WHITE-M
    ├── WHITE-L
    ├── BLUE-S
    ├── BLUE-M
    └── BLUE-L
```

九个 SKU 共用一个 Product。

但每个 SKU 可以拥有自己的：

- SKU 编号。
- 条形码。
- 库存。
- 重量和尺寸。
- 价格条目。
- 特定图片。
- 上下架限制。

### 5.3 防止规格组合重复

不能只检查 SKU 编号。

例如：

```text
SKU-001：Black + XL
SKU-002：Black + XL
```

虽然 SKU 不同，规格组合却重复。

建议每个 Variant 维护一个服务端生成的规范化 `option_key`。

例如：

```text
color:black|size:xl
```

实际应使用稳定的 Option/Value ID 生成，而不是依赖会被翻译或修改的显示名称。

在写入事务中检查规格完整性，并通过唯一约束保证同一商品内的组合不重复。

`option_key` 不接受客户端或 Agent 任意生成的值，而是由商品服务统一计算。

无变体商品可以使用固定的 `default` 组合。

## 六、行业属性模板：不能与 SKU 规格混淆

这是需要特别注意的领域边界。

**SKU Option 不等于 Product Attribute。**

例如：

服装的颜色和尺码，可能决定 SKU。

服装的面料、领型、袖长、洗护说明，则一般属于商品属性。

### 6.1 建议的属性表

| 表 | 功能 |
|---|---|
| `attribute_definitions` | 定义属性名称和类型 |
| `attribute_enum_values` | 定义可选枚举值 |
| `attribute_templates` | 定义行业属性模板 |
| `attribute_template_fields` | 模板与属性关系 |
| `product_attribute_values` | 商品属性值 |
| `variant_attribute_values` | SKU 专属属性值 |
| `product_types` | 商品类型与属性模板绑定 |

每个属性应至少包含：

```json
{
  "code": "fabric",
  "data_type": "enum",
  "scope": "product",
  "localized": true,
  "required_for_publish": true,
  "filterable": true,
  "multiple": false
}
```

这表示：

- 属性代码是 `fabric`。
- 属于枚举。
- 作用于 Product。
- 展示值可以翻译。
- 发布商品前必须填写。
- 允许作为筛选条件。
- 只能选择一个值。

### 6.2 属性必须有明确数据类型

第一阶段支持：

| 类型 | 用途 |
|---|---|
| string | 普通文本 |
| integer | 整数 |
| decimal | 数值和规格 |
| boolean | 是/否 |
| date | 日期 |
| enum | 枚举 |
| multi_enum | 多选枚举 |
| measurement | 数值和单位 |
| media_reference | 引用媒体 |

实际存储可使用多个类型化字段，并通过约束保证取值有效。

例如测量数据使用精确数值和单位编码，而不是直接保存 `"220ml"` 这个无法可靠换算的字符串。

高频筛选属性需要建立有针对性的索引。

PostgreSQL 18 的 JSONB 支持 GIN 索引，但官方也说明通用索引与表达式索引具有不同的存储和查询代价。因此不应该给所有 JSONB 字段无差别建立 GIN 索引。([PostgreSQL JSON 文档](https://www.postgresql.org/docs/18/datatype-json.html))

### 6.3 行业模板与页面模板必须分离

建议分别定义：

**Attribute Template**

描述商品应该具有什么数据。

**Product Page Template**

描述这些数据应该怎样展示。

例如服装行业属性模板包含：

```text
颜色
尺码
面料
版型
适用季节
洗护说明
```

服装商品详情模板包含：

```text
商品图片画廊
商品标题
价格
颜色选择器
尺码选择器
尺码表
购买按钮
商品详情
相关推荐
```

用户更换 UI 主题时，不应该丢失已经填写的服装属性。

同样，Agent 应该能够将家具商品绑定家具属性模板，而无需改变网站渲染引擎的代码。

### 6.4 商品类型支持自定义

不能把服装、香薰、家具等行业写死在 Go 代码里。

应允许管理员通过 API 创建商品类型和属性模板。

但是，自定义模板只能使用系统提供的属性数据类型与校验规则。

如果未来增加一种新的底层属性类型，例如复杂的材料配方结构，才需要相应的服务端能力升级。

这保证了普通商家可以自由扩展数据模型，同时不需要执行任意数据库 DDL。

## 七、数据库关键约束：给出可实施的 SQL

下面是核心关系的 PostgreSQL 18 DDL 示例。

它用于固定键、外键、索引和 RLS 的设计方式，并非整个项目的完整迁移脚本。

```sql
CREATE TABLE tenants (
    id UUID PRIMARY KEY DEFAULT uuidv7(),
    name TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE products (
    tenant_id UUID NOT NULL REFERENCES tenants(id),
    id UUID NOT NULL DEFAULT uuidv7(),
    product_code TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'draft',
    revision BIGINT NOT NULL DEFAULT 1,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    PRIMARY KEY (tenant_id, id),

    UNIQUE (tenant_id, product_code),

    CHECK (status IN (
        'draft',
        'active',
        'archived'
    ))
);

CREATE TABLE product_variants (
    tenant_id UUID NOT NULL,
    id UUID NOT NULL DEFAULT uuidv7(),
    product_id UUID NOT NULL,
    sku TEXT NOT NULL,
    option_key TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    PRIMARY KEY (tenant_id, id),

    FOREIGN KEY (tenant_id, product_id)
        REFERENCES products(tenant_id, id),

    UNIQUE (tenant_id, product_id, option_key)
);

CREATE UNIQUE INDEX ux_variant_sku
ON product_variants (
    tenant_id,
    upper(btrim(sku))
);

CREATE INDEX idx_variant_product
ON product_variants (
    tenant_id,
    product_id
);
```

### 为什么使用复合键？

`product_variants` 不只是通过 `product_id` 引用商品。

它使用：

```sql
FOREIGN KEY (tenant_id, product_id)
REFERENCES products(tenant_id, id)
```

这使数据库本身能够阻止变体错误地引用另一个租户的商品。

PostgreSQL 官方支持复合唯一约束、复合外键和部分唯一索引。([PostgreSQL 18 约束文档](https://www.postgresql.org/docs/18/ddl-constraints.html))

### 为什么使用 UUIDv7？

PostgreSQL 18 原生提供 `uuidv7()`。

它能够生成具有时间排序特征的 UUID，适合作为分布式环境中不依赖集中分配的资源标识。([PostgreSQL 18 Release Notes](https://www.postgresql.org/docs/18/release-18.html))

但 UUIDv7 不代表数据库查询天然具有更高性能。索引、数据局部性和查询计划仍需要通过实际测试判断。

### RLS 的实现

```sql
ALTER TABLE products
ENABLE ROW LEVEL SECURITY;

ALTER TABLE products
FORCE ROW LEVEL SECURITY;

CREATE POLICY products_tenant_policy
ON products
TO app_runtime
USING (
    tenant_id =
    nullif(
        current_setting('app.tenant_id', true),
        ''
    )::uuid
)
WITH CHECK (
    tenant_id =
    nullif(
        current_setting('app.tenant_id', true),
        ''
    )::uuid
);
```

其他租户业务表采用相应策略，并根据角色与操作类型收紧权限。

Go 应用必须在可信身份验证后，在数据库事务内部设置租户上下文。

不能让客户端或 Agent 自己指定数据库会话中的租户身份。

此外，需要单独设计域名解析使用的受限只读路径，因为公开请求在解析域名之前尚不知道 `tenant_id`。

**安全边界不能只依赖 RLS。** PostgreSQL 官方指出，超级用户、`BYPASSRLS` 角色以及部分表所有者访问不受普通 RLS 限制；另外，`TRUNCATE` 并不受行级安全策略保护。([PostgreSQL RLS 文档](https://www.postgresql.org/docs/18/ddl-rowsecurity.html))

因此应用运行账号必须：

- 不使用超级用户。
- 不拥有 `BYPASSRLS`。
- 不承担数据库迁移。
- 不允许 Agent 执行任意 SQL。
- 不允许未经授权直接操作内部表。

### 一个重要的实现细节

商品 SKU 的唯一性应当在**租户范围内**定义，而不是全平台范围。

同时，不能因为商品被归档就立即释放 SKU 唯一性。

否则新的商品可能复用旧订单引用过的 SKU，造成历史记录和外部系统同步混乱。

第一版建议不自动复用已使用过的 SKU 编号。

---

## 八、CMS 数据库：内容与展示分离

企业官网和博客虽然都需要富文本、图片及视频，但它们的业务身份不同。

例如博客文章可以出现在：

- 博客列表。
- 首页最新文章组件。
- 商品详情页相关推荐。
- 企业动态页面。
- 其他语言版本。

所以不能把博客正文直接存储在某个页面组件里。

### 8.1 CMS 主要表

| 表 | 作用 |
|---|---|
| `pages` | 站点页面身份 |
| `page_revisions` | 页面布局与内容版本 |
| `posts` | 博客文章身份 |
| `post_revisions` | 博客内容版本 |
| `post_categories` | 博客分类 |
| `post_tags` | 文章标签 |
| `post_publications` | 文章的发布状态与版本 |
| `company_profile_revisions` | 企业公开介绍版本 |
| `product_content_revisions` | 商品标题、描述及 SEO 内容 |
| `content_redirects` | URL 变更后的重定向 |

### 8.2 内容版本必须不可变

例如：

```text
Blog Post：post_001
    │
    ├── Revision 1：初始草稿
    ├── Revision 2：加入图片
    ├── Revision 3：修改内容
    └── Revision 4：正式发布
```

正式发布的 Revision 4 不允许原地修改。

用户再次编辑时，创建 Revision 5。

这样才能支持：

- 历史审查。
- 版本比较。
- 内容恢复。
- Agent 修改溯源。
- 多人协作。
- 发布审批。

**不可变是指版本内容不可变，不是禁止删除所有历史版本。** 历史清理需要单独的保留策略，并且不能删除仍被正式发布版本引用的内容。

### 8.3 产品描述也需要版本化

例如一个商品已经正式上架。

Agent 批量重新编写了 500 个商品的标题和详情。

正确流程应为：

```text
已发布商品内容 V1
        │
        ▼
Agent 创建 V2 草稿
        │
        ▼
质量检查 / 人工审核
        │
        ▼
发布 V2
```

期间不影响现有商品的正常销售。

商品内容发布与库存变化应分离。

对于同一商品在不同站点上的描述，第一版采用：

**租户级商品默认内容 + 站点级可选覆盖。**

既避免重复维护，又允许 B2B 采购站使用技术型文案，B2C 品牌站使用消费者导向文案。

---

## 九、媒体数据库：免费本地存储与 S3 共用

沿用 V0.2 的免费本地存储决定。

| 表 | 作用 |
|---|---|
| `storage_backends` | LocalFS、S3 等后端配置 |
| `media_blobs` | 实际二进制文件身份 |
| `media_assets` | 用户管理的图片、视频、文件 |
| `media_variants` | 缩略图、视频封面及转码版本 |
| `media_usages` | 资源引用关系 |
| `media_upload_sessions` | 上传会话 |
| `media_operations` | 文件处理、迁移、清理任务 |

商品、博客和企业资料都只引用 `media_asset_id`。

例如：

```text
media_asset_id: a123
          │
          ▼
media_blob: b456
          │
          ▼
storage_backend: local
          │
          ▼
/data/media/originals/...
```

未来迁移到 RustFS，只改变受存储迁移流程控制的 Blob 定位信息。

商品表不需要修改。

必须明确：**媒体资产 ID 是稳定的业务标识，物理存储地址不是。**

### 媒体公开权限

媒体至少区分：

- Public：公开展示。
- Private：仅授权人员访问。
- Draft：用于草稿预览。
- Restricted：受限制的企业证明材料等。

营业执照默认不应作为 Public。

商品图片需要完成上传和验证后，才可供正式页面引用。

如果采用 CDN，缓存键与公开权限必须分离；私有文件不能仅仅因为知道文件名就能够被下载。

## 十、交易数据的最小约束

尽管本轮重点是建站协议，但商品、库存和交易模型不能留下会导致未来重构的缺口。

### 10.1 定价

建议至少包含：

```text
price_lists
price_entries
volume_price_tiers
customer_groups
customer_price_list_assignments
```

价格选择依据：

```text
站点 → 销售渠道 → 市场 → 客户身份
                  → 数量 → 生效时间
```

冲突规则必须确定。

例如合同客户价格是否覆盖数量阶梯价，需要在价格引擎中明确，不允许由前端选择最低的一条价格。

金额使用精确数值类型，币种使用明确的货币编码，不使用浮点数直接计算财务金额。

### 10.2 库存

建议：

```text
inventory_locations
inventory_levels
inventory_movements
inventory_reservations
```

库存预留与订单创建必须有事务边界。

并发下单、订单取消、支付超时和重复支付通知都需要对应的幂等处理。

### 10.3 订单

订单应保存：

- 商品与 SKU 的成交快照。
- 成交价格和币种。
- 税费和折扣。
- 客户及收货信息快照。
- 支付状态。
- 履约状态。
- 订单状态历史。

未来商品改名或修改价格，不得影响历史订单的原始成交记录。

这类事实数据不能被 Agent 的普通商品编辑 API 直接覆盖。

## 十一、数据库索引与规模策略

针对 10,000 SPU、300,000 SKU 的测试数据集，第一版优先考虑以下访问路径。

| 查询场景 | 核心索引方向 |
|---|---|
| 查询商品详情 | tenant_id + product_id |
| SKU 精确查询 | tenant_id + 规范化 SKU |
| 获取商品全部 SKU | tenant_id + product_id |
| 查询站点已上架商品 | tenant_id + channel_id + status |
| 商品分类列表 | tenant_id + category_id |
| 行业属性筛选 | tenant_id + attribute_id + 类型化值 |
| 商品媒体 | tenant_id + product_id + sort_order |
| 博客列表 | site_id + locale + publish_time |
| 页面查询 | site_id + locale + 路由 |
| 客户价格查询 | price_list_id + variant_id |
| 批量任务记录 | tenant_id + job_id + status |

具体索引列序和覆盖策略必须由真实 SQL 与 `EXPLAIN (ANALYZE, BUFFERS)` 验证。

### 不建议一开始进行数据库分区

商品多并不自动意味着必须分区。

第一版先使用普通 PostgreSQL 表，结合：

- 合适的复合索引。
- Keyset Pagination。
- 批量插入与更新。
- 大批量导入的暂存表。
- 查询计划分析。
- 必要的搜索索引。

需要说明的是，PostgreSQL 分区表的唯一约束受到分区键限制，过早分区可能增加 SKU 唯一性和跨分区关系的复杂度。([PostgreSQL 18 分区文档](https://www.postgresql.org/docs/18/ddl-partitioning.html))

后续如果订单事件、审计日志等追加型数据增长明显，可以优先评估对这些表按时间分区。

商品核心表不预先分片。

### 批量任务与数据库事务

推荐：

**短事务 + 分批处理 + 幂等执行。**

例如导入 5,000 个 SPU：

1. 文件解析后写入暂存区。
2. 执行完整的数据校验。
3. 计算新增、更新和冲突差异。
4. 经授权提交后按商品聚合成批次。
5. 每个批次执行独立事务。
6. 记录成功或失败结果。
7. 异步更新搜索及页面缓存。

不能在一个长事务中连续处理几千张商品图片，也不能由 HTTP 请求一直等待整个导入任务完成。

River 官方支持在同一 PostgreSQL 事务中提交业务修改与后台任务，适合这种可靠异步处理模式。([River Transactional Enqueueing](https://riverqueue.com/docs/transactional-enqueueing))

# 第三部分：ARCH-004 V1 可编程建站协议

## 十二、重新定义“模板”

我建议把网站模板体系明确分为五个概念。

| 概念 | 职责 | 是否可通过普通 API 修改 |
|---|---|---|
| Theme Package | 提供实际组件代码和基础视觉资源 | 安装操作受控 |
| Design Tokens | 颜色、字体、间距、尺寸 | 可以 |
| Component Instance | 页面上的一个组件实例 | 可以 |
| Page Template | 页面结构及默认数据绑定 | 可以 |
| Site Release | 一组已经验证并发布的网站配置 | 通过发布 API |

这五个概念不能混成一张 `templates` 表。

### 12.1 Theme Package

Theme Package 是开发者提供的主题包。

例如：

```text
themes/
└── fashion-minimal/
    ├── manifest.json
    ├── tokens.schema.json
    ├── templates/
    │   ├── home.json
    │   ├── product.json
    │   └── blog.json
    ├── components/
    │   ├── Hero.astro
    │   ├── ProductGrid.astro
    │   ├── ProductGallery.astro
    │   └── ProductCard.astro
    └── assets/
```

主题包声明它依赖哪些组件和组件版本。

主题安装阶段应验证：

- Manifest 结构。
- 组件是否存在。
- 组件版本是否兼容。
- Design Tokens 是否有效。
- 是否包含不允许的资源或权限要求。

普通主题配置操作不需要重新编译。

**安装新的可执行组件代码则属于软件部署行为。**

这一区分能够避免把 API 修改页面变成远程执行任意代码的漏洞。

## 十三、Component Registry：所有组件的统一定义

### 13.1 每个组件必须拥有稳定标识

例如：

```text
core.hero@1
core.rich-text@1
core.image@1
core.video@1

catalog.product-grid@1
catalog.product-gallery@1
catalog.variant-selector@1
catalog.price-display@1

company.profile@1
company.contact-list@1
company.factory-gallery@1

blog.post-list@1
blog.article-body@1

b2b.quote-form@1
b2c.add-to-cart@1
```

这里的 `@1` 代表组件契约的主版本，而不是组件的业务实例 ID。

同一种组件可以在一个页面上出现多次。

### 13.2 组件定义需要包含什么？

```json
{
  "type": "catalog.product-grid",
  "major_version": 1,
  "display_name": "商品网格",
  "category": "commerce",
  "render_mode": "server",
  "props_schema": "catalog.product-grid.props.v1",
  "binding_schema": "catalog.product-grid.binding.v1",
  "slots": {},
  "capabilities": [
    "catalog.read"
  ]
}
```

每个组件定义包括：

- 类型。
- 契约版本。
- 属性 Schema。
- 可用数据绑定。
- 支持的子组件槽位。
- 默认配置。
- 响应式规则。
- 渲染实现。
- 所需能力。

建议使用 JSON Schema Draft 2020-12 验证页面和组件配置。该规范提供明确的对象、数组、引用和组合验证机制。([JSON Schema 官方规范](https://json-schema.org/draft/2020-12/))

但 JSON Schema 只负责配置结构和类型的一部分。

例如：

某个组件引用的商品分类是否真实存在，仍需要业务服务执行语义校验。

### 13.3 组件属性必须受 Schema 控制

例如商品网格：

```json
{
  "type": "object",
  "properties": {
    "columns_desktop": {
      "type": "integer",
      "minimum": 1,
      "maximum": 6
    },
    "columns_mobile": {
      "type": "integer",
      "minimum": 1,
      "maximum": 2
    },
    "show_price": {
      "type": "boolean"
    }
  },
  "required": [
    "columns_desktop",
    "columns_mobile"
  ],
  "additionalProperties": false
}
```

这样：

```json
{
  "columns_desktop": 4,
  "columns_mobile": 2,
  "show_price": true
}
```

属于有效配置。

而：

```json
{
  "columns_desktop": 5000
}
```

不符合约束。

Agent 和普通用户都不能绕过组件 Schema。

## 十四、页面结构：采用节点图，而不是巨大 HTML

我建议把页面表示为**有根、有界的组件树**。

数据库中使用 JSONB 保存经过验证的页面结构。

但在 API 层采用稳定的 Node ID，避免每次调整组件顺序就重写复杂的嵌套数组路径。

### 14.1 一个完整首页配置示例

```json
{
  "schema_version": 1,
  "root_id": "root",
  "nodes": {
    "root": {
      "component": "core.page-layout@1",
      "props": {},
      "slots": {
        "main": [
          "hero",
          "new-arrivals"
        ]
      }
    },
    "hero": {
      "component": "core.hero@1",
      "props": {
        "title": {
          "en": "New Collection",
          "zh-CN": "全新系列"
        },
        "image_id": "media_001",
        "layout": "split"
      },
      "slots": {}
    },
    "new-arrivals": {
      "component": "catalog.product-grid@1",
      "props": {
        "columns_desktop": 4,
        "columns_mobile": 2,
        "show_price": true
      },
      "binding": {
        "resolver": "catalog.collection-products@1",
        "params": {
          "collection_id": "collection_001",
          "limit": 8
        }
      },
      "slots": {}
    }
  }
}
```

这个 JSON 是页面配置的**示意格式**，其中资源 ID 应由正式 API 返回真实标识。

### 14.2 为什么采用节点图？

因为它支持用户和 Agent 以相同方式操作页面。

例如：

**操作一：修改标题**

只修改 `hero.props.title`。

**操作二：增加视频组件**

向 `nodes` 增加一个视频节点，再把其 ID 加入父组件对应的 Slot。

**操作三：移动商品网格**

调整 `root.slots.main` 中的节点顺序。

**操作四：更换商品集合**

只修改 `new-arrivals.binding.params.collection_id`。

不需要重新编译网站，也不需要重新生成商品数据。

### 14.3 页面图必须满足的约束

建议至少保证：

1. 必须存在一个 Root。
2. Node ID 在页面内唯一。
3. 不允许循环引用。
4. 一个节点默认只能属于一个父槽位。
5. Slot 只能包含组件声明允许的子组件类型。
6. 组件属性必须通过对应 Schema。
7. Resolver 必须存在且版本兼容。
8. 媒体、商品和分类引用必须通过授权与存在性验证。
9. 不允许未声明的任意 JavaScript。
10. 限制节点总量、层级深度和数据查询预算。

其中节点数量、深度和查询预算需要做成可配置限制，并通过性能测试决定默认值。

不能因为页面数据存储为 JSONB，就允许用户构造无限递归组件或无限数据查询。

### 14.4 页面文本与多语言

V1 建议：

**页面结构默认跨语言共享，组件中的可翻译字段按 Locale 保存。**

例如示例里的：

```json
"title": {
  "en": "New Collection",
  "zh-CN": "全新系列"
}
```

渲染时根据网站当前语言选择相应内容。

缺少翻译时，根据网站配置的回退语言处理。

更复杂的不同语言布局，可以在后续引入局部覆盖，但第一版不需要为每种语言复制完整组件树。

产品标题、描述和博客正文则由对应内容领域管理自己的多语言版本。

这样可以避免同一段内容分别存在于商品数据库和页面组件配置中。

## 十五、Data Resolver：连接业务数据与页面组件

这是 V0.3 最关键的新增模块。

**页面组件不直接查询数据库，也不接受用户指定的任意 SQL。**

它通过一个标准数据解析接口获得需要的数据。

### 15.1 Data Resolver 架构

```text
                Astro Renderer
                      │
                      ▼
                 Page Document
                      │
                      ▼
                Component Tree
                      │
                      ▼
                Data Bindings
                      │
                      ▼
              Data Resolver Registry
                      │
          ┌───────────┼────────────┐
          │           │            │
          ▼           ▼            ▼
      Catalog      Company       CMS
      Resolver     Resolver     Resolver
          │           │            │
          └───────────┼────────────┘
                      │
                      ▼
                 Go Read API
                      │
                      ▼
                 PostgreSQL
```

### 15.2 标准 Resolver

第一批应提供：

| Resolver | 数据来源 | 使用场景 |
|---|---|---|
| `catalog.product@1` | 单个商品 | 商品详情 |
| `catalog.collection-products@1` | 商品集合 | 首页新品 |
| `catalog.category-products@1` | 分类商品 | 分类页面 |
| `catalog.related-products@1` | 关联商品 | 商品推荐 |
| `company.profile@1` | 企业资料 | 关于我们 |
| `company.contacts@1` | 联系资料 | 联系页面 |
| `company.gallery@1` | 企业媒体 | 工厂展示 |
| `blog.latest-posts@1` | 最新文章 | 首页新闻 |
| `blog.related-posts@1` | 相关文章 | 博客详情 |
| `site.navigation@1` | 导航配置 | Header/Footer |

### 15.3 Resolver 必须有输入和输出 Schema

例如：

```json
{
  "resolver": "catalog.collection-products@1",
  "params": {
    "collection_id": "collection_001",
    "limit": 8
  }
}
```

Go 后端负责：

1. 校验 Resolver 类型。
2. 校验参数。
3. 验证 Collection 属于当前 Tenant。
4. 验证商品在当前站点已上架。
5. 根据 Market 与 Locale 获取可展示数据。
6. 返回统一的商品展示模型。

前端组件不需要知道数据来自多少张 PostgreSQL 表。

这让业务数据模型以后可以调整，而不必修改所有主题组件。

### 15.4 建立统一的 View Model

例如商品列表组件不应该直接收到完整的商品数据库记录。

它只需要：

```json
{
  "id": "product_001",
  "title": "Classic Shirt",
  "url": "/products/classic-shirt",
  "image": {
    "id": "media_001",
    "alt": "Classic Shirt"
  },
  "price": {
    "amount": "89.00",
    "currency": "USD"
  },
  "availability": "available"
}
```

这是公开商品卡片模型的示意。

对于 B2B 站点，价格可能是：

```json
{
  "price": null,
  "price_display": "request_quote"
}
```

但这仅决定如何展示。

是否允许查看合同价、请求报价和提交订单，仍由后端授权与定价服务决定。

**隐藏前端组件不等于完成权限控制。**

### 15.5 避免 N+1 查询

假设首页有：

- 8 个新品。
- 8 个热卖商品。
- 8 个推荐商品。

错误做法是每张商品卡片单独调用一次 API。

正确方法是：

**批量解析组件依赖 → 合并查询 → 批量获取商品和媒体 → 返回页面所需 View Model。**

可以设计内部接口：

```http
POST /internal/v1/render-context
```

输入包含服务端确认的：

```text
Tenant
Site
Release
Route
Locale
Market
Audience
```

以及待解析的组件绑定。

输出一份经过权限过滤的页面渲染数据。

该接口只允许可信的 Storefront 服务调用，不作为直接对公网开放的通用查询接口。

同时应限制单次页面渲染中 Resolver 数量、嵌套深度、查询数量及超时时间，防止复杂模板导致数据库过载。

# 第四部分：模板继承与版本发布

## 十六、商品详情模板继承

现在解决一个很现实的问题：

**10,000 个商品怎样使用不同的页面模板，而不需要逐个配置？**

建议采用以下优先级：

```text
商品专属模板
      ↓ 不存在
商品主分类模板
      ↓ 不存在
商品类型模板
      ↓ 不存在
站点默认商品模板
      ↓ 不存在
主题默认商品模板
```

举例：

```text
Fashion Theme
    │
    └── 默认商品详情模板
             │
             ├── 上衣模板
             │     └── Shirt-001 专属覆盖
             │
             ├── 裤装模板
             │
             └── 鞋类模板
```

如果一个商品属于多个分类，必须明确其主分类或显式指定模板，避免因分类排序不同导致页面模板不稳定。

模板继承也不应该采用复杂的任意 JSON 深层合并。

建议第一版支持：

- 完全继承上层模板。
- 显式选择另一个模板。
- 对组件属性进行有限、类型化的覆盖。
- 对组件槽位进行受约束的调整。

这样更容易实现确定性渲染、升级兼容和版本回滚。

### 16.1 模板变更不需要修改全部商品

例如修改服装详情页模板：

将：

```text
图片区 / 商品信息
尺码表
商品描述
相关推荐
```

变成：

```text
图片区 / 商品信息
尺码表
视频展示
商品描述
相关推荐
```

只需要发布新的模板版本。

使用该模板的商品会在后续渲染中采用新布局，不需要更新每个 Product。

这能避免大规模商品场景下大量无意义的数据库写入。

## 十七、Site Release：整个网站统一发布

### 17.1 数据库设计

建议增加：

| 表 | 用途 |
|---|---|
| `site_drafts` | 当前网站修改草稿 |
| `site_releases` | 不可变的发布版本 |
| `site_release_pages` | 本次发布使用哪些页面版本 |
| `site_release_routes` | 本次发布的页面路径 |
| `site_settings_revisions` | 网站设置版本 |
| `navigation_revisions` | 导航版本 |
| `theme_installations` | 已安装主题及兼容版本 |
| `site_publish_events` | 发布与回滚记录 |

`sites` 表维护：

```text
published_release_id
```

用于确定正式网站当前使用哪个版本。

### 17.2 发布流程

假设正式网站使用 Release 12。

Agent 需要修改首页、导航和联系页面。

```text
                 Published Release 12
                          │
                          ▼
                     Site Draft
                          │
            ┌─────────────┼─────────────┐
            │             │             │
            ▼             ▼             ▼
          首页           导航        联系页面
          V13            V8            V5
            │             │             │
            └─────────────┼─────────────┘
                          │
                          ▼
                     Validation
                          │
                          ▼
                     Preview
                          │
                          ▼
                    Publish Plan
                          │
                          ▼
                PostgreSQL Transaction
                          │
                          ▼
                 Published Release 13
```

发布前必须验证：

| 检查项 | 必须通过 |
|---|---|
| 组件存在 | 所有组件可被当前 Renderer 加载 |
| 版本兼容 | 组件配置与实现兼容 |
| 页面结构 | 组件树没有循环和无效引用 |
| 数据绑定 | Resolver 参数正确 |
| 媒体引用 | 正式媒体已经 READY |
| 站点路由 | 没有 URL 冲突 |
| 导航链接 | 内部目标存在并可公开访问 |
| 访问控制 | 没有意外暴露私有内容 |
| 主题依赖 | 主题包和组件版本仍然可用 |
| 发布权限 | 调用者具有发布权限 |
| 版本冲突 | 正式版本未被其他操作覆盖 |

### 17.3 发布必须使用数据库事务

逻辑上：

```sql
BEGIN;

-- 锁定站点发布状态
SELECT published_release_id
FROM sites
WHERE tenant_id = $1
  AND id = $2
FOR UPDATE;

-- 检查当前 Release 是否等于草稿的基础版本

-- 插入新的 Site Release
-- 插入页面、导航、路由等不可变版本引用
-- 写入发布审计和事务性事件

-- 切换正式发布指针
UPDATE sites
SET published_release_id = $3
WHERE tenant_id = $1
  AND id = $2;

COMMIT;
```

这是事务流程示意，正式 SQL 还要包含发布版本检查、全部关系约束和错误处理。

如果发布失败，数据库事务回滚，正式网站继续使用旧版本。

如果成功，后续请求读取新的 Release。

单次 SSR 请求应锁定它所使用的 `release_id`，不能在同一个页面渲染过程中同时读取新旧两个网站布局版本。

### 17.4 必须划清 Site Release 的范围

第一版建议 Site Release 管理：

- 主题安装版本。
- Design Tokens。
- 静态页面。
- 页面模板。
- 导航。
- 站点设置。
- 网站 SEO 与路由配置。

商品实时库存、价格和订单不属于 Site Release。

博客及商品内容拥有自己的发布版本。如果一次操作必须同时发布博客和导航，发布服务应在同一数据库事务内提交对应版本指针，并在审计中记录关联关系。

**站点回滚默认回滚网站结构和配置，不自动撤销已经发生的订单、库存变化或商品成交。**

独立发布的博客也不应被一次普通主题回滚意外撤销。

### 17.5 发布后缓存如何更新？

建议采用：

```text
Site Release Commit
          │
          ▼
   Transactional Event
          │
          ▼
   Cache Invalidation
          │
          ▼
    New SSR Response
```

缓存键包含：

```text
site_id
release_id
locale
market
route
public_audience_segment
```

同时使用商品、分类及内容资源标签处理业务内容更新。

Astro 当前官方文档支持按路由缓存、标签和失效控制，但具体能力取决于所配置的缓存提供者。第一版不应强制引入分布式缓存。([Astro Route Caching](https://docs.astro.build/en/guides/caching/))

需要区分两种一致性：

**数据库发布指针可以原子切换。**

**浏览器、反向代理和 CDN 已缓存的响应可能存在短暂传播延迟。**

不能把后者错误地宣传成严格瞬时一致。

# 第五部分：API 与 Agent 的统一操作协议

## 十八、建站 API 设计

我建议明确划分：

- 组件查询。
- 草稿修改。
- 校验。
- 预览。
- 发布。
- 历史版本和回滚。

### 18.1 组件 API

```http
GET /api/v1/components

GET /api/v1/components/{type}

GET /api/v1/themes

GET /api/v1/themes/{id}
```

返回组件 Schema、可用参数、预设模板及版本信息。

### 18.2 网站草稿 API

```http
POST /api/v1/sites/{site_id}/drafts

GET /api/v1/sites/{site_id}/drafts/{draft_id}

PATCH /api/v1/sites/{site_id}/drafts/{draft_id}/pages/{page_id}
```

页面修改可以使用受支持的 JSON Patch 操作，并结合 ETag 实现乐观并发控制。

例如：

```http
PATCH /api/v1/sites/site_001/drafts/draft_001/pages/home
Content-Type: application/json-patch+json
If-Match: "revision-12"
```

请求：

```json
[
  {
    "op": "replace",
    "path": "/nodes/hero/props/title/en",
    "value": "Autumn Collection"
  }
]
```

这里的修改对象是经过验证的页面配置。

不是直接修改前端源码或数据库中的任意字段。

### 18.3 页面组件操作

对于更复杂的可视化编辑，建议另外提供高级领域操作，例如：

```http
POST /api/v1/sites/{site_id}/drafts/{draft_id}/operations
```

支持：

```text
component.add
component.remove
component.move
component.configure
component.bind
template.assign
theme.configure
navigation.update
```

这种操作方式比要求 Agent 自行维护大型 JSON Pointer 更稳定。

例如增加一个商品组件，API 可以负责生成 Node ID、校验 Slot 和绑定集合。

### 18.4 预览和发布 API

```http
POST /api/v1/sites/{site_id}/drafts/{draft_id}/validate

POST /api/v1/sites/{site_id}/drafts/{draft_id}/preview

POST /api/v1/sites/{site_id}/drafts/{draft_id}/publish

GET  /api/v1/sites/{site_id}/releases

POST /api/v1/sites/{site_id}/releases/{release_id}/restore
```

预览必须和正式站使用相同的核心渲染器。

不能在后台编辑器自己模拟一套近似的 HTML，导致预览和正式发布后的结果不同。

建议使用隔离的预览入口和短期授权凭证，并禁止搜索引擎索引草稿预览。

### 18.5 API 错误必须机器可读

例如：

| HTTP 状态 | 错误码 | 含义 |
|---|---|---|
| 400 | `INVALID_REQUEST` | 请求格式错误 |
| 403 | `SCOPE_DENIED` | 权限不足 |
| 404 | `RESOURCE_NOT_FOUND` | 资源不可访问或不存在 |
| 409 | `VERSION_CONFLICT` | 草稿基线过期 |
| 409 | `ROUTE_CONFLICT` | URL 冲突 |
| 422 | `INVALID_PAGE_GRAPH` | 页面结构校验失败 |
| 422 | `INVALID_BINDING` | 数据绑定错误 |
| 429 | `RATE_LIMITED` | 超过资源预算 |

同一错误结构必须被管理后台、SDK 和 Agent 共用。

## 十九、Agent 操作网站的完整流程

假设用户要求：

> 将官网改成黑白极简风格，首页增加新品展示和企业介绍，底部添加 WhatsApp 联系按钮，并发布一篇秋季新品博客。

Agent 应当执行：

```text
读取网站当前状态
        │
        ▼
读取已安装主题及组件 Schema
        │
        ▼
查询可用商品、企业资料及媒体
        │
        ▼
创建 Site Draft
        │
        ├── 更新 Design Tokens
        ├── 创建商品展示组件
        ├── 绑定新品 Collection
        ├── 增加企业资料组件
        ├── 配置 WhatsApp 入口
        └── 创建博客草稿
        │
        ▼
验证所有修改
        │
        ▼
生成 Diff 与预览
        │
        ▼
根据权限要求进行审批
        │
        ▼
发布 Site Release
        │
        ▼
返回发布结果与审计记录
```

### 19.1 Agent 不应拥有特殊修改通道

它和后台使用同一套领域服务。

差异只有调用身份和权限范围。

例如：

| 操作 | 常规 Agent 权限 |
|---|---|
| 查询商品 | 允许 |
| 创建商品草稿 | 允许 |
| 批量补全商品资料 | 按授权范围允许 |
| 修改页面草稿 | 允许 |
| 生成预览 | 允许 |
| 正式发布网站 | 根据发布权限或审批策略 |
| 修改客户合同价 | 需要专项授权 |
| 修改企业营业执照文件 | 需要专项授权 |
| 修改支付收款账户 | 使用更严格的独立权限流程 |
| 修改历史订单成交金额 | 普通管理接口不允许 |

### 19.2 Agent 修改必须产生结构化差异

例如：

```json
{
  "operation": "page.update",
  "resource": "home",
  "base_revision": 12,
  "changes": [
    {
      "field": "hero.title.en",
      "before": "Summer Collection",
      "after": "Autumn Collection"
    }
  ],
  "validation": "passed",
  "status": "awaiting_publish"
}
```

这样用户可以直接审核到底修改了什么。

系统也能支持 Agent 执行失败后的问题定位。

### 19.3 Agent 批量操作必须能恢复

例如批量修改 20,000 个商品 SKU。

任务应该有：

```text
Job
 ├── Input Snapshot
 ├── Validation Results
 ├── Approved Change Set
 ├── Execution Batches
 ├── Item-level Results
 ├── Retry State
 └── Audit Trail
```

如果处理到第 12,000 条时服务器重启：

- 前 12,000 条中已经提交的成功记录保留。
- 未完成记录重新进入待处理状态。
- 使用幂等键识别已经完成的操作。
- 失败项能够独立重新校验和执行。

不能简单地从第一条重新导入并重复创建商品。

# 第六部分：网站渲染架构

## 二十、Astro 如何真正渲染数据库中的页面

这是决定方案是否能落地的最后一个关键环节。

建议使用一套通用的 Astro 动态页面入口。

### 20.1 运行过程

```text
访问 https://shop.example.com/products/shirt-001
                        │
                        ▼
                   Caddy
                        │
                        ▼
               Astro Storefront
                        │
                        ▼
                  Route Resolver
                        │
             ┌──────────┴──────────┐
             │                     │
             ▼                     ▼
       Domain → Site          Route → Resource
             │                     │
             └──────────┬──────────┘
                        │
                        ▼
                 Published Release
                        │
                        ▼
                Template Resolution
                        │
                        ▼
                Component Tree
                        │
                        ▼
                Data Resolver Batch
                        │
                        ▼
                  HTML Rendering
                        │
                        ▼
                 Browser / Cache
```

请求从经过验证的域名确定站点。

再根据路径确定访问的是首页、商品、博客还是其他页面。

之后读取对应的页面模板和业务数据。

### 20.2 URL 路由必须统一管理

建议第一版保留系统路由命名空间。

例如：

```text
/
/products/{slug}
/collections/{slug}
/blog/{slug}
/pages/{slug}
/cart
/checkout
/account
```

企业可以通过页面编辑器创建其他自定义页面路径。

但不允许自定义内容占用支付、账户、系统 API 和静态资源等保留路由。

必须有统一路由注册与冲突检测，而不是让 Astro 路由和 Go API 各自决定同一个 URL 的含义。

### 20.3 不为一万个商品生成一万个源代码页面

Astro 的按需动态路由能够在收到请求时根据路径获取商品数据，不需要在构建阶段枚举所有商品。([Astro Routing](https://docs.astro.build/en/guides/routing/))

因此可以使用类似：

```text
src/pages/[...path].astro
```

的通用入口，再由业务 Route Resolver 判断当前页面类型。

实际实现中，购物车、账户、结算等保留路径可以采用明确的专用路由。

### 20.4 渲染层不应该直接连接 PostgreSQL

我建议第一版坚持：

**Astro 通过内部 Go Read API 获取页面数据。**

而不是让 Astro 直接使用 PostgreSQL 凭证。

这样能够得到三个好处：

第一，所有数据查询仍然由 Go 统一管理权限和业务规则。

第二，未来可以更换前端渲染器，而不用重新开发业务查询逻辑。

第三，Agent、管理后台和 Storefront 可以共享经过正式定义的数据模型。

代价是 Go 和 Astro 之间多了一次服务调用。

应通过批量 Render Context、连接复用和缓存控制成本，而不是每个组件发一次网络请求。

### 20.5 Bun 在这里如何使用？

V0.3 暂时维持：

- Bun：前端依赖、脚本和测试工具链。
- Astro：店铺 SSR 渲染。
- Go：核心业务 API。
- Node.js：初期正式 SSR 运行时基线。

Bun 运行 Astro SSR 可以进入独立验证，但暂不视为已通过。

Astro 官方明确提示 Bun 环境可能遇到部分集成兼容问题。([Astro 官方 Bun 指南](https://docs.astro.build/en/recipes/bun/))

是否最终使用 Bun 执行 SSR，应根据同一应用的兼容性、吞吐、内存和稳定性测试决定。

# 第七部分：实现顺序与工程验收

## 二十一、第一批真正应该开发的模块

根据 V0.3，我建议先完成六个纵向闭环，而不是按数据库、后端、前端分别开发到很后面才集成。

| 顺序 | 开发闭环 | 必须交付 |
|---|---|---|
| 1 | Tenant + Site | 创建网站、域名解析、权限隔离 |
| 2 | Catalog + Media | 商品、SKU、属性、LocalFS 上传 |
| 3 | Component Registry | 注册组件、Schema、渲染组件 |
| 4 | Page + Data Resolver | 通过 API 创建页面并绑定商品 |
| 5 | Draft + Release | 修改、预览、发布、回滚 |
| 6 | Agent + Bulk | 批量商品操作和网站草稿修改 |

这六个闭环完成后，系统就具备实际建站平台的基础形态。

不必等支付、物流、优惠券和完整 CRM 开发完毕才验证模板架构。

## 二十二、V0.3 验收矩阵

| 编号 | 验收要求 | 预期结果 |
|---|---|---|
| DB-01 | 两个租户使用相同 SKU | 数据互不冲突 |
| DB-02 | SKU 跨租户错误引用商品 | 数据库拒绝 |
| DB-03 | 同商品重复规格组合 | 数据库与领域服务拒绝 |
| DB-04 | 修改已发布商品描述 | 创建新内容版本 |
| DB-05 | 归档商品 | 历史订单仍可追溯 |
| DB-06 | LocalFS 迁移到 S3 | Media ID 不变 |
| UI-01 | API 创建首页 | Astro 正确渲染 |
| UI-02 | API 更换 Banner 图片 | 无需重新构建 |
| UI-03 | API 修改商品网格绑定 | 新商品正确显示 |
| UI-04 | 调整商品模板 | 商品数据不发生批量写入 |
| UI-05 | 提交循环组件树 | 校验失败 |
| UI-06 | 使用不存在的 Resolver | 校验失败 |
| UI-07 | 不同租户引用私有媒体 | 授权拒绝 |

应在实际开发时转化为单元测试、数据库集成测试和端到端测试。

# 第八部分：下一轮仍需要解决的问题

经过 V0.3，数据库和模板协议之间的核心关系已经明确。

但还不能认为整个系统的技术规格已经完整。

接下来存在三个更深层的问题。

### 问题一：页面编辑器如何做到真正可视化？

我们已经定义页面为组件树。

但管理后台还需要：

- 组件拖拽。
- 选中编辑。
- 响应式布局。
- 即时预览。
- 图片上传。
- 属性面板自动生成。
- 撤销和重做。
- 组件复制。
- 模板保存。
- 主题切换。
- 页面发布。

这里最重要的是：**可视化编辑器不应再发明另一套页面模型，而应直接操作 V0.3 定义的 Page Document。**

下一轮需要确定 UI 编辑器的状态模型、操作协议、预览同步和错误恢复。

### 问题二：多行业模板怎样真正形成生态？

现在可以表示商品属性和页面组件。

但还需要建立正式的行业模板包：

```text
Industry Package
├── Product Type Definitions
├── Attribute Templates
├── Category Presets
├── Page Templates
├── Component Presets
├── SEO Defaults
└── Import Mapping Rules
```

例如安装服装行业模板后，自动获得：

尺码、颜色、版型、面料、尺码表、服装商品详情、分类筛选和 Excel 导入映射。

安装香薰行业模板后，自动获得：

容量、香型、扩香方式、包装规格、MOQ、阶梯报价和 B2B 询盘页面组件。

行业模板应该是**数据和配置包**，尽可能复用已经注册的底层组件。

### 问题三：Agent 如何自动创建完整网站？

当前 Agent 已经能够修改页面配置。

下一步应该设计完整的建站计划：

```text
用户需求
   ↓
网站结构规划
   ↓
选择行业模板
   ↓
创建商品属性体系
   ↓
导入商品与媒体
   ↓
生成企业介绍和博客草稿
   ↓
选择主题
   ↓
组合页面组件
   ↓
校验数据绑定
   ↓
生成预览
   ↓
人工确认
   ↓
网站发布
```

其中最关键的不是让 AI 生成代码，而是让 AI 产生**能够被系统验证、比较、执行和恢复的建站操作计划**。

这样即使换成其他 Agent 或 AI 模型，也可以使用同一套平台能力。

## V0.3 最终架构结论

截至这一轮，我建议将整个项目的长期核心收敛为：

```text
                 OpenSite Commerce
                        │
          ┌─────────────┼─────────────┐
          │             │             │
          ▼             ▼             ▼
      React Admin    Astro SSR     AI Agent
          │             │             │
          └─────────────┼─────────────┘
                        │
                        ▼
                 Unified Go API
                        │
          ┌─────────────┼─────────────┐
          │             │             │
          ▼             ▼             ▼
       Business      Content       Site
       Services      Revision      Release
          │             │             │
          └─────────────┼─────────────┘
                        │
                        ▼
                  PostgreSQL
                        │
          ┌─────────────┼─────────────┐
          │             │             │
          ▼             ▼             ▼
       Catalog        CMS        Presentation
          │             │             │
          └─────────────┼─────────────┘
                        │
                        ▼
                 Media Service
                        │
                LocalFS / S3
```

**这一轮固定下来的关键设计是：**

商品、企业、博客属于业务数据；模板和组件属于展示配置；Site Release 决定正式网站使用哪些配置版本；Data Resolver 负责安全地把业务数据提供给前端。

React 管理后台和 Agent 使用同一套 API，因此二者拥有相同的操作能力与业务约束。

用户可以自由组合已经安装的组件和模板，但不需要直接修改程序源码。

数据库、商品和媒体资产不依赖某个主题的存在，也不依赖任何收费云服务。

### 我的下一步建议

**V0.4 应集中完成两个规格：**

**ARCH-011：可视化 Page Builder。** 把组件选择、拖拽、编辑、预览、撤销和发布设计成真正可实现的管理后台。

**ARCH-012：行业模板与 Agent 建站协议。** 让系统能够从一份企业资料和一批商品出发，自动规划并建立完整的 B2B/B2C 网站。

这会把目前已经明确的数据库和模板协议，进一步转化为用户能够实际操作的建站产品。

目前的工作仍属于架构研究与规格设计，尚未创建仓库、执行迁移或验证运行性能。
