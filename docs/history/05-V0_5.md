# OpenSite Commerce V0.5
## 工程契约冻结：数据库迁移、OpenAPI、组件 SDK 与最小部署

**版本：V0.5 — Implementation Contract**  
**日期：2026 年 10 月 11 日**  
**状态：工程设计，尚未执行代码或数据库迁移**

经过 V0.1～V0.4，我们已经完成了业务架构、商品模型、媒体系统、模板引擎、可视化编辑器和 Agent 建站协议的总体设计。

这一轮需要改变工作方式：

**停止继续增加架构概念，开始定义能够直接交给编码代理实施、测试和验收的工程契约。**

本轮处理四份规格：

| 规格 | 内容 | 交付目标 |
|---|---|---|
| ARCH-014 | Database Migration V1 | 明确实际表结构、约束及事务 |
| ARCH-015 | OpenAPI Contract V1 | 明确接口请求、响应、错误及授权 |
| ARCH-016 | Component SDK V1 | 明确前端组件如何注册、渲染、升级 |
| ARCH-017 | Deployment & Test Harness | 明确最小部署、运行边界和验收测试 |

## 一、先纠正前四轮的五个设计风险

### 1. 不应该一次创建上百张业务表

之前的设计涵盖商品、订单、支付、物流、企业、博客、主题、Agent 等模块，方向正确，但实施范围过大。

如果第一阶段同时创建所有数据库表，很容易出现业务约束不完整、表之间关系反复修改、接口还没有实现就先积累大量无用结构的问题。

**V0.5 决定：优先完成一条可运行的纵向闭环。**

```text
创建企业
    ↓
创建网站
    ↓
创建商品及 SKU
    ↓
上传商品图片
    ↓
创建页面草稿
    ↓
配置商品展示组件
    ↓
生成真实预览
    ↓
发布网站
    ↓
访问正式商品页面
    ↓
修改并回滚页面
```

第一阶段不需要完整购物车、支付、物流和多仓库存。

但必须保留这些模块未来扩展所需的领域边界。

### 2. Site Release 只能保证数据库发布指针原子切换

之前容易将“网站原子发布”理解得过于宽泛。

真实系统中存在三类状态：

| 状态 | 一致性机制 |
|---|---|
| PostgreSQL 中的发布指针 | 数据库事务 |
| 图片和视频文件 | 文件状态机及一致性校验 |
| SSR 和 CDN 缓存 | 带版本的缓存键与失效事件 |

这三种机制不能合并成一个跨数据库、文件系统和 CDN 的全局事务。

因此，**原子发布严格指数据库内的发布版本切换**。

正式页面只引用已经通过验证的媒体和组件版本。

### 3. 多租户隔离必须覆盖外键，不仅是 RLS

所有租户业务表需要 `tenant_id`。

涉及跨表关联时，应优先使用复合外键，避免不同租户的数据发生错误引用。

PostgreSQL RLS 是第二道防线，不能代替 API 认证、对象级授权和租户作用域检查。尤其需要注意，表所有者、特殊权限角色和 `TRUNCATE` 不遵循普通行级策略的全部限制。

### 4. 页面配置和可执行组件必须分离

普通用户和 Agent 能够创建、复制、排序、配置已注册组件。

但安装新的 Astro/React 组件代码仍属于软件部署行为。

**API 编辑页面不等于 API 可以执行任意代码。**

这将成为开源主题生态最重要的安全边界。

### 5. 数据库的架构完整性不等于项目已经具备交易能力

第一阶段可以发布：

- 企业官网。
- 商品展示站。
- 产品目录。
- B2B 询盘站。
- 博客和内容网站。

但如果支付、库存预留和结算状态机尚未完成，不应声称已经支持真实 B2C 在线交易。

这不是放弃 B2C，而是将复杂交易模块放到稳定的数据与建站基础之后。

# 二、V0.5 冻结的系统边界

继续采用：

| 层级 | 技术 | 具体职责 |
|---|---|---|
| Backend | Go | 业务、认证、数据校验、API |
| Database | PostgreSQL 18 | 事务、业务数据、版本 |
| Data Access | pgx + sqlc | 显式 SQL、类型化查询 |
| Background Jobs | River | 异步处理与重试 |
| Admin | React + TypeScript | 商品后台、页面编辑器 |
| Toolchain | Bun | 前端安装、构建、测试 |

Bun 暂时不替换 Go 核心业务服务。Astro 官方也提醒，使用 Bun 作为运行时仍可能遇到集成兼容问题，因此 SSR 运行时保持独立验证。

API 规范暂定 **OpenAPI 3.1.2**，优先保证生成器、校验器和 SDK 工具链兼容。官方已经在 2026 年 9 月 10 日发布 OpenAPI 3.2.1，因此后续可以验证后升级，不应误认为 3.1 是最新版本。

# 三、ARCH-014：PostgreSQL Migration V1

## 3.1 第一批数据库范围

第一阶段先建立能够运行完整建站闭环的数据结构。

| 领域 | 第一批表 | 本阶段作用 |
|---|---|---|
| 企业 | `tenants`、`organizations` | 企业和数据归属 |
| 网站 | `sites` | 网站身份和发布状态 |
| 商品 | `products`、`product_variants` | SPU、SKU |
| 商品内容 | `product_content_revisions` | 商品内容版本 |
| 商品上架 | `product_listings` | 站点商品展示范围 |
| 媒体 | `media_blobs`、`media_assets` | 文件与媒体资源 |
| 页面 | `pages`、`page_revisions` | 可编辑页面 |
| 发布 | `site_releases`、`site_release_routes` | 原子版本切换 |
| 媒体引用 | `product_media`、`site_release_media` | 保护正在使用的图片 |
| 事件 | `outbox_events` | 缓存失效及可靠事件 |

用户身份、成员关系和会话需要独立的认证迁移，必须在公开管理 API 前实现。这里不把尚未设计完的认证系统伪装成已完成。

第一阶段不增加 Redis、独立搜索数据库或消息中间件。

## 3.2 SQL 数据结构

以下给出关键迁移的实际 SQL 结构。

这是**尚未在 PostgreSQL 实例上执行的迁移草案**，可以作为实现输入，但正式进入仓库前仍须进行数据库迁移测试。

PostgreSQL 18 已原生支持 `uuidv7()`，可以直接用于生成资源 ID。([PostgreSQL 18 官方说明](https://www.postgresql.org/docs/18/release-18.html))

### A. 企业和网站

```sql
BEGIN;

CREATE SCHEMA IF NOT EXISTS app;

CREATE TABLE app.tenants (
    id UUID PRIMARY KEY DEFAULT uuidv7(),
    name TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE app.organizations (
    tenant_id UUID NOT NULL REFERENCES app.tenants(id),
    id UUID NOT NULL DEFAULT uuidv7(),
    legal_name TEXT,
    display_name TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    PRIMARY KEY (tenant_id, id)
);

CREATE TABLE app.sites (
    tenant_id UUID NOT NULL,
    id UUID NOT NULL DEFAULT uuidv7(),
    organization_id UUID NOT NULL,
    name TEXT NOT NULL,
    published_release_id UUID,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    PRIMARY KEY (tenant_id, id),

    FOREIGN KEY (tenant_id, organization_id)
        REFERENCES app.organizations(tenant_id, id)
);
```

这里不把 `organization_id` 当成租户 ID。

一个 Tenant 可以运营多个 Site，也可以在未来扩展为多个经营主体。

第一版正常使用时，默认创建一个 Tenant 和一个 Organization。

### B. 商品和 SKU

```sql
CREATE TABLE app.products (
    tenant_id UUID NOT NULL REFERENCES app.tenants(id),
    id UUID NOT NULL DEFAULT uuidv7(),

    product_code TEXT NOT NULL,

    code_normalized TEXT
        GENERATED ALWAYS AS (
            upper(btrim(product_code))
        ) STORED,

    status TEXT NOT NULL DEFAULT 'draft',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    PRIMARY KEY (tenant_id, id),

    UNIQUE (tenant_id, code_normalized),

    CHECK (btrim(product_code) <> ''),

    CHECK (status IN (
        'draft',
        'active',
        'archived'
    ))
);

CREATE TABLE app.product_variants (
    tenant_id UUID NOT NULL,
    id UUID NOT NULL DEFAULT uuidv7(),
    product_id UUID NOT NULL,

    sku TEXT NOT NULL,

    sku_normalized TEXT
        GENERATED ALWAYS AS (
            upper(btrim(sku))
        ) STORED,

    option_key TEXT NOT NULL,

    PRIMARY KEY (tenant_id, id),

    FOREIGN KEY (tenant_id, product_id)
        REFERENCES app.products(tenant_id, id),

    UNIQUE (tenant_id, sku_normalized),

    UNIQUE (
        tenant_id,
        product_id,
        option_key
    ),

    CHECK (btrim(sku) <> '')
);
```

这里解决两个不同的问题。

**SKU 编号唯一性**：同一企业内部不能有重复的规范化 SKU。

**规格组合唯一性**：同一商品不能有两个相同的颜色、尺码组合。

`option_key` 必须由服务端根据稳定的规格选项 ID 生成，不允许用户直接指定任意字符串。

需要注意，`upper(btrim(...))` 是初步规范化策略。对于完整的 Unicode SKU、大小写规则和特殊字符，还要进一步定义产品编号规范，不能仅依赖数据库默认排序规则。

### C. 商品内容与站点上架

```sql
CREATE TABLE app.product_content_revisions (
    tenant_id UUID NOT NULL,
    product_id UUID NOT NULL,
    revision BIGINT NOT NULL,

    localized_content JSONB NOT NULL,

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    PRIMARY KEY (
        tenant_id,
        product_id,
        revision
    ),

    FOREIGN KEY (tenant_id, product_id)
        REFERENCES app.products(tenant_id, id),

    CHECK (revision > 0),
    CHECK (jsonb_typeof(localized_content) = 'object')
);

CREATE TABLE app.product_listings (
    tenant_id UUID NOT NULL,
    site_id UUID NOT NULL,
    product_id UUID NOT NULL,

    slug TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'draft',

    published_content_revision BIGINT,

    PRIMARY KEY (
        tenant_id,
        site_id,
        product_id
    ),

    UNIQUE (
        tenant_id,
        site_id,
        slug
    ),

    FOREIGN KEY (tenant_id, site_id)
        REFERENCES app.sites(tenant_id, id),

    FOREIGN KEY (tenant_id, product_id)
        REFERENCES app.products(tenant_id, id),

    FOREIGN KEY (
        tenant_id,
        product_id,
        published_content_revision
    )
        REFERENCES app.product_content_revisions(
            tenant_id,
            product_id,
            revision
        ),

    CHECK (status IN (
        'draft',
        'active',
        'archived'
    )),

    CHECK (
        status <> 'active'
        OR published_content_revision IS NOT NULL
    )
);
```

该结构能够保证：

- 一个商品可以用于多个网站。
- 不同网站可以选择不同的商品内容版本。
- 商品草稿不会因为创建了 Product 就自动对外展示。
- 商品上架需要明确内容版本。
- 商品内容更新不必修改所有页面模板。

未来还需要扩展按销售渠道、市场及 Locale 区分的商品可见性。

**本轮先以 Site 为商品展示边界，不在第一份迁移中引入完整的渠道定价模型。**

### D. 免费本地媒体存储

```sql
CREATE TABLE app.media_blobs (
    tenant_id UUID NOT NULL,
    id UUID NOT NULL DEFAULT uuidv7(),

    backend TEXT NOT NULL,
    storage_key TEXT NOT NULL,

    sha256 BYTEA NOT NULL,
    size_bytes BIGINT NOT NULL,

    status TEXT NOT NULL DEFAULT 'staging',

    PRIMARY KEY (tenant_id, id),

    UNIQUE (
        tenant_id,
        backend,
        storage_key
    ),

    CHECK (octet_length(sha256) = 32),
    CHECK (size_bytes >= 0),

    CHECK (backend IN ('local', 's3')),

    CHECK (status IN (
        'staging',
        'ready',
        'deleting'
    ))
);

CREATE TABLE app.media_assets (
    tenant_id UUID NOT NULL,
    id UUID NOT NULL DEFAULT uuidv7(),
    blob_id UUID NOT NULL,

    filename TEXT NOT NULL,
    mime_type TEXT NOT NULL,

    visibility TEXT NOT NULL DEFAULT 'private',

    PRIMARY KEY (tenant_id, id),

    FOREIGN KEY (tenant_id, blob_id)
        REFERENCES app.media_blobs(tenant_id, id),

    CHECK (visibility IN (
        'private',
        'public'
    ))
);

CREATE TABLE app.product_media (
    tenant_id UUID NOT NULL,
    product_id UUID NOT NULL,
    media_id UUID NOT NULL,

    role TEXT NOT NULL,
    sort_order INTEGER NOT NULL DEFAULT 0,

    PRIMARY KEY (
        tenant_id,
        product_id,
        media_id,
        role
    ),

    FOREIGN KEY (tenant_id, product_id)
        REFERENCES app.products(tenant_id, id),

    FOREIGN KEY (tenant_id, media_id)
        REFERENCES app.media_assets(tenant_id, id)
);
```

商品和网站只保存 `media_id`。

不保存：

```text
/home/user/photos/product-001.jpg
```

也不永久保存具体 RustFS 地址。

物理文件位置属于 Media Service 的内部细节。

正式实施还需增加上传会话、处理任务、文件用途和媒体状态管理。这里先建立稳定的资源引用模型。

### E. 页面版本和 Site Release

```sql
CREATE TABLE app.pages (
    tenant_id UUID NOT NULL,
    id UUID NOT NULL DEFAULT uuidv7(),
    site_id UUID NOT NULL,

    page_key TEXT NOT NULL,

    PRIMARY KEY (tenant_id, id),

    UNIQUE (
        tenant_id,
        site_id,
        id
    ),

    UNIQUE (
        tenant_id,
        site_id,
        page_key
    ),

    FOREIGN KEY (tenant_id, site_id)
        REFERENCES app.sites(tenant_id, id)
);

CREATE TABLE app.page_revisions (
    tenant_id UUID NOT NULL,
    page_id UUID NOT NULL,
    revision BIGINT NOT NULL,

    locale TEXT NOT NULL,
    path TEXT NOT NULL,

    document JSONB NOT NULL,

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    PRIMARY KEY (
        tenant_id,
        page_id,
        revision
    ),

    UNIQUE (
        tenant_id,
        page_id,
        revision,
        locale,
        path
    ),

    FOREIGN KEY (tenant_id, page_id)
        REFERENCES app.pages(tenant_id, id),

    CHECK (revision > 0),
    CHECK (left(path, 1) = '/'),
    CHECK (jsonb_typeof(document) = 'object')
);

CREATE TABLE app.site_releases (
    tenant_id UUID NOT NULL,
    site_id UUID NOT NULL,
    id UUID NOT NULL DEFAULT uuidv7(),

    release_no BIGINT NOT NULL,
    renderer_build_id TEXT NOT NULL,

    manifest JSONB NOT NULL,

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    PRIMARY KEY (
        tenant_id,
        site_id,
        id
    ),

    UNIQUE (
        tenant_id,
        site_id,
        release_no
    ),

    FOREIGN KEY (tenant_id, site_id)
        REFERENCES app.sites(tenant_id, id),

    CHECK (release_no > 0),
    CHECK (jsonb_typeof(manifest) = 'object')
);

CREATE TABLE app.site_release_routes (
    tenant_id UUID NOT NULL,
    site_id UUID NOT NULL,
    release_id UUID NOT NULL,

    locale TEXT NOT NULL,
    path TEXT NOT NULL,

    page_id UUID NOT NULL,
    page_revision BIGINT NOT NULL,

    PRIMARY KEY (
        tenant_id,
        site_id,
        release_id,
        locale,
        path
    ),

    FOREIGN KEY (
        tenant_id,
        site_id,
        release_id
    )
        REFERENCES app.site_releases(
            tenant_id,
            site_id,
            id
        ),

    FOREIGN KEY (
        tenant_id,
        site_id,
        page_id
    )
        REFERENCES app.pages(
            tenant_id,
            site_id,
            id
        ),

    FOREIGN KEY (
        tenant_id,
        page_id,
        page_revision,
        locale,
        path
    )
        REFERENCES app.page_revisions(
            tenant_id,
            page_id,
            revision,
            locale,
            path
        )
);
```

这里有一个重要变化：

**网站路由属于 Release，而不是可变的页面记录。**

假设一个页面最初位于：

`/about`

后来变为：

`/company`

旧的 Site Release 仍然保留 `/about` 的路由关系。

新 Release 可以配置 `/company`，并增加对应的重定向。

正式发布前，路由服务必须同时校验商品、博客、系统保留路径及静态页面，避免不同业务领域占用同一 URL。

最后增加 Site 的正式发布指针约束：

```sql
ALTER TABLE app.sites
ADD CONSTRAINT sites_published_release_fk
FOREIGN KEY (
    tenant_id,
    id,
    published_release_id
)
REFERENCES app.site_releases(
    tenant_id,
    site_id,
    id
);
```

这样一个 Site 不能错误地指向另一个 Site 的 Release。

### F. 事务与事件

```sql
CREATE TABLE app.outbox_events (
    tenant_id UUID NOT NULL,
    id UUID NOT NULL DEFAULT uuidv7(),

    event_type TEXT NOT NULL,
    payload JSONB NOT NULL,

    status TEXT NOT NULL DEFAULT 'pending',

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    PRIMARY KEY (tenant_id, id),

    CHECK (status IN (
        'pending',
        'processing',
        'completed',
        'failed'
    ))
);

COMMIT;
```

实际交付还要补充事件重试时间、尝试次数和错误信息。

发布成功时，业务事务可以写入 Outbox，用于后续缓存失效和外部通知。

River 可以把后台任务与 PostgreSQL 业务修改放在同一个事务中入队，这适合媒体处理和可靠异步任务。([River 官方文档](https://riverqueue.com/docs/transactional-enqueueing))

### G. 数据隔离

所有租户业务表都必须启用 RLS。

示例：

```sql
ALTER TABLE app.products
ENABLE ROW LEVEL SECURITY;

ALTER TABLE app.products
FORCE ROW LEVEL SECURITY;

CREATE POLICY products_tenant_scope
ON app.products
USING (
    tenant_id =
    nullif(
        current_setting('app.tenant_id', true),
        ''
    )::uuid
)
WITH CHECK (
    tenant_id =
    nullif(
        current_setting('app.tenant_id', true),
        ''
    )::uuid
);
```

生产运行时需要在事务内设置经过认证的租户上下文。

```sql
BEGIN;

SELECT set_config(
    'app.tenant_id',
    $1,
    true
);

-- 执行受授权的业务 SQL

COMMIT;
```

这里 `$1` 必须由可信的服务端认证上下文提供。

PostgreSQL 的 `set_config(..., true)` 只在当前事务内生效，适合连接池场景下的租户上下文隔离。([PostgreSQL 官方文档](https://www.postgresql.org/docs/18/functions-admin.html))

需要特别注意，其他表同样必须配置 RLS 和最小权限。上述 SQL 仅展示产品表的策略，尚不构成完整安全迁移。

**数据库迁移需要前向版本管理；应用运行账号不具备 DDL、`TRUNCATE` 或绕过 RLS 的能力。**

# 四、ARCH-015：OpenAPI Contract V1

## 4.1 API 分层

建议正式区分四种 API：

| API | 调用方 | 权限模型 |
|---|---|---|
| Admin API | React 后台 | 登录身份 + RBAC |
| Public API | 网站访客 | 公开资源 + 会话权限 |
| Internal Render API | Astro SSR | 服务间认证 |
| Automation API | Agent、ERP、脚本 | 带 Scope 的 API Key |

它们共享 Go 业务服务，而不是各自建立独立的商品管理逻辑。

一个重要约束是：

**前端能够执行的业务动作，必须有正式 API；但这不意味着所有内部数据库操作都应暴露为公开 CRUD。**

例如：

可以提供商品归档 API。

不应该提供删除历史订单明细的通用接口。

## 4.2 第一版 API 路由

### 企业及站点

| Method | Path | 操作 |
|---|---|---|
| POST | `/v1/organizations` | 创建企业 |
| GET | `/v1/organizations/{id}` | 查询企业 |
| PATCH | `/v1/organizations/{id}` | 修改企业 |
| POST | `/v1/sites` | 创建网站 |
| GET | `/v1/sites/{id}` | 查询网站 |

### 商品

| Method | Path | 操作 |

| POST | `/v1/products` | 创建商品 |

| POST | `/v1/media/uploads` | 创建上传会话 |

## 4.3 实际 OpenAPI 契约示例

建议在仓库中使用：

`api/openapi/opensite-v1.yaml`

下面给出页面编辑接口的核心定义。

```yaml
openapi: 3.1.2

info:
  title: OpenSite Commerce API
  version: 0.5.0

servers:
  - url: /api

security:
  - bearerAuth: []

paths:
  /v1/sites/{site_id}/drafts/{draft_id}/operations:
    post:
      operationId: applyPageOperations
      summary: Apply page draft operations

      parameters:
        - name: site_id
          in: path
          required: true
          schema:
            type: string
            format: uuid

          in: path
          required: true
          schema:
            type: string
            format: uuid

        - name: If-Match
          in: header
          required: true

            type: string

        - name: Idempotency-Key
          in: header
          required: true

            type: string
            minLength: 1
            maxLength: 128

      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/OperationBatch"

  securitySchemes:

      required:
        - operations

            $ref: "#/components/schemas/PageOperation"
```

## 4.4 API 并发与幂等规则

建议明确以下规范。

### 查询

支持：

- Cursor Pagination。
- Filter。
- Sort。
- 限制返回字段。
- 受控的关联数据展开。

大商品表优先采用 Keyset Pagination，避免深度 Offset 翻页。

### 修改

页面草稿使用 ETag 和 `If-Match`。

例如：

```http
If-Match: "draft-revision-12"
```

如果当前版本已经变成 13，返回：

```http
412 Precondition Failed
```

避免两个编辑器窗口相互覆盖。

### 创建与批量任务

使用 `Idempotency-Key`。

同一个调用身份、API 操作、幂等键和相同请求内容重复提交时，应返回与既有操作一致的结果，而不是重复创建商品。

相同幂等键对应不同请求内容时，应拒绝冲突。

后台处理中的异步任务可以返回 `202 Accepted`，并提供任务资源地址。

### 错误格式

统一使用 RFC 9457 Problem Details，而不是每个模块设计自己的错误 JSON。该标准使用 `application/problem+json` 表示机器可读的 HTTP 错误。([RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html))

例如：

```json
{
  "type": "https://docs.opensite.example/errors/version-conflict",
  "title": "Draft revision conflict",
  "status": 412,
  "code": "VERSION_CONFLICT",
  "expected_revision": 12,
  "current_revision": 13
}
```

上面的文档域名只是协议示例，正式项目应使用真实的项目文档域名。

# 五、ARCH-016：Component SDK V1

这是本轮需要特别重视的部分。

此前已经确定：

**React 编辑器、API 和 Agent 使用同一份 PageDocument；Astro 负责正式渲染。**

现在必须定义组件的实际开发规范。

## 5.1 组件分成三个部分

一个组件不是单独的 `.astro` 文件。

建议组件包由以下结构组成：

```text
component/
├── manifest.json
├── props.schema.json
├── editor.schema.json
├── defaults.json
└── renderer.astro
```

其中：

| 文件 | 功能 |
|---|---|
| manifest | 组件标识、版本、能力 |
| props.schema | 业务属性校验 |
| editor.schema | 后台编辑控件 |
| defaults | 默认参数 |
| renderer | 真正的 Astro 渲染实现 |

项目中的基础组件可以使用这个逻辑结构，不必强制每个组件都有独立目录和重复配置文件。

## 5.2 Component Manifest

例如 Hero：

```json
{
  "api_version": "opensite.component/v1",
  "id": "core.hero",
  "major_version": 1,
  "display_name": "Hero Banner",
  "category": "content",
  "render_mode": "server",
  "capabilities": [],
  "slots": {},
  "props_schema": "./props.schema.json",
  "editor_schema": "./editor.schema.json"
}
```

组件可以声明：

- 支持的布局。
- 可配置字段。
- 子组件槽位。
- 数据绑定需求。
- 响应式能力。
- 所需的业务权限。
- 兼容的组件契约版本。

这里要把组件契约版本和实际软件构建版本分开。

例如：

```text
core.hero@1
```

表示公共配置契约主版本。

而：

```text
renderer_build_id
```

表示包含实际组件代码的前端构建。

### 为什么需要两个版本？

组件可以在不修改配置契约的前提下修复 CSS Bug。

但如果组件的 Prop Schema 出现不兼容变更，就必须升级契约主版本，或者提供配置迁移。

这样能够更准确地判断旧主题和旧页面是否仍然可渲染。

---

## 5.3 组件注册机制

Astro 构建阶段将组件编译进程序。

可以采用静态注册表：

```typescript
import Hero from "../components/Hero.astro";
import ProductGrid from "../components/ProductGrid.astro";
import CompanyProfile from "../components/CompanyProfile.astro";

export const componentRegistry = {
  "core.hero@1": Hero,
  "catalog.product-grid@1": ProductGrid,
  "company.profile@1": CompanyProfile
} as const;
```

渲染器通过组件 ID 查找实际组件。

**不能根据数据库传来的字符串动态加载任意服务器文件。**

Astro 支持使用变量表示动态组件，但客户端 Hydration 指令存在构建期要求，不能简单应用于所有动态组件。因此交互式 React Islands 应在受信任的 Astro 组件内部静态声明。([Astro 组件语法](https://v4.docs.astro.build/en/basics/astro-syntax/))

例如：

```text
ProductDetail.astro
      │
      ├── ProductGallery.astro
      ├── ProductInformation.astro
      └── VariantSelector React Island
```

真正需要浏览器交互的部分才加载 React。

这样可以减少纯展示页面的不必要 JavaScript。

## 5.4 组件数据模型

建议区分：

```typescript
type ComponentNode = {
  id: string;
  component: string;
  props: Record<string, unknown>;
  binding?: DataBinding;
  slots: Record<string, string[]>;
};

type DataBinding = {
  resolver: string;
  params: Record<string, unknown>;
};

type PageDocument = {
  schema_version: 1;
  root_id: string;
  nodes: Record<string, ComponentNode>;
};
```

这里只是 TypeScript 类型的核心结构。

正式 SDK 还需要：

- JSON Schema 类型。
- Locale 处理。
- 编辑器 UI Schema。
- 响应式属性。
- 组件兼容信息。
- 资源引用验证。

### 组件运行上下文

建议统一提供：

```typescript
type RenderContext = {
  siteId: string;
  releaseId: string;
  locale: string;
  marketId?: string;
  route: string;
  preview: boolean;
};
```

但不允许组件任意修改这些字段。

组件只能获得渲染服务提供的可信上下文。

不能自行指定其他租户或站点 ID 读取业务数据。

## 5.5 Data Resolver 契约

组件不直接访问 PostgreSQL。

例如：

```json
{
  "resolver": "catalog.collection-products@1",
  "params": {
    "collection_id": "collection-001",
    "limit": 8
  }
}
```

Go Read Service 负责：

1. 检查 Resolver 是否存在。
2. 验证参数。
3. 根据站点确定商品可见范围。
4. 查询商品数据。
5. 关联媒体和公开内容。
6. 产生稳定的 View Model。
7. 返回给 Astro 渲染器。

### 数据查询预算

V1 应明确限制：

| 限制 | 初步建议 |
|---|---|
| 页面最大节点 | 默认不超过 200 |
| 最大组件嵌套深度 | 默认 8 层 |
| 单个商品网格最大返回量 | 默认 48 |
| 单页 Resolver 调用 | 合并与批量执行 |
| 单次渲染耗时 | 可配置超时 |
| 数据绑定 | 仅允许已注册 Resolver |

这些是待基准测试调整的初始限制，不是经过证明的性能最优值。

## 5.6 SDK 必须保持前后端一致

我建议采用两部分 SDK：

**TypeScript SDK**

提供给 React 后台、主题开发者和外部客户端。

负责：

- PageDocument 类型。
- 组件 Manifest 类型。
- OpenAPI 客户端。
- 编辑器操作类型。
- 组件 Schema。
- 预览通信类型。

**Go Contract Package**

提供给 Go 后端。

负责：

- PageDocument 解析。
- 操作校验。
- Schema 验证。
- Resolver 参数检查。
- 发布版本检查。

两种语言的实现必须使用同一套规范测试样例。

例如一个循环嵌套的页面结构，不能在 TypeScript 编辑器中判定有效，而 Go 后端判定无效。

**服务端是最终校验权威。**

TypeScript 校验主要用于即时反馈，不能代替后端验证。

# 六、Site Release 的工程实现

## 6.1 发布过程必须具备确定性

我建议把正式发布服务定义为：

```text
PublishService
    │
    ├── Authenticate
    ├── Authorize
    ├── Lock Site
    ├── Verify Base Release
    ├── Validate Draft
    ├── Validate Component Registry
    ├── Validate Data Bindings
    ├── Validate Media References
    ├── Validate Routes
    ├── Create Immutable Release
    ├── Update Published Pointer
    ├── Write Outbox Event
    └── Commit
```

一个值得注意的问题是：

**预览时通过校验，不代表正式发布时一定还能通过。**

例如，预览以后：

- 某张图片被删除。
- 某个组件被升级。
- 商品分类被移除。
- 别的管理员发布了新版本。

因此，正式发布事务需要重新检查关键前置条件。

## 6.2 版本冲突检测

假设：

```text
Current Release = 12
Draft Base Release = 12
```

此时可以进入发布。

但如果另一个管理员已经发布 Release 13：

```text
Current Release = 13
Draft Base Release = 12
```

就必须返回版本冲突。

不能直接用旧草稿覆盖新版本。

发布时对 Site 行加锁，并在事务中检查基础版本。

## 6.3 发布指针更新

核心 SQL 可以采用：

```sql
UPDATE app.sites
SET published_release_id = $1
WHERE tenant_id = $2
  AND id = $3
  AND published_release_id
      IS NOT DISTINCT FROM $4;
```

其中：

- `$1`：准备发布的新 Release。
- `$2`：Tenant ID。
- `$3`：Site ID。
- `$4`：预期的旧 Release。

必须检查受影响行数为 1。

如果更新了 0 行，则代表当前站点版本与预期不一致，事务应回滚。

新 Release 的创建、路由引用、发布指针变更和对应事件记录必须在同一数据库事务中完成。

## 6.4 组件构建版本固定

还需要修正前几轮遗漏的一个问题。

假设旧 Release 使用：

```text
core.hero@1
```

但新版本程序已经删除了对应渲染实现。

这时即使数据库仍然保留旧 Release，也未必能够恢复旧网站。

因此：

**Site Release 必须记录对应的 Renderer Build ID 和组件契约清单。**

在升级或回滚时，检查当前部署是否仍能渲染目标 Release。

必要时保留兼容的旧组件实现，或者先运行页面配置迁移。

不能把数据库记录还在就等同于页面一定可恢复。

## 6.5 Agent 审批版本必须锁定

此前已经定义了 Site Plan。

V0.5 增加一个明确协议：

**审批绑定规范化计划内容哈希。**

计划包含的操作、目标资源、前置版本和授权范围应进入确定性摘要。

对于 JSON 的跨语言规范化，可以采用 RFC 8785 的 JSON Canonicalization Scheme，再计算 SHA-256。该规范专门用于生成可重复计算的 JSON 表达。([RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html))

如果 Agent 在批准后修改计划内容，新的计划摘要不同，旧审批不能用于新计划。

此外，还必须重新检查执行时权限是否仍然有效。

# 七、ARCH-017：最小部署与免费存储

## 7.1 正式确定四个基础运行组件

第一版默认只需要：

```text
Caddy
  │
  ├── Admin 静态资源
  ├── Astro Storefront
  └── Go API
         │
         ├── PostgreSQL
         ├── River Worker
         └── LocalFS
```

建议运行结构：

| 组件 | 运行方式 | 是否必须 |
|---|---|---|
| Caddy | 容器 | 是 |
| Go API | 容器 | 是 |
| Astro SSR | 容器 | 是 |
| PostgreSQL | 容器 | 是 |
| React Admin | 编译后静态资源 | 是 |
| River Worker | 初期可在 Go 进程内运行 | 是 |
| LocalFS | 持久化磁盘目录 | 是 |
| Redis/Valkey | 独立服务 | 否 |
| RustFS | 独立服务 | 否 |
| Meilisearch | 独立服务 | 否 |

### 为什么不要求 RustFS？

因为普通商家可能只有一台服务器。

项目安装以后，应该直接能够上传商品图片和企业资料。

不应该先要求用户学习 Bucket、Access Key 和 S3 Endpoint。

未来切换 RustFS 时，仍然使用之前定义的 Storage Adapter。

## 7.2 本地存储必须使用安全的写入流程

不能简单执行：

```text
HTTP Upload → 直接写入正式图片目录
```

正确流程：

```text
创建 Upload Session
        │
        ▼
限制文件大小和类型
        │
        ▼
写入临时文件
        │
        ▼
计算 SHA256
        │
        ▼
校验文件内容
        │
        ▼
同步并完成原子文件移动
        │
        ▼
更新数据库状态
        │
        ▼
异步处理缩略图
        │
        ▼
Media READY
```

本地文件的原子移动要求源和目标位于支持该语义的同一文件系统，并需要考虑文件、目录同步及异常断电后的恢复。

数据库事务无法和文件系统原子提交。

所以必须通过上传状态和后台清理任务处理：

- 文件已经写入但数据库操作失败。
- 数据库记录已经存在但文件不完整。
- 上传中断。
- 图片处理失败。
- 服务重启。

对于已经发布的媒体，删除前必须检查商品、内容版本和仍被保留的 Site Release 引用。

不能简单根据最后访问时间就删除原图。

## 7.3 备份原则

最小正式部署至少需要：

**PostgreSQL 一致性备份 + 媒体目录备份 + 应用配置备份。**

媒体和数据库应通过恢复清单建立对应关系。

例如在备份任务中记录：

```text
Backup ID
Database Snapshot
Media Object Manifest
Application Version
Renderer Build
Created At
Checksum Manifest
```

恢复时必须验证：

- 数据库可恢复。
- 媒体对象完整。
- 关键对象哈希正确。
- 已发布页面引用的媒体仍然存在。
- 当前 Renderer 能够渲染已发布 Release。

备份目标应独立于主存储故障域。

**免费自部署可以减少软件授权费用，但不能以牺牲备份为代价。**

## 7.4 多域名与 HTTPS

企业官网需要支持用户自己的域名。

初期可以通过 Caddy 自动管理 HTTPS。

但如果将来一个实例同时托管大量用户域名，不能无条件接受任意域名的证书申请。

Caddy 的 On-Demand TLS 支持通过授权检查端点判断是否允许为指定域名签发证书。官方明确要求采取防滥用措施。([Caddy 文档](https://caddyserver.com/on-demand-tls))

建议：

```text
用户申请绑定域名
        │
        ▼
平台生成所有权验证信息
        │
        ▼
用户配置 DNS
        │
        ▼
Go API 验证域名所有权
        │
        ▼
标记为 Verified
        │
        ▼
Caddy 允许证书申请
        │
        ▼
网站通过 HTTPS 访问
```

域名解析服务只根据已经验证且启用的域名映射站点。

不能直接信任任意 Host Header 映射到用户指定的 Tenant。

第一版单站点部署可以先使用明确配置的域名，多域名动态证书管理作为独立部署验收。

# 八、测试体系：不再用功能列表代替验收能力

这也是本轮需要真正改进的地方。

过去几轮列出了大量测试目标，但还没有明确哪些测试是阻止合并的必要条件。

我建议建立如下最小质量门禁。

## 8.1 五类必过测试

| 测试类别 | 测试重点 | 合并条件 |
|---|---|---|
| Database | 外键、唯一性、RLS、迁移 | 全部通过 |
| API Contract | OpenAPI、请求响应、错误码 | 全部通过 |
| Domain | 商品、媒体、发布业务不变量 | 全部通过 |
| Renderer | 页面配置、组件兼容、预览一致性 | 全部通过 |
| Integration | 创建商品到网站发布的端到端流程 | 全部通过 |

性能和压力测试也要持续执行，但初期可以把大型压测放在独立的定期测试流水线，而不是每次提交都运行 300,000 SKU 的完整数据集。

## 8.2 必须编写的数据库测试

### 租户隔离测试

创建两个 Tenant。

Tenant A 创建商品。

Tenant B 使用自己的运行身份查询 A 的商品。

预期：

```text
0 条可见记录
```

执行更新：

```text
不能修改 Tenant A 的数据
```

还要检查跨租户复合外键是否阻止错误引用。

### SKU 唯一性测试

同一租户创建两个规范化后相同的 SKU。

预期：

```text
Unique Violation
```

不同租户使用相同 SKU。

预期：

```text
允许
```

### 商品变体测试

同一个 Product 创建两个相同的规格组合。

预期：

```text
拒绝第二个组合
```

### RLS 上下文测试

使用连接池，依次执行 Tenant A、Tenant B 的请求。

预期：

```text
Tenant A 请求结束后，
Tenant B 不继承 A 的数据库上下文。
```

这项测试应该覆盖正常提交、事务回滚、连接复用及异常退出。

---

## 8.3 Site Release 一致性测试

### 测试一：发布失败

1. 创建 Release 12。
2. 创建新草稿。
3. 故意加入无效组件。
4. 发起发布。

预期：

- 发布失败。
- 正式站仍然使用 Release 12。
- 没有部分发布的路由。
- 错误指向具体组件。

### 测试二：并发发布

1. 管理员 A 和 B 都基于 Release 12 创建草稿。
2. A 成功发布 Release 13。
3. B 再尝试直接发布。

预期：

B 收到版本冲突，不能覆盖 A 的 Release 13。

### 测试三：媒体缺失

1. 页面草稿引用一个不存在或未 READY 的媒体。
2. 发起发布。

预期：

发布服务拒绝发布，并返回具体媒体资源的错误。

### 测试四：旧组件兼容

1. 创建依赖 `core.hero@1` 的 Release。
2. 更新组件注册表。
3. 尝试回滚到旧 Release。

预期：

只有在当前 Renderer 仍然兼容旧配置时，才允许恢复。

否则返回明确的组件兼容性错误。

## 8.4 大规模商品测试

测试数据：

| 指标 | 测试规模 |
|---|---:|
| 商品 SPU | 10,000 |
| SKU | 300,000 |
| 媒体引用 | 100,000 |
| 商品分类 | 1,000 |
| 页面实例 | 1,000 |
| 主题 | 多个 |
| 并发修改 | 多客户端 |
| 批量导入 | 5,000 SPU/任务 |

这里需要重点观察：

- PostgreSQL 索引大小。
- 查询计划。
- API p50/p95/p99。
- 内存占用。
- 导入吞吐。
- 数据库连接数。
- Worker CPU 和内存。
- SSR 响应时间。
- 图片处理队列积压。

推荐保留固定数据集和负载脚本，让每次关键架构修改都能进行可重复比较。

**不在缺乏实测的情况下承诺特定 QPS、百万级 SKU 或单机吞吐。**

# 九、第一批开发任务：按可验证纵向闭环拆分

如果交给多个 Codex 编码代理并行开发，我建议不要按“前端代理、后端代理、数据库代理”永久切分。

应先冻结接口，再按领域拆分，避免多个代理同时修改核心表和公共协议。

## 9.1 Milestone 1：基础数据与认证

| 工作 | 验收 |
|---|---|
| 初始化 Go 工程 | 编译和基础测试通过 |
| PostgreSQL 迁移框架 | 能从空库顺序迁移 |
| Tenant/Organization | 能创建企业 |
| 用户及成员认证 | 角色与租户作用域正确 |
| Site 创建 | 能关联企业 |
| RLS | 跨租户测试通过 |

**完成标准：能够安全创建并查询一个企业网站。**

## 9.2 Milestone 2：商品与免费媒体

| 工作 | 验收 |
|---|---|
| Product | 能创建商品 |
| Variant | 支持 SKU |
| Content Revision | 支持内容版本 |
| LocalFS | 上传文件 |
| Media Asset | 文件引用 |
| Product Listing | 商品关联网站 |

**完成标准：能够通过 API 创建商品、上传图片，并查询完整的公开商品展示数据。**

## 9.3 Milestone 3：页面组件

| 工作 | 验收 |
|---|---|
| Component Registry | 注册三种基础组件 |
| PageDocument | 创建页面文档 |
| JSON Schema | 参数校验 |
| Data Resolver | 绑定商品数据 |

建议先实现三个组件：

```text
core.hero@1
catalog.product-grid@1
company.profile@1
```

**完成标准：一个包含企业介绍和商品网格的页面能够真实渲染。**

## 9.4 Milestone 4：发布与预览

| 工作 | 验收 |
|---|---|
| Draft Service | 创建和修改草稿 |
| Preview Session | 安全预览 |
| Release Service | 发布 |
| Route Resolver | 正确路由 |
| Rollback | 恢复以前的布局 |
| Cache Invalidation | 发布后展示新内容 |

**完成标准：用户修改首页布局后，能够预览、发布和回滚，并且不会影响商品记录。**

## 9.5 Milestone 5：后台编辑器与 Agent

| 工作 | 验收 |
|---|---|
| React Admin | 页面列表和组件面板 |
| 可视化编辑 | 组件添加、移动、修改 |
| TypeScript SDK | 使用公开 API |
| Agent Adapter | 通过同一操作接口修改页面 |
| Operation Audit | 返回修改差异 |
| Idempotency | 重试不重复执行 |

**完成标准：人和 Agent 能够分别修改同一个网站草稿，且都经过相同的权限、版本和组件校验。**

# 十一、V0.5 反向审查：还有什么不能立即实施？

虽然本轮已经进入工程规格，但我认为仍然有五项必须谨慎处理。

| 风险 | 如果处理错误 | 下一步处理 |
|---|---|---|
| 数据库迁移 | 后续 SKU、价格和发布关系难以调整 | 先运行空库迁移和约束测试 |
| 组件协议 | React 编辑器与 Astro 正式站不一致 | 先建立三个真实组件的双端验证 |
| 媒体状态 | 图片丢失、重复、错误删除 | 增加故障注入和恢复测试 |
| API 版本 | SDK、后台、Agent 频繁不兼容 | 先固化 OpenAPI，建立兼容性测试 |
| 站点发布 | 旧版本无法恢复 | 测试数据库版本与 Renderer 版本兼容 |

特别是数据库部分，当前 SQL 已经具体到表和外键，但还缺少正式的：

- 用户身份和 API Key 迁移。
- `site_domains` 与域名验证模型。
- 完整商品 Option/Attribute Schema。
- 媒体上传会话与处理状态。
- 草稿编辑会话和操作日志。
- Idempotency 持久化表。
- 路由重定向模型。
- 详细的审计及任务表。
- 全部表的 RLS、权限和索引迁移。

这些属于继续完成 V1 迁移的明确工作，不应被理解为已经实现。

同样，OpenAPI 示例还需要扩展成覆盖首条纵向闭环的完整机器可校验规范。

# 十二、V0.6 的正确方向

我不建议 V0.6 再引入新的数据库、框架、微服务或 AI 系统。

下一轮应该集中完成三个任务。

### ARCH-018：完整的最小业务迁移

把 V0.5 中的 SQL 草案整理为可验证的迁移序列：

```text
001_identity
002_tenant_organization
003_site_domain
004_catalog
005_media
006_page
007_release
008_idempotency_audit
009_rls_policies
010_indexes
```

这里只列出建议的迁移组织方式，最终还需按外键依赖关系调整执行顺序。

### ARCH-019：完整 OpenAPI 最小闭环

不再只展示路由名称，而是定义：

- 所有 Request Schema。
- 所有 Response Schema。
- 字段语义。
- 资源权限。
- 错误类型。
- 幂等策略。
- 版本冲突。
- 发布操作。
- 媒体上传协议。

让 TypeScript SDK 和 Go 服务端都能基于同一份接口规范开发。

### ARCH-020：首个可验证的端到端样例

用一个真实业务场景作为统一验收。

我建议使用：

**一个兼具 B2B 商品展示与企业介绍的香氛独立站。**

原因是它可以覆盖：

- 企业资料。
- 商品。
- SKU。
- 商品主图。
- 企业图片。
- 商品详情。
- 首页商品网格。
- 博客。
- 联系方式。
- B2B 询盘入口。
- 组件模板。
- 页面发布。
- Agent 修改。

这个样例能够检验平台是否真正支持一个完整企业官网，而不是只有商品表和几张静态网页。

再使用服装行业的大 SKU 数据集进行独立性能验证，避免将单一香氛样例误认为多行业能力已经成立。

## V0.5 最终结论

本轮确定了三个最重要的实施边界。

**第一，PostgreSQL 是业务事实与发布版本的唯一核心数据源。** 图片、视频存储在免费自部署的文件系统或可选 S3 服务中。商品、媒体、页面都使用稳定的资源 ID，不绑定具体主题或存储地址。

**第二，OpenAPI 是管理后台、Agent 和其他软件访问业务能力的正式契约。** 所有修改经过同一套身份、授权、数据校验、并发控制和审计机制。

**第三，组件 SDK 是建站系统的关键接口。** 用户无需修改程序代码，即可通过 UI、API 或 Agent 操作已经注册的组件，完成企业官网、商品页面、博客和营销页面的配置。

截至 V0.5，我们有了能够进入编码阶段的**首批数据库结构、API 协议示例、组件注册模型、发布事务设计和工程验收基线**，但尚未完成完整迁移、可机器验证的全量 API 契约及实际运行测试。

**下一轮的重点应从“继续写架构”转向“把 V0.5 的未完成契约补齐，并用一个最小真实网站证明它们可以协同工作”。**

这比继续增加功能模块更有价值，也能够尽早发现需要修改的底层架构问题。
