# Admin core UI (C-08b)

`web/admin` composes the existing design tokens and `packages/ui`. It manages
products, SKUs and the reserve → content → complete → attach media workflow.
Catalog edits use a quoted version in `If-Match`; a 412 retains the draft until
the user explicitly reloads. Adding media does not claim an atomic product CAS:
the existing attachment API has no version precondition.

Staff authentication follows PR #43's login challenge, session and logout
contract. Cookies are HttpOnly; JavaScript retains only the CSRF token in memory.
Every API request includes cookies and rejects redirects. A 401, logout or the
session DTO's absolute expiry clears private page state and the query cache.
Authentication generations prevent a late bootstrap or logout from replacing a
new session. A failed logout retains the session and CSRF token for a retry.
The DTO does not expose the server's idle deadline; idle expiry is discovered
on the next 401. Immediate idle-deadline DOM clearing is not claimed.

## Backend connections

PR #83 connects production cookie sessions to `AdminOrAPIKey` catalog/media
routes. The browser never receives an API key.
The administrator supplies a store UUID; the server must authorize membership
and scopes on each request. `tests/e2e/admin.spec.ts` exercises real login and
catalog creation; the complete SKU/media/publication journey requires its own
current-head persistence witnesses.

Order reads use the product owner's contract, with `orders:read`, cursor paging,
an optional state filter and a quoted detail version ETag. Every `*_minor` is a
decimal string, formatted using BigInt without converting amounts to Number.
Domain Money permits three uppercase ASCII letters. Codes not recognized by
Intl display their original minor units explicitly instead of guessing a decimal
exponent. Production list/detail reads use the generated OpenAPI client over the
same cookie transport and session guard as catalog. API failures never select a
fixture fallback. Anonymous routes reach login before private reads.
Development/gallery pages and Playwright fixtures show the exact label
**CONTRACT FIXTURE (orders read API pending PR)**. The fixture is isolated by the
test runner's intercepted requests; no fixture data is bundled into production.
PR #47 (`ec09fa8`) defines the pending read projection: line titles are null
(the snapshot retains only `sku_code`), so lines display the SKU. Shipping method
means the rate rule (`fixed`, `by_weight`, `free_over_amount`), not a carrier;
a missing method is shown as **Not recorded**. The published nullable string
fields remain accepted. Adjustments use signed `amount_minor` with no `kind`;
the projection contains no guest email. Final pages omit `next_cursor`. Order numbers are positive JSON integers; unsafe
integers are rejected rather than displayed with silently rounded digits.
E2E-ADMIN connects PR #47 and exercises seeded orders through real staff sessions.
Shipping/refund action buttons are absent while
the corresponding APIs are pending.

## Acceptance

C-22b adds a session-guarded **Data privacy** page in store navigation. It shows
the owner-approved English and Chinese support-deletion notice through typed
messages, including the 30-day processing and export-copy commitment. This is
information only: no customer data read, deletion control, API, or support
workflow is implemented here.

`bash scripts/check_all.sh` includes frontend source gates. Bun tests cover
transport, validation, auth races and exact money formatting. Playwright covers
login, product list/create/edit, SKU edits/archive, upload/attachment, order
list/detail, logout and session expiry on desktop and mobile, with axe checks.
`tests/frontend` uses explicit contract fixtures and cannot prove backend
authorization. `tests/e2e` separately uses the real stack and retained DB witnesses;
its current-SHA CI receipt determines integration acceptance.

Visual golds must be generated by the pinned CI container. Push a source commit
with `[visual-baseline-update]`, download that run's artifact, then run
`check-baselines.ts` and `verify-baseline-artifact.ts` before committing its PNGs. Only an intended visual change (red comparison) needs new golds
and provenance. Local browser runs may check functionality but never author
committed golds. No Go backend, SQL migration or generated OpenAPI is changed by
this card.
