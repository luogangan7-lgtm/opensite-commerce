## Reading status and evidence

- `PASS` requires an executed assertion, final source SHA, CI job/run URL and retained receipt. A green job containing FIXME tests does not make those flows PASS.
- `FIXME(PR #…)` identifies a declared upstream dependency. It remains incomplete until that PR is merged and the real flow executes on the final SHA.
- `BLOCKED(reason)` identifies missing implementation, credentials/authorization, or current-SHA execution evidence. Existing automated component coverage is listed separately from missing E2E coverage.
- Run receipts must distinguish executed/passed/failed/FIXME/skipped counts. Missing services, missing seed, unexpected 401/404, empty page and test discovery failure must fail; they cannot silently skip or satisfy a flow.
- Execution evidence below is filled only after CI finishes. Baseline coverage is not evidence that a new final SHA passed. Backend checks and browser checks must refer to the same final SHA before MVP delivery.

## New E2E job and promotion policy

`mvp-e2e / mvp-e2e` starts as a **nonrequired** check. It must fail on executed assertion/setup errors; it must not use `continue-on-error` or convert missing dependencies into green executed flows. `scripts/e2e/run.py` owns CI-only disposable Compose setup, seed, health checks, browser result and receipts. The workflow then runs the existing `scripts/ops_drill.sh` backup → disposable volume loss → restore drill and retains its separate receipt. Both steps must succeed; browser readiness cannot substitute for restore. Existing `foundation` and `frontend` checks stay unchanged; the new job does not replace them or change repository settings.

Initial browser inventory: `tests/e2e/storefront.spec.ts` covers published home/list/detail/CMS/navigation/404 and host denial; `tests/e2e/admin.spec.ts` covers rejected credentials, the anonymous guard, a real owner login (owner created by `cmd/bootstrap-admin` through the temporary restricted bootstrap LOGIN) → session → logout, and anonymous private API denial; `tests/e2e/mvp-gaps.spec.ts` declares unfinished guest purchase, staff SKU/media/publish and real-API admin orders flows as FIXME. The runner locks thirteen executed test titles and three declared gap titles across desktop/mobile: **26 passed tests and 6 FIXME results**, zero unexpected/flaky results; anything else fails. The PR #83 assertion signs in through the real UI, reads the owner catalog, keeps the genuine browser cookie alive through tenant activity past its original one-minute idle expiry without polling the session endpoint, rejects a different tenant and a missing-CSRF write, then creates and reads back a product. This is the enforced inventory, not a passing claim before its current-head CI receipt. The C-19a increment adds a real signed Fake webhook API scenario with independently checked persisted facts. Its ready order is an owned SQL fixture; it does not clear the unfinished browse/cart/checkout purchase journey. The Fake scenario has historical E3 evidence in run `38455561681` on `d37cf3a`; that receipt reports 24 expected, 8 FIXME, zero unexpected/flaky, and both payment SQL witnesses PASS. Subsequent documentation or main-integration commits are covered only by their own [PR #119 CI receipts](https://github.com/luogangan7-lgtm/opensite-commerce/pull/119). Accessibility runs on each covered page in desktop/mobile; existing reviewed visual comparisons stay in `frontend`.

Promotion requires all critical flows above implemented and executed, **zero FIXME/BLOCKED critical rows**, stable current-SHA CI runs, retained artifacts and independent review. The owner explicitly adds the required check in repository settings. C-24a does not change branch protection/settings and does not represent this infrastructure increment as completed MVP delivery.
